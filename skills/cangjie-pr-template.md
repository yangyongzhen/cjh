# PR 模板（仓颉项目）

## 标题

`<type>(<scope>): <简述>`
type 取值：`feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` / `build`

## 正文模板

````markdown
## 背景 / 问题
（为什么要改：现象、影响面、复现步骤或 issue 链接）

## 改动内容
- …
- …

## 验证方式
- [ ] `cjpm build` 通过
- [ ] `cjpm test` 通过（新增用例：…）
- [ ] 手工验证：命令 / 场景 / 观察到的结果

## 影响与兼容性
（是否破坏兼容、是否需要迁移、是否要同步改文档或版本号）

## 关联
Closes #<issue>   /   Refs #<issue>
````

## 提交前自检清单

- [ ] 改动能被一句话说清，且只做这一件事（不夹带无关重构或纯格式化）
- [ ] 新行为有对应测试：新功能覆盖主路径 + 错误路径 + 一个边界；**bug 修复先有复现用例**再修
- [ ] 测试全绿，且贴出跑过的命令与结果
- [ ] 文档同步（README / 设计文档 / 变更记录）
- [ ] 无残留调试输出、无用文件、一次性脚本
- [ ] 没有提交敏感信息（token、私钥、本地绝对路径）

## 评审侧关注点（作者可先自查）

| 关注点 | 自查问题 |
|---|---|
| 单一职责 | 这个改动如果拆成两个 PR，是否更清楚？ |
| 兼容性 | 有没有改动公开 API / 配置格式 / 产物路径？ |
| 边界 | 空输入、超长输入、并发访问想过没有？ |
| 资源 | 文件句柄、子进程、锁都有对应的释放/解锁路径吗？ |
| 可测性 | 新增逻辑能脱离 UI / 网络单测吗？ |
