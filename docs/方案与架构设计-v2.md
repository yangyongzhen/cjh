# cjh 方案与架构设计（v2）：从"仓颉实现"到"生态级差异化"

> 最后更新：2026-08-22
> 性质：后续开发的指导性设计文档
> 原则：不追求"用仓颉复刻一个 agent"，而是回答"仓颉 agent 凭什么存在"

---

## 0. 立项初衷（用户原话）

> 当下的 agent 方案有很多，如 codex、claude、deepseek 的 dsh，pi 和 omp 等等。
> 不能只是用仓颉实现个就算是创新吧？那样并没有太多新意。
> 要做就抱着做最好的态度，要体现出仓颉独有的优势和做出自己的特点来。
> 比如 dsh 的插件机制就很强大，可以很多人给他贡献生态插件。
> 那么你的这个设计的优势呢？

**本文档的一切设计，围绕回答上面这个问题展开。** 三个硬约束：

1. **不重复造轮子**：功能层面主流 agent 已证明可行，功能堆砌无意义；
2. **仓颉独有优势是前提**：别的语言能轻易做到的，不构成竞争力；取长补短，好的当然可以借鉴，但仓颉语言特性带来的差异化更值得做；
3. **生态贡献是目标**：像 dsh 的插件生态一样，让社区愿意为 cjh 贡献——这要求插件门槛足够低、分发足够顺、信任机制足够完善。

---

## 1. 现状：agent 生态的结构性痛点

主流 agent 已走过"证明可行"阶段，进入"生态混战"。盘点（基于公开资料与代码研究）：

| Agent | 实现 | 特点 |
|---|---|---|
| Codex CLI | Rust | OpenAI 生态绑定、TUI、审批流 |
| Claude Code | TS | 技能（skills）、MCP 支持、企业权限模型 |
| DeepSeek dsh | — | **插件机制突出**，社区贡献生态插件 |
| pi | TS+Bun | 自我扩展（skills）、模块化极佳（ai/agent/tui 分离） |
| omp | Rust+TS | 工程级 TUI、扩展/自定义工具/MCP、agent 编排 |

**共同痛点（这是机会所在）：**

1. **供应商锁定**：Codex 绑 OpenAI、Claude 绑 Anthropic，换模型=换 agent。协议层统一但厂商绑定的现状未破。
2. **插件生态碎片化**：每个 agent 有自己的插件格式（dsh 插件、pi skills、omp extensions、MCP 工具），**彼此不兼容**，社区贡献被分散。
3. **运行时包袱**：TS 系依赖 Node/Bun 运行时 + npm 依赖树；Rust 系体积大。分发与部署成本高。
4. **安全模型参差**：多数 agent 默认全权限（可执行任意命令），审批流是"事后确认"而非"事前最小权限"。
5. **上下文管理原始**：compaction 多是截断/摘要，缺乏结构化记忆分层。
6. **TUI 体验两极**：顶级（omp/pi）与可用（多数）差距巨大，但都不是架构核心。
7. **无信任链/可审计性**：插件/技能代码来源不可验证，供应链风险。

**结论：下一个 agent 的价值不在"又一个 CLI 工具"，而在回答——用什么语言/架构/生态策略，能同时解决以上多个痛点。**

## 2. 差异化定位：cjh 的立身之本

仓颉语言的特性恰好命中上述痛点中的 4 个。这是"为什么是仓颉"而非"顺便用仓颉"：

| 仓颉特性 | 解决的痛点 | 差异化优势 |
|---|---|---|
| **静态编译单二进制**（cjnative） | 运行时包袱、分发成本 | 无 Node/Bun/npm 依赖树，`一个文件 = 一个 agent`，<10MB |
| **强安全语言设计**（安全 DNA） | 安全模型 | 插件/技能编译期类型检查，内存安全，恶意代码风险结构性降低 |
| **多后端编译**（cjnative/cjvm + 鸿蒙位） | 平台覆盖 | 未来可原生跑鸿蒙（华为生态位），跨端同构 |
| **M:N 轻量线程 + 高性能** | 上下文管理、并发 | 原生并发处理流式/多 agent，低开销 |
| **国产根技术** | 信创/自主可控 | 政企、金融等敏感场景无涉外运行时依赖 |

**定位一句话**：cjh 不是"仓颉版 Claude Code"，而是 **"单一静态二进制 + 类型安全插件生态 + 协议中立 + 鸿蒙原生位"的下一代编码 agent**——用语言特性解决生态痛点，而非功能堆砌。

**"仓颉独有"的严格定义**：上表中每一项，都必须回答"为什么必须是仓颉"——

- 单二进制：Node/Rust 系 agent 做不到零依赖分发（有运行时/工具链包袱），**仓颉 cjnative 天然如此**；
- 类型安全插件：TS 插件是运行时解释、JS-X-Ray 静态扫描兜底（dsh 的 poison-guard 就是这么补的），**仓颉插件直接编译期类型检查**，从源头消除一类供应链攻击；
- 鸿蒙位：主流 agent 无一覆盖，**仓颉是鸿蒙官方语言**，这是独占位；
- M:N 线程：TS 的 worker 有共享内存限制、Rust 的 async 有生态复杂度，**仓颉的轻量线程是语言内建**。

**设计评审标准（借力而非排斥）**：主流 agent 的成熟设计（插件生态、MCP、审批流、记忆管理等）**应当借鉴、取长补短**——这是行业共识，不该为了"差异化"而排斥。评审的关键不是"别人有没有做过"，而是：**借鉴之后，仓颉是否带来了增量价值**。

- 借鉴 dsh 的插件机制 → 仓颉版本用**编译期类型安全 + 签名信任链**补上 JS 生态靠运行时扫描兜底的缺口（增量：安全）；
- 借鉴 omp 的 TUI/扩展架构 → 仓颉版本用**单二进制 + 零依赖**降低分发门槛（增量：分发）；
- 借鉴 MCP 工具协议 → 仓颉版本天然**类型化 schema**，协议与实现零阻抗（增量：开发效率）；
- 完全照搬且无任何增量 → 才需要质疑其存在意义。

一句话：**"好的设计当然可以借鉴，但借鉴后有无仓颉增值才是评审标准"**——既不自闭排外，也不平庸照搬。

## 3. 总体架构（v2）

```
┌───────────────────────────────────────────────┐
│                 终端 TUI（cjterm）             │
│   差分渲染 / 滚动 / 编辑 / 审批交互 / 会话视图  │
└───────────────┬───────────────────────────────┘
┌───────────────▼───────────────────────────────┐
│            Agent 运行时（core）                │
│  主循环 / 消息状态机 / 工具调用协议 / 记忆分层   │
└───────────────┬───────────────────────────────┘
┌───────────────▼───────────────────────────────┐
│        能力安全模型（capability）              │
│  命令/工具/资源三域白名单 · 最小权限 · 审批链   │
└───────────────┬───────────────────────────────┘
┌───────────────▼───────────────────────────────┐
│            插件/技能系统（生态核心）            │
│  cjpm 插件包 · 技能即文件 · 沙箱执行 · 信任链   │
└───────────────┬───────────────────────────────┘
┌───────────────▼───────────────────────────────┐
│           LLM 协议层（协议中立）               │
│  OpenAI 兼容 / Anthropic / 本地模型 / 聚合网关  │
└───────────────────────────────────────────────┘
```

**与 v1 的架构演进**：v1 是"能跑"（agent 循环+工具+单协议）；v2 把**能力安全、插件生态、协议中立、记忆分层**提升为一等公民。

## 4. 核心子系统设计

### 4.1 协议中立层（已建基础，强化）

- 现状：`LlmProvider` 接口 + OpenAI/Anthropic 实现，`CJH_PROVIDER` 切换
- 演进：**Provider Registry**（运行时注册任意兼容端点）+ **模型能力描述**（上下文窗口/工具支持/费用——驱动 agent 自适应）
- 关键：**不绑定任何厂商**，`settings.json` 声明即可切换；默认零厂商依赖（离线 mock 可用）

### 4.2 能力安全模型（升级为一等公民）

v1 的 capability 只有命令白名单。v2 扩展为**三域模型**：

```json
{
  "identifier": "default",
  "commands": ["greet", "system:*"],
  "tools":   ["bash", "read_file"],
  "resources": {
    "fs":  ["$HOME/project/**", "!/tmp/secret/**"],
    "net": ["api.deepseek.com"],
    "proc": ["!rm", "!mkfs"]
  },
  "approval": ["bash:write", "proc:*"]   // 需人工确认的操作
}
```

- **事前最小权限**（非事后审批）：未声明即拒绝
- **审批链**：危险操作（写文件/执行命令）默认需确认，TUI 内嵌审批 UI
- **资源级控制**：文件路径 glob、网络白名单、危险命令黑名单
- 这套模型独立于 LLM 层，**任何 provider 都受同一安全边界约束**

### 4.3 插件/技能系统（对标 dsh 强插件 + 超越）

这是差异化竞争的主战场。设计目标：**让社区愿意为 cjh 贡献插件**。

**a) 插件 = 技能 + 工具 + 配置 的三位一体包**

```
~/.cjh/plugins/<name>/
├── plugin.json      # 元数据（id/版本/权限声明/作者/校验和）
├── skills/          # 技能文件（prompt 模板 + 约束）
├── tools/           # 工具实现（仓颉源码 或 WASM 或 声明式命令）
└── config/          # 插件默认配置
```

**b) 三种工具实现形态（分层开放）**

| 形态 | 适用 | 安全级别 |
|---|---|---|
| **声明式**（JSON Schema + shell 模板） | 简单命令封装 | 高（受限执行） |
| **WASM**（编译后沙箱） | 需要逻辑的插件 | 高（无系统调用） |
| **仓颉原生**（编译进主二进制） | 深度集成 | 需签名/审查 |

**c) 技能即文件（skills）**：参考 pi/omp 的经验——技能是**可版本化、可分享的文本资产**（prompt + 工具引用 + 使用约束），不是代码。降低贡献门槛：写 Markdown 即贡献插件。

**d) 信任链**：插件元数据含**发布者签名 + 内容校验和**，本地记录"已信任发布者"列表。未信任插件降级为沙箱模式或拒绝加载。这直接回应供应链痛点（Claude/dsh 的插件分发都缺这个）。

**e) 生态策略**：发布到**仓颉中心仓**（pkg.cangjie-lang.cn，cjpm 已对接），`cj-tauri plugin add <name>` 即装即用。借仓颉官方生态通道，而非自建孤岛。

### 4.4 记忆分层（上下文管理）

现状：会话 JSON 全量持久化。痛点：长会话 token 爆炸、跨会话无记忆。

v2 设计三层记忆：

```
工作记忆（当前会话）→ 摘要记忆（历史压缩，LLM 生成摘要）→ 长期记忆（跨会话，结构化索引）
```

- **结构化**：文件/命令/决策以结构化事件记录（非纯文本），可检索
- **压缩策略**：超窗口时按"工具结果→中间推理→早期对话"优先级压缩
- **记忆检索**：长期记忆支持语义/关键词检索，agent 按需拉取（而非全量注入）

### 4.5 多 agent 编排（远期）

omp 有 agent hub 的概念。cjh 远期支持**子 agent 并行**（研究/编码/审查分角色），基于仓颉 M:N 线程低成本实现。v2 文档先留接口位。

### 4.6 TUI（cjterm 持续打磨）

- 已具备：差分渲染、滚动、转义序列、状态行
- 规划：内嵌编辑器（多行输入）、审批弹窗、会话时间线视图、模型切换面板
- 原则：TUI 是**交互外壳**，不是架构核心——所有功能经 API 可被无头模式复用

## 4.7 并发执行引擎（速度是硬指标）

明确要求"执行速度要快，能并行的并行"。仓颉的 M:N 轻量线程是天然优势，设计如下：

### 并行层级

| 层 | 并行度 | 实现 |
|---|---|---|
| **工具调用并行** | 无依赖的工具同时执行 | 工具调用图（ToolCallGraph）分析依赖 → 并行调度 |
| **文件操作批量** | 同批次读写并行 | 线程池（固定 worker） |
| **多 agent 编排** | 研究/编码/审查子 agent 并行 | 子 agent 独立线程 + 结果聚合 |
| **流式与渲染** | LLM 流式接收与 TUI 渲染分离 | 接收线程 + 渲染循环（已实现） |
| **预热** | 连接/模型初始化提前 | 启动时预建 provider 连接池 |

### 工具调用图（核心设计）

工具不是无条件并行——存在依赖（读文件→改文件→验证）。设计：

```
工具调用序列 → 依赖分析（参数引用/副作用声明）→ DAG → 分层调度
```

- 工具声明 `sideEffects: read|write|exec` + `dependsOn: [工具名]`
- 无依赖的工具同层并行（如并发读多个文件、并发跑多个 grep）
- 有依赖的串行等待
- 通过仓颉 `spawn` 原生实现，无外部并发库

### 性能基线（目标）

- 启动到可交互：< 50ms（单二进制 + 无运行时初始化）
- 单工具调用开销：< 5ms（本地工具，不含 LLM 往返）
- 并行工具批：N 个独立工具 ≈ 单工具时间（线性加速）
- 内存：常驻 < 30MB（对照 Node 系 agent 的 100MB+）

### 延迟隐藏

- **流式先行**：LLM 首个 token 到达即渲染（已实现 takeDelta）
- **预取**：agent 声明下一步可能读的文件，后台预读
- **异步审批**：危险操作审批不阻塞其他工具执行

## 4.8 IM 渠道接入层（远程协同）

明确要求"开放接入外部客户端，如微信、钉钉等"。dsh 生态已验证这是刚需
（DingTalk/Feishu/Telegram/WeCom/WeChat/QQ 全渠道插件存在）。cjh 设计为**一等架构能力**而非插件拼凑：

### 设计：Channel 抽象 + Agent Gateway

```
┌─────────────────────────────────────────┐
│              Agent Gateway               │
│   会话管理 · 队列 · 审批转发 · 通知推送    │
└──────┬─────────┬─────────┬──────────────┘
       │         │         │
   ┌───▼──┐ ┌───▼──┐ ┌───▼──┐
   │ TUI  │ │ HTTP │ │ IM   │  ← Channel 适配器（可插拔）
   └──────┘ └──────┘ └──────┘
   （本地）  （Web）   （微信/钉钉/飞书/Telegram…）
```

### Channel 接口

```cangjie
public interface Channel {
    public func sendMessage(chatId: String, content: String): Unit
    public func sendApproval(chatId: String, req: ApprovalRequest): Unit
    public func onMessage(cb: (String, String) -> Unit): Unit  // (chatId, text)
    public func onApprovalResult(cb: (String, Bool) -> Unit): Unit
}
```

- **会话隔离**：每个 chatId 一个独立 agent 会话（远程多人各自上下文）
- **审批远程化**：危险操作经 IM 推送审批卡片（确认/拒绝），dsh 已有此模式
- **流式回传**：LLM 增量经渠道逐条推送（消息形式，非整块）
- **无公网依赖**：优先 WebSocket 长连接/长轮询（免公网回调 URL，dsh 已验证此路径）

### 首批渠道（按优先级）

1. **HTTP/Web**：自带 Web UI（远程访问 + 手机浏览器）
2. **企业微信 / 钉钉**：国内协同刚需
3. **Telegram / 飞书**：开发者常用
4. **微信（个人）**：bot 受限，降级为通知推送

### 架构收益

- **一套 agent 逻辑，多端触达**：TUI/Web/IM 都是 Channel，agent 核心零改动
- **远程协同**：审批、通知、会话管理全部可远程
- **与插件系统协同**：渠道本身可以是插件（注册 Channel 实现），但**核心网关内置**

## 5. 与主流 agent 的对比矩阵（目标态）

| 维度 | Codex | Claude Code | dsh | pi/omp | **cjh** |
|---|---|---|---|---|---|
| 运行时 | Rust | Node | 轻量 | Node/Bun | **零依赖单二进制** |
| 供应商 | OpenAI | Anthropic | DeepSeek | 多 | **协议中立多 provider** |
| 插件格式 | 专有 | skills | 专有插件 | skills/ext | **cjpm 包 + 三形态** |
| 安全模型 | 审批 | 权限+审批 | 基础 | 基础 | **三域最小权限** |
| 信任链 | 无 | 无 | 无 | 无 | **签名+校验和** |
| 鸿蒙 | 无 | 无 | 无 | 无 | **原生位** |
| 插件生态 | 封闭 | 开放 | **强** | 开放 | **借官方中心仓** |
| 执行并行 | 中 | 中 | 中 | 中 | **M:N 线程 + 工具 DAG 并行** |
| IM 远程协同 | 无 | 无 | **有** | 无 | **Channel 网关内置** |

**cjh 的"护城河"不是单一功能，而是组合**：单二进制 × 类型安全 × 协议中立 × 三域安全 × 信任链 × 鸿蒙位——任何单一对手都难以同时具备。

## 7. 设计原则（后续开发守则）

1. **语言特性即差异化**：能用仓颉类型系统/编译期能力解决的，不用运行时检查（如插件工具的 Schema → 编译期校验）
2. **安全前置**：capability 默认拒绝，一切新能力先过安全评审
3. **协议中立**：任何 provider/插件格式都不做硬编码，Registry 模式
4. **零依赖优先**：能纯仓颉实现的不用外部库（cjterm 已示范）
5. **无头可用**：所有交互功能有 API 形态，TUI 只是外壳；Channel 抽象使 TUI/Web/IM 平等
6. **并行优先**：能并行的绝不串行（工具 DAG/流式/多 agent），速度是产品体验的一部分
6. **生态开放**：插件发布走官方中心仓，降低贡献门槛（技能即 Markdown）
7. **模块化设计**：在实现过程中能抽象复用的模块，单独独立出来贡献给生态复用
8. **单元测试**：每实现完一个功能，都要做充分的单元测试保证质量

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 仓颉生态早期，贡献者少 | 技能即 Markdown 降低门槛；借官方中心仓与大赛渠道 |
| WASM 工具沙箱工程量大 | 先做声明式 + 签名原生，WASM 后置 |
| 与成熟 agent 竞争 | 不打功能战，打"组合优势 + 安全 + 信创"差异化 |
| 鸿蒙开发环境门槛 | 架构留位，验证靠 DevEco 环境（社区/官方） |
| 模型能力差异大 | Provider Registry 的模型能力描述层兜底 |
| IM 渠道平台政策多变（微信 bot 受限） | 渠道分层：强渠道（企微/钉钉/Telegram）优先，弱渠道降级为通知 |
| 并行执行引入竞态 | 工具 DAG 显式声明依赖；默认保守（无声明则串行） |
