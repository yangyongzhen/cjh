```
配置（config/）→ ~/.cjh/{settings.json, auth.json, sessions/}
    │
```

## 三、踩坑记录（重要）

### 3.1 子包链接：cjpm 的坑

**现象**：`src/llm/`、`src/agent/` 等子包编译成 staticlib 成功，但主包 exe 链接报
`undefined reference to _CGP7cjh.llmiiHv`。

**根因**：cjpm 编译子包为 .a 后，主包 exe 的自动链接**不会带上子包库**；
手写 `link-option = "-Ltarget/release/cjh -lcjh.agent ..."` 又会**覆盖** stdx 自动链接，导致 stdx 符号缺失。

**解法**：link-option 留空，依赖表也留空——cjpm 在 clean 构建下会自动处理子包链接。
（首次失败的 link-option 残留会干扰后续构建，务必 `cjpm clean` 再试。）

### 3.2 包间循环依赖

agent → tools → llm → agent 成环。解法：把无依赖的模型类型（ChatMessage/ToolCall/ModelResponse）
抽到独立包 `cjh.model`，依赖方向变为单向。

### 3.3 仓颉语法要点（本次新踩）

| 主题 | 结论 |
|---|---|
| 子包名 | 目录 `src/llm/` 内包名须为 `cjh.llm`（点分包名） |
| import 顺序 | **所有 import 必须在声明之前**；FFI/函数定义不能插在 import 中间 |
| Byte 字面量 | `10u8`（Byte 是 UInt8 别名，无 toByte()） |
| String 下标 | `s[i]` 返回 **Byte**（UTF-8 字节），非 Rune；切片 `s[0..n]` |
| lambda 多参 | `{ a, b => ... }`（无括号）；单参 `{ x => }`；空 `{ => }` |
| lambda 捕获可变变量 | 禁止（"needs to be called directly"）；用类静态成员中转 |
| Option 默认值 | `opt ?? default`（无 getOrElse） |
| CPointer→CString | `CString(ptr)` 构造（unsafe 上下文） |
| 数组构造 | 无 `[a,b]` 字面量；用 `Array(n, repeat: v)` 或 ArrayList |
| 环境变量 | FFI `getenv`（std.env 无封装）；std.env 只有 ConsoleReader/Writer |
| 标准输入 | `getStdIn().read(buf)` 流式读（ConsoleReader 无公开构造） |
| 集合 map | ArrayList 无 map；用 for 循环 |
| JsonValue 形态判断 | 必须 `match (v.kind())`，不能 `==`/`!=` |

### 3.4 TUI 层新增踩坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **字节截断破坏 UTF-8** | `line[0..cols]` 按字节截断，切到中文中间 → 后续 `Rune(单字节)` 抛 `Invalid utf8` | 不预截断；迭代码点（`for (cp in text)`）自然截断到列宽 |
| **Rune(单字节)** | `Rune(line[i])` 对 UTF-8 中间字节（>127）抛异常 | String 迭代得到 UInt32 码点，`Rune(cp)` 还原字符 |
| **if-let 需 Some 模式** | `if (let x <- opt)` 绑定仍是 Option | 必须 `if (let Some(x) <- opt)` |
| **`??` 优先级** | `a ?? "" == "1"` 被解析错 | 加括号 `(a ?? "") == "1"` |
| **link-option 覆盖子包链接** | 手写 link-option 后子包 .a 不自动链 | link-option 留空（除 C 库），子包由 cjpm 自动处理；改 link-option 后 `cjpm clean` |
| **新增子包漏链** | 新加 tui 子包后 undefined reference | `cjpm clean` 重建（增量缓存不识别新子包） |

### 3.5 配置/会话层新增踩坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **foreign 函数改名后无定义** | `cjGetenv` undefined reference | foreign 函数名须与 C 符号一致（用 `getenv` 匹配 libc），不能随意改名 |
| **类内 static foreign** | `@C public foreign static func` 语法错 | foreign 顶层声明 + 类内静态方法包装 |
| **复合 if-let** | `if (let a <- x, let b <- y)` / 分号都错 | 用 `&&` 连接：`if (let a <- x && let b <- y)` |
| **Directory.list 不存在** | 遍历目录报错 | 用 `Directory.walk(path, cb)` 回调式 |
| **DateTime 无 toUnixTimestamp** | 时间戳方法名错 | `toUnixTimeStamp(): Duration`（注意大小写）；会话 ID 用 Duration 转秒.毫秒 |
| **if-else 分支类型不一致** | else 分支表达式返回值被丢弃 | `let _ = expr` 显式丢弃 |
| **lambda 捕获可变局部变量** | "needs to be called directly" | 用类静态成员（SessionState.current / CliSession.id）中转 |

子包源码改动后：`cjpm clean && cjpm build`（增量缓存可能误报循环依赖/漏链）。

### 3.7 LLM 截断死循环（本次新踩，OMP 式三层防线）

**现象**：`deepseek-v4-flash` 单轮 max_tokens 装不下完整 H5 游戏（~5000+ 字符），一次性 `write_file` 被截断 → 文件不完整（缺 `</script></body></html>`）→ LLM 收到截断警告后**重新 `write_file`** → 再次截断 → 死循环。

**根因分析**（对照 OMP/Aider/Cursor）：
1. **Payload 膨胀 vs max_tokens**：write_file 让模型输出几千行代码，极其消耗 Output Tokens，极易触发截断上限
2. **截断检测不可靠**：DeepSeek 返回 `finish_reason=tool_calls` 而非 `length`，`finish_reason=="length"` 检测不触发
3. **重写倾向**：模型收到"文件不完整"警告后，注意力机制趋向于重新发起 write_file，而非增量续写
4. **Cache 前缀破坏**：每轮追加 tool 结果破坏了前缀，导致 DeepSeek prompt cache 命中率低

**解法**（三层防线，对齐 OMP）：

| 层 | OMP 做法 | cjh 实现 |
|---|---|---|
| 工具契约层 | 拆分 write（骨架）+ edit（增量） | `AppendFileTool` 新增 + `WriteTool` content 软上限（150 行/4000 字符）超限警告但不阻断 |
| 截断打断层 | JSON 损坏时落盘已有片段 + 绝对指令打断 | `ModelResponse.truncatedPaths` + `StreamAccumulator` 记录被截断 write_file/edit_file 的 path → agent loop 注入 `[System Notice]` 绝对指令（已落盘、禁止重写、强制 append_file 续写到闭合），斩断"重写 → 截断 → 重写"死循环 |
| 前缀冻结层 | 静态 System Prompt + Tools 定义 + 尾部追加 History | messages 数组审计确认 append-only；`truncateToolResult` Tool Output 压缩 Hook（>6000 字符 Head/Tail 裁剪） |

**关键踩坑点**：

| 坑 | 现象 | 解法 |
|---|---|---|
| **finish_reason 不可靠** | DeepSeek 返回 `tool_calls` 而非 `length`，截断检测不触发 | 改用 `tryParseJson` 失败即标记 `truncated=true`（因 DeepSeek 不报告 `finish_reason=length`） |
| **repairTruncatedJson 方案选择** | JSON 被截断时，方案1（截断到上一个完整字段）丢弃 content，方案2（补 `"}`）保留 content | 方案2优先于方案1，保留被截断 content 让前半段落盘 |
| **enum 模式参数数量** | `PatchOp.LineAnchor` 加 String 参数后，`case LineAnchor(_)` 编译报 "enum pattern's parameters size is wrong" | 所有 `LineAnchor(_)` 改为 `LineAnchor(_, _)`，漏改一处即编译失败 |
| **提示词语言** | 中文 systemPrompt + 工具 description 浪费 token | 全改英文（bash/read_file/write_file/append_file/grep/list_dir/hashline_edit + systemPrompt + [System Notice]），保留 "answer in Chinese" 让模型回复中文 |

### 3.9 工具层潜伏 bug（第十二轮单测实测揪出，全部已修）

> 新增 `src/tests/`（62 用例）与 `src/core_funcs_test.cj`（根包 19 用例）后，实测暴露 6 个从未被发现的 bug。教训：**零测试覆盖 = 带病运行**（edit/hashline 两个核心工具此前从未真正工作过）。

| Bug | 现象 | 根因 | 修复 |
|---|---|---|---|
| **edit 替换毁文件** | 任何 `edit` 替换把文件变成数字串（`let x = 1` → `101010810111632...`） | `replaceString` 逐字节 `result.append(text[i])`，`StringBuilder.append(Byte)` 把字节当**十进制整数**追加 | 改整段 String 切片（`text[lastCopy..i]`）追加，UTF-8 安全 |
| **hashline 必抛异常** | `HashlineEditTool` 每次调用 `OverflowException: mul` | FNV-1a 用 UInt32 直接乘法，`hash * 16777619` 溢出，仓颉默认溢出检查抛异常 | 全程 UInt64 运算 + 每步 `& 0xFFFFFFFF` 截断 |
| **grep/glob 目录搜索不递归** | 目录搜索只覆盖第一层；遇 `.git` 直接停止整个搜索 | 误以为 `Directory.walk` 递归——实测**非递归**（只遍历直接子项），且回调返回 `false` **终止整个遍历** | 显式递归子目录；忽略目录返回 `true` 只跳过 |
| **append_file 静默创建** | append 到不存在文件成功（OpenMode.Append 自动建文件），与 spec "Fails if not exist" 不符 | 仓颉 `OpenMode.Append` 对不存在文件会创建 | execute 前显式 `exists(path)` 校验 |
| **会话 ID 毫秒碰撞** | `save` 与 `saveFork` 同毫秒调用生成相同 ID，后者覆盖前者（parent 链错乱） | `newSessionId` 只有 `秒.毫秒` 精度 | 追加进程内静态计数器 `秒.毫秒.计数器` |
| **tool 消息丢 name 字段** | 会话保存/恢复后 tool 消息工具名丢失 | `ChatMessage.toOpenAiJson()` 对 tool 角色只写 `tool_call_id`/`content` | 非空 name 补写 |
| **glob/list_dir 静态状态竞态** | V2d 并发执行 + 子代理共享 registry 时并发调用互相踩踏 | `GlobState`/`ListDirState` 用静态可变字段（为绕 lambda 捕获限制） | 改每调用实例状态（`let st = GlobCallState()`，对齐 GrepTool 的 GrepWalkState 模式） |
| **hashline 多锚点行号偏移缺失** | 前序锚点 Insert/Delete 后，后续 `@@N` 定位错行（内容校验必然误拒） | apply 无偏移跟踪（注释声称有，实际没有） | 加 `lineOffset` 累计校正 |
| **同锚点多行插入顺序颠倒** | `@@1\n+x\n+y` 得 `[y,x,...]` | 块内 Insert 用固定 `lineIdx`，未递增插入位置 | 恢复 `insertAfterLine` 递增 |
| **capability 资源检查缺口** | `append_file/edit_file/hashline_edit/glob` 完全跳过 fs 白名单检查；append/edit 写文件按读检查 | `executeGuarded` 的 path 检查列表只有 4 个工具；`isWrite` 只认 `write_file` | 补全 8 个带 path 工具 + 写类工具 isWrite=true |

**仓颉新踩坑**（测试编写时）：

| 坑 | 现象 | 解法 |
|---|---|---|
| **块注释嵌套** | 注释里写 `**/*`（glob 字面量）触发 `/*` 嵌套注释解析，报 `illegal character` | 注释里不写 `星号斜杠` 序列 |
| **无默认参数** | `func f(a: Bool = false)` 编译错 | 重载或调用处显式传参 |
| **无命名参数（普通参数）** | `f(x: 1)` 报 "target is not a named parameter" | 只有 `p!:` 声明支持命名；普通参数按位置传 |
| **零参 lambda** | `{ () => ... }` 编译错 | 写 `{ => ... }` |
| **字符串迭代给 Byte** | `for (ch in s)` 的 ch 是 `Byte`（UInt8）非码点 | 比较用 `120u8`，不是 `120u32` |

### 3.10 Windows 交叉构建（跨平台终端层，第十四轮）

**目标**：Linux 上 `cjpm build --target x86_64-pc-windows-gnu` 直接产出 Windows exe（已验证 `dist/cjh-v1.3.2-windows-x64.exe`，PE32+ 7.97MB）。**不需要 Windows 版 SDK**——cangjie SDK 自带 `lib/windows_x86_64_cjnative` 平台 std 库，交叉编译自动切换。

| 坑 | 现象 | 解法 |
|---|---|---|
| **根 link-option 是 Linux 专属** | `lld: error: unknown argument: --disable-new-dtags / -rpath`（ld.lld -m i386pep 不认） | `[package] link-option` 清空；Linux 运行时库位置改由 `cj-env.sh` 的 `LD_LIBRARY_PATH` 提供（发布静态链接不依赖） |
| **target 段无法覆盖 link-option** | `[target.x86_64-pc-windows-gnu] link-option = ""` 不生效（cjpm 只读 [package] 级） | 根清空是唯一路径；stdx 路径用 `[target.X.bin-dependencies].path-option`（该段有效） |
| **stdx 按平台独立发布** | `can not find package 'stdx.net.http'`（linux stdx 无 windows 平台目录） | gitcode.com/Cangjie/cangjie_stdx/releases 下载 `cangjie-stdx-windows-x64-<ver>.zip`（asset 名规律，下载需登录 401）解压到 `~/.cangjie/stdx/` |
| **`os` 是仓颉内置条件** | 需 `@When[os == "Windows"]` 而非自定义 cfg | 编译期自动注入目标平台（值：`Windows Linux macOS HarmonyOS`，大小写敏感），无需 `--cfg` |
| **`@When` 只能用于声明** | `@When[os == "Windows"] { return WB() }` 报 "expected declaration" | 两个同名函数各带 `@When` 互斥（编译期只留一个）；类声明/foreign 函数同样支持 |
| **`&var` 不能取地址** | `CPointer(&mode)` 语法错 | `LibC.malloc` 缓冲 + 手写小端读写（同 termios FFI 模式）；FFI 指针参数统一 `CPointer<UInt8>`（`Void` 未导入） |
| **Windows 目标名** | `x86_64-pc-windows-msvc` 报 "environment msvc not found" | 用 `x86_64-pc-windows-gnu`（SDK 自带 mingw/lld 工具链，无需外部安装） |
| **`os` 条件编译验证** | 单向编译无法证明另一平台后端被排除 | 交叉编译产物 `strings` 查符号：无 `tcgetattr/termios`（POSIX 后端排除）、有 `GetConsoleMode/ReadConsoleInputW`（Windows 后端编入） |

**部署**：Windows 产物已**静态化 stdx**（link-option 加 `-lcrypt32 -lws2_32` + path-option 指 stdx `static/`）——依赖从 42 DLL 降到 **exe + libcangjie-runtime.dll + libboundscheck.dll（3 文件）**，`dist/cjh-<ver>-windows-x64.zip`（4.8MB）整包分发。**单文件 exe 不可达**：仓颉 SDK 1.0.5 未提供 Windows 静态 runtime（`libcangjie-runtime.a` 仅 Linux 有，Windows 只有 DLL + import lib），`cjc --static` 仅对 Linux 生效；runtime DLL 又依赖 libboundscheck.dll（传递依赖无法消减）——等待官方发布 Windows 静态 runtime。构建用 `./scripts/winbuild.sh`（自动临时替换 root link-option，结束恢复；root link-option 的 `-rpath` 是 Linux 专属，lld/mingw 不认）。**Linux 默认静态单文件**：cjpm.toml 默认 `--static` + stdx `static/` 路径，`cjpm build` 直接产出零依赖单文件（仅系统 libc）；**静态下 `cjpm test` 会 double free 崩溃（SIGSEGV，仓颉运行时/测试框架组合 bug，发布二进制正常）**——测试用 `./scripts/test.sh` 自动切动态配置跑完恢复静态。

### 3.8 Hashline 编辑协议（对齐 OMP Hashline Edits）

**设计动机**：OMP 的编辑协议不是全量 Write，而是 Hashline Edits——带 Hash 锚点的精准局部编辑。

**核心机制**：
- **Hash 锚点**（`@@{hash}`）：行内容 FNV-1a 32-bit，取低 16 位转 4 hex，遍历所有行算 hash 匹配定位
- **防漂移**：文件变了导致哈希对不上，patch 被拒绝（`LocateError("无匹配行")`）
- **碰撞处理**：多行匹配同一 hash → `LocateError("哈希碰撞")`，要求模型提供更多上下文

**cjh 与 OMP 的两点差异**：

1. **行号锚点优先于哈希锚点**：
   - cjh 同时支持 `@@N`（行号锚点，**推荐**）和 `@@{hash}`（哈希锚点，**向后兼容**）
   - 原因：模型无法预先计算哈希值，实测 LLM 反复尝试各种 hash 格式都失败
   - 行号锚点对 LLM 更友好——模型用 read_file 看到的行号直接引用

2. **行号锚点加可选内容校验**（本次新增）：
   - 格式：`@@N content` — 定位第 N 行**并校验该行内容必须等于 content**
   - 不匹配 → `ApplyError("行号 N 内容不匹配：期望「content」，实际「...」")`，patch 被拒绝
   - 与 `-old` 双保险互补：`@@N content` 锚点定位时就校验（防漂移），`-old` 删除/替换时校验（防打错地方）

**效率收益**（OMP 实测基准）：
- 编辑成功率 6.7% → 68.3%（10× 提升）
- 输出 Token 减少 61%（重试循环消失）

**实现文件**：`src/tools/hashline.cj`（489 行）
- `HashlineEditTool`：工具入口，读文件 → 解析 patch → 应用 → 写回
- `HashlineEditParser`：解析 patch 文本为 `ArrayList<PatchOp>`
- `HashlineEditApplier`：应用 patch 到原文件行列表
- `HashlineHash`：FNV-1a 32-bit 哈希计算 + 行定位
- `PatchOp` 枚举：`LineAnchor(Int64, String)` / `HashAnchor(String)` / `Insert` / `Delete` / `Replace`

### 3.11 仓颉 String 字节切片校验 UTF-8 边界 + spawn 未捕获异常静默杀线程（2026-09-01 僵尸忙态事故，v1.3.5）

**现象**：TUI 回合早已结束（日志 `Agent.run 正常结束`），但状态行永久冻结在 `Streaming… (127s · 第4轮)`，看门狗每 60s 重复无效中断，之后所有 Enter 全走"打断"分支、排队消息永不发送。

**根因链（两层叠加，缺一不可）**：

1. **仓颉 `String[0..N]` 按字节切片且校验 UTF-8 边界**：切点落在多字节字符中间 → 抛 `IllegalArgumentException: Invalid utf8 byte sequence`。实测（1.0.5）：72 个 CJK 字符 `size=216`（size 单位是字节），`[0..18]/[0..45]/[0..60]`（3 的倍数=字符边界）正常，`[0..20]` 抛异常。中文密集内容上**任意固定字节阈值都可能落字符中间**。
2. **spawn 任务内未捕获异常只杀任务线程、进程存活**（实测）：异常不打断主循环、无崩溃栈——收尾逻辑静默死掉，比崩溃更隐蔽。

**触发路径**：compaction 把历史压成 673 字节中文 `[历史摘要]` 作为首条 user 消息 → `summarizeForMemory()` 内 `task[0..60]`（第 60 字节=0x8B，CJK 中间）抛异常 → 该调用在 TUI spawn 收尾块（entries.cj）**try/catch 之外**求值（`saveProjectMemory(dir, agent.summarizeForMemory())`，实参先求值）→ 收尾线程死亡 → `setAgentRunning(false)` 永不执行 → `agentRunning=true` 僵尸态。**短消息（≤阈值）不切片所以不复现**——上一轮 user 仅 33 字节安然无恙，本轮 673 字节必炸，属于"偶发"形态。

| 坑 | 现象 | 解法 |
|---|---|---|
| **`String[0..N]` 校验边界** | 中文内容切片抛 `Invalid utf8 byte sequence` | 统一用 `cjutil.truncateUtf8(text, maxBytes)`（回退合法字符边界，不抛）；`tailUtf8` 取尾部。新增切片前先问：内容会是中文吗？ |
| **`spawn {}` 未捕获异常** | 只杀任务线程、进程存活、无栈——最隐蔽的静默死 | spawn 任务里**收尾关键路径**（状态复位、队列出队）必须 try/catch 兜底，或包进函数后调用点捕获；禁止让 `spawn` 闭包裸奔 |
| **`String(Rune(byte))` 摩尔化** | `Rune(0xE4)` 按 Latin-1 编成 2 字节，逐字节 append 重建的串不是原串、长度翻倍 | 重建字符串必须整段 String 切片，禁止逐字节 append（与 `StringBuilder.append(Byte)` 按十进制输出同源） |
| **实参在 try 外求值** | `f(x, g())` 中 `g()` 抛异常时 try 管不到 | 关键实参先 `let` 接住，再接着进 try |

**修复**（v1.3.5）：`summarizeForMemory()` 两处裸切片改 `truncateUtf8`；entries.cj spawn 收尾块记忆保存独立 try/catch（`summarizeForMemory()` 实参先求值再接住），保证 `setAgentRunning(false)` 必达。回归测试 `src/agent/summarize_memory_test.cj` 用事故真实数据（byte60=0x8B）钉死：前提自证（裸切片必抛）+ 修复后全绿。

**排查方法论（本次耗时最长的部分）**：日志铁证 `run 正常结束` 已打印 → 死点在 run 返回之后；`.4` 会话文件 mtime vs `bin.md` 记忆文件 mtime 二分定位到 `store.save` 之后、`setAgentRunning(false)` 之前；spawn 静默死无法 attach 活进程取栈（进程早已"健康"存活）→ 只能靠文件 mtime + 日志窗口二分 + 最小复现实验证伪各假设。

### 3.12 裸 socket connect/write 无超时 → 首个 LLM 请求卡死、abort() 空转（2026-09-02 Thinking 442s 事故，v1.3.6）

**现象**：TUI 首个 LLM 请求发出后**状态行永久冻结**在 `Streaming… (127s · 第4轮)`，空闲看门狗自 10:10:49 起每 61s 触发，8 次 interrupt 全部无效；之后所有 Enter 走"打断"分支、排队消息永不发送。与 §3.11 的关键区别：日志里**没有** `Agent.run 正常结束`——run 线程本身还卡在第一个 LLM 请求里没返回。

**根因链（三层叠加，缺一不可）**：

1. **仓颉裸 `TcpSocket.connect` 没有超时参数**（1.0.5 实测）：TCP + TLS 路径（含 DNS 解析）在 connect 阶段挂死时，`readTimeout` 完全不起作用——它只在数据可读性检查上生效，覆盖不到 connect 本身；`write()` 大 payload 经代理也可能挂死，同样无超时。
2. **`HttpStreamClient.abort()` 打不断 connect 阶段**：`abort()` 只做 `close(this.socket)`，而 `this.socket` 在 `connect()` 成功返回后才赋值（`Some(tls)`/`Some(sock)`）——connect 挂死期间 `socket == None`，`case None => ()` 空转。中断信号传得到、但关不到一个还没建好的连接。
3. **请求阶段整体无"可中断的超时"**：connect / 写请求 / 读响应头 三个阶段都在主请求线程上直接同步调用，任何一个挂死 = 整个 run 永久挂起，看门狗的 interrupt 既无超时兜底、abort 又空转 → 双重失效。

**触发路径**：网络瞬态异常（当时 DNS 40ms→挂死；当前已恢复）+ 首个请求复用连接失败走新建路径 → `connect()` 在 DNS/TCP/TLS 某一步挂死 → `socket` 永远 `None` → 看门狗 `interrupt()` → `cancelChecker=true` 但 connect 不响应、`abort()` close(None) 空转 → run 永不返回 → `agentRunning=true` 僵尸态。

| 坑 | 现象 | 解法 |
|---|---|---|
| **裸 socket `connect` 无超时** | DNS/TCP/TLS 挂死时 `readTimeout` 不起作用，无限阻塞 | 任何可能无限阻塞的阶段用 `cjutil.runWithBudget` 包一层（spawn + `Future.get(pollMs)` 轮询 + 预算判定），把"无限阻塞"变成"有界可中断" |
| **`abort()` 关不到未建好的连接** | connect 阶段 `socket==None`，`close(None)` 空转，中断失效 | 中断不再依赖"关 socket"，改由 `runWithBudget` 的 `cancelChecker` 在预算轮询中主动判定并抛 `BudgetCancelledException`，≤pollMs 内响应 |
| **写请求无超时** | 大 payload 经代理 `write()` 挂死，无读超时窗口 | `tr.request(...)` 同样套 `runWithBudget`（30s 预算） |
| **仓颉：捕获可变局部变量的 lambda 必须直接调用、不能传参** | `runWithBudget(..., { => tr.request(path, hdrs, body) })` 报 `lambda capturing mutable variables needs to be called directly`（`hdrs`/`body` 是 `var`） | 传参前用 `let` 接住不可变快照（`let reqHdrs = hdrs; let reqBody = body.toJsonString()`），lambda 只捕获 let 局部量 |
| **spawn 任务内异常额外打 stderr** | 未捕获异常会向 stderr 打印报告，污染 TUI 输入框 | `runWithBudget` 内部用 `BudgetOutcome` 载体收住异常，task 闭包不裸抛（与 §3.11 spawn 静默死同源治理） |

**修复（v1.3.6，初版）**：新增 `cjutil.runWithBudget<T>(label, budgetMs, pollMs, isCancelled, task)` 预算竞速原语（`libs/cjutil/src/concurrency.cj`）——spawn 子任务执行 task，主线程每 pollMs 轮询结果并查 `isCancelled`，超预算抛 `BudgetTimeoutException`、被取消抛 `BudgetCancelledException`、task 异常原样重抛。首版把预算包在 **openai.cj 的调用点**（connect×2 + request×2）。

**修复（v1.3.7，下沉通用化）**：首版只覆盖了 OpenAI 兼容协议——anthropic.cj / ollama.cj 的同构调用点（`transport.connect()` + `transport.request()`）同样裸奔，且 openai 的 `warmup()` 预热路径也漏了。把预算**下沉进 `HttpStreamClient` 内部**（一处管所有现有+未来协议）：
- `connect()` 整体包 `runWithBudget`（预算 = `idleTimeout`，中断 = 本对象 `cancelChecker`——provider 建连前就注入，零额外传参），**预算内重试一次**（首连超预算可能是 DNS 瞬态抖动；被中断不重试），重试超预算才抛 `BudgetTimeoutException`
- `request()` 的 `write()` 同样包 `runWithBudget`（预算 = 新增 `writeTimeout` 字段，默认 30s）
- openai.cj 四处调用点全部还原为直调 `tr.connect()` / `tr.request(...)`（删除冗余包装 + `let` 快照 hack），`warmup()` 缩建连预算到 15s
- **anthropic / ollama / 未来新协议：零改动自动获得同款保护**——新协议只要复用 `HttpStreamClient` 就天然有界可中断，不再需要每个调用点记得包预算

**回归测试**：`libs/cjutil/src/concurrency_test.cj` 5 用例（T=Int64 / T=Unit / 异常重抛保类型 / 超预算耗时≈预算 / 运行中取消）+ `http_transport_test.cj` 场景 16 黑洞地址用例：`192.0.2.1`（RFC 5737 TEST-NET，设计上不可路由，SYN 被丢弃）探针实测裸 connect 8s+ 挂起（= 事故形态），`idleTimeout=1s` 时 `connect()` 在 ~2s 内抛 `BudgetTimeoutException`，证明 connect 不再是无限阻塞死区。cjllm 包 31/0 全绿。

**排查方法论（本次耗时最长的部分）**：原 TUI 进程已退出、无法抓活线程栈，纯靠日志 + 代码推理。日志窗口（`10:09:48` 起无 `run 正常结束`、`10:10:49` 起看门狗每 61s 触发且 8 次全无效）钉死"run 未返回"；代码走读发现 `connect()` 无超时 + `abort()` 只关 `this.socket` + connect 挂死时 `socket==None` 三点交汇成死区；用独立探针项目（`/tmp/cjh_fut`）离线验证 `spawn + Future.get(timeout)` 的完整语义（异常经 `get()` 重抛、超时后可二次 `get()`、`Future<Unit>`/泛型/`T=Unit` 均可用），再落地为生产原语。

### 3.13 构建配置回归：静态链接配置被连带清空，发布包变动态二进制（2026-09-02 打 v1.3.7 发布包时发现）

**现象**：打 v1.3.7 发布包时 `ldd` 发现当前 `cjpm build` 产物依赖 40+ 个仓颉/仓颉 stdx 动态库（`libcangjie-runtime.so` + 一批 `libstdx.*.so`，rpath 绝对路径），而 README 明确写着"Linux 静态单文件，默认 `--static`"、v1.3.4 及以前的发布包都是 16MB 单文件。Windows 交叉包同样中招：exe 从 v1.3.4 的 13.3MB（`objdump -p` 导入仅 7 个系统/runtime DLL）缩水成 8.3MB，导入表冒出 **12 个 `libstdx.*.dll`**——stdx 从静态链接退化成动态依赖。

**根因链（两次配置漂移叠加）**：

1. `66f1095`（"build: 默认静态链接"）把 `compile-option` 设为 `--static --static-std --static-libs`、stdx `path-option` 指向 `static/stdx`；`test.sh` 靠"备份静态配置 → 切 `cjpm.toml.dynamic.bak` 跑测试 → 恢复"工作。
2. **`f7b5945`（"fix(llm): 协议结束标记提前终止"）提交时 cjpm.toml 处于动态测试态**（`compile-option = ""` + `dynamic/stdx`）——大概率是某次切动态配置后忘记恢复就提交了。此后所有构建都产出动态链接二进制，README/`test.sh` 注释却仍在描述静态行为，文档与配置脱节。
3. **`winbuild.sh` 的 `WINDOWS_STDX` 指向 `dynamic/stdx`**：动态 stdx 目录里只有 4 个 FFI 模块的 `.dll.a` 导入库（keysFFI/x509FFI/tlsFFI/dynamicLoader-opensslFFI），其余模块链接器直接取 `.dll` 作运行时依赖 → exe 动态挂 12 个 libstdx DLL；而 `static/stdx` 里是全套 33 个真 `.a` 静态库。"Windows stdx 静态链接"的效果实际依赖这个路径选择，cjpm.toml 漂移后它静默生效。

| 坑 | 现象 | 解法 |
|---|---|---|
| **临时切配置后忘恢复就提交** | `test.sh` 的 `trap restore EXIT` 只覆盖脚本自身；手动切动态配置（排障/实验）后忘恢复，动态态被 `git commit` 带走 | 发版/打包前先 `ldd`/`objdump` 核对产物依赖，与"静态单文件"预期比对；提交前 `git diff cjpm.toml` 扫一眼 |
| **文档与配置脱节** | README 写"默认静态"，实际 HEAD 产动态二进制，连续 3 个版本（v1.3.5~v1.3.7 首次构建）都是动态包而无人发现 | 发布包是"配置正确性"的天然验收点：**ldd 只应见系统 libc 系**；Windows 用 `objdump -p \| grep "DLL Name"` 核对导入表 |
| **动态 stdx 目录无全套导入库** | 指向 `dynamic/stdx` 时 exe 动态依赖 12 个 `libstdx.*.dll`（体积反而变小 8.3MB，部署却要拖一堆 DLL） | `winbuild.sh` 的 `WINDOWS_STDX` 指 `static/stdx`（33 个真 `.a`），脚本内注释"勿改回 dynamic" |

**修复**（v1.3.7 发布提交）：`cjpm.toml` 恢复 `--static --static-std --static-libs` + `static/stdx` 路径（以 `66f1095` 为基准）；`winbuild.sh` `WINDOWS_STDX` 改指 `static/stdx`。验证：Linux 产物 16MB、`ldd` 仅 6 个系统库、`env -i`（无 LD_LIBRARY_PATH）直接运行；Windows exe 13.3MB、`objdump` 导入回落为 v1.3.4 同款 7 个 DLL（CRYPT32/KERNEL32/msvcrt/SHELL32/WS2_32 + 2 个 runtime DLL）。

**教训**：`test.sh` 的"切配置-恢复"机制只保护脚本生命周期内的构建，**保护不了"人手动切配置后忘记恢复"的窗口期**。凡有"临时改配置"的工作流，配置漂移风险真实存在——验收必须落到**产物本身**（ldd/objdump 核对依赖表），不能只信配置文件的当前内容。

## 七、可复用模块抽离（生态贡献）

遵循"可复用模块独立成库"原则，已抽离：

### cjterm — 仓颉终端 UI 库（`libs/cjterm/`）

**零外部依赖的纯仓颉终端库**，任何需要终端界面的仓颉项目可复用：

| 模块 | 能力 |
|---|---|
| `Ansi` | ANSI 转义（颜色 256 色/光标/清屏/隐藏光标） |
| `Screen` | 差分渲染（期望状态网格 + 仅输出差异行） |
| `Term` | **纯 libc FFI**：termios 原始模式、非阻塞按键、ioctl 终端尺寸 |

**关键设计**：termios 用纯 FFI 直调 libc（tcgetattr/tcsetattr/read/ioctl/select），
**无外部 .so 依赖**——`@C struct` 布局手写（Linux x86_64 termios 60 字节），
标志位用 UInt32 位运算（仓颉按位取反是 `!` 一元运算符，非 `~`）。

**使用**：主项目 `[dependencies] cjterm = { path = "./libs/cjterm" }`。

### 抽离原则

- 零/低依赖优先（cjterm 零依赖 → 最先抽）
- 业务耦合的留在主项目（config 依赖 llm、tools/agent 是 agent 专属）
- 候选后续抽离：`cjh.llm`（LLM 客户端，依赖 model）、`cjh.model`（消息模型）
