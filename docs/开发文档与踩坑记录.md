    │

## 三、踩坑记录（重要）

### 3.1 子包链接：cjpm 的坑

**现象**：`src/llm/`、`src/agent/` 等子包编译成 staticlib 成功，但主包 exe 链接报
`undefined reference to _CGP7cjh.llmiiHv`。

**根因**：cjpm 编译子包为 .a 后，主包 exe 的自动链接**不会带上子包库**；
手写 `link-option = "-Ltarget/release/cjh -lcjh.agent ..."` 又会**覆盖** stdx 自动链接，导致 stdx 符号缺失。

**解法**：link-option 留空，依赖表也留空——cjpm 在 clean 构建下会自动处理子包链接。
（首次失败的 link-option 残留会干扰后续构建，务必 `cjpm clean` 再试。）

### 3.2 包间循环依赖

agent → tools → llm → agent 成环。解法：把无依赖的模型类型（ChatMessage/ToolCall/ModelResponse）
抽到独立包 `cjh.model`，依赖方向变为单向。

### 3.3 仓颉语法要点（本次新踩）

| 主题 | 结论 |
|---|---|
| 子包名 | 目录 `src/llm/` 内包名须为 `cjh.llm`（点分包名） |
| import 顺序 | **所有 import 必须在声明之前**；FFI/函数定义不能插在 import 中间 |
| Byte 字面量 | `10u8`（Byte 是 UInt8 别名，无 toByte()） |
| String 下标 | `s[i]` 返回 **Byte**（UTF-8 字节），非 Rune；切片 `s[0..n]` |
| lambda 多参 | `{ a, b => ... }`（无括号）；单参 `{ x => }`；空 `{ => }` |
| lambda 捕获可变变量 | 禁止（"needs to be called directly"）；用类静态成员中转 |
| Option 默认值 | `opt ?? default`（无 getOrElse） |
| CPointer→CString | `CString(ptr)` 构造（unsafe 上下文） |
| 数组构造 | 无 `[a,b]` 字面量；用 `Array(n, repeat: v)` 或 ArrayList |
| 环境变量 | FFI `getenv`（std.env 无封装）；std.env 只有 ConsoleReader/Writer |
| 标准输入 | `getStdIn().read(buf)` 流式读（ConsoleReader 无公开构造） |
| 集合 map | ArrayList 无 map；用 for 循环 |
| JsonValue 形态判断 | 必须 `match (v.kind())`，不能 `==`/`!=` |

### 3.4 TUI 层新增踩坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **字节截断破坏 UTF-8** | `line[0..cols]` 按字节截断，切到中文中间 → 后续 `Rune(单字节)` 抛 `Invalid utf8` | 不预截断；迭代码点（`for (cp in text)`）自然截断到列宽 |
| **Rune(单字节)** | `Rune(line[i])` 对 UTF-8 中间字节（>127）抛异常 | String 迭代得到 UInt32 码点，`Rune(cp)` 还原字符 |
| **if-let 需 Some 模式** | `if (let x <- opt)` 绑定仍是 Option | 必须 `if (let Some(x) <- opt)` |
| **`??` 优先级** | `a ?? "" == "1"` 被解析错 | 加括号 `(a ?? "") == "1"` |
| **link-option 覆盖子包链接** | 手写 link-option 后子包 .a 不自动链 | link-option 留空（除 C 库），子包由 cjpm 自动处理；改 link-option 后 `cjpm clean` |
| **新增子包漏链** | 新加 tui 子包后 undefined reference | `cjpm clean` 重建（增量缓存不识别新子包） |

### 3.5 配置/会话层新增踩坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **foreign 函数改名后无定义** | `cjGetenv` undefined reference | foreign 函数名须与 C 符号一致（用 `getenv` 匹配 libc），不能随意改名 |
| **类内 static foreign** | `@C public foreign static func` 语法错 | foreign 顶层声明 + 类内静态方法包装 |
| **复合 if-let** | `if (let a <- x, let b <- y)` / 分号都错 | 用 `&&` 连接：`if (let a <- x && let b <- y)` |
| **Directory.list 不存在** | 遍历目录报错 | 用 `Directory.walk(path, cb)` 回调式 |
| **DateTime 无 toUnixTimestamp** | 时间戳方法名错 | `toUnixTimeStamp(): Duration`（注意大小写）；会话 ID 用 Duration 转秒.毫秒 |
| **if-else 分支类型不一致** | else 分支表达式返回值被丢弃 | `let _ = expr` 显式丢弃 |
| **lambda 捕获可变局部变量** | "needs to be called directly" | 用类静态成员（SessionState.current / CliSession.id）中转 |

子包源码改动后：`cjpm clean && cjpm build`（增量缓存可能误报循环依赖/漏链）。

### 3.7 LLM 截断死循环（本次新踩，OMP 式三层防线）

**现象**：`deepseek-v4-flash` 单轮 max_tokens 装不下完整 H5 游戏（~5000+ 字符），一次性 `write_file` 被截断 → 文件不完整（缺 `</script></body></html>`）→ LLM 收到截断警告后**重新 `write_file`** → 再次截断 → 死循环。

**根因分析**（对照 OMP/Aider/Cursor）：
1. **Payload 膨胀 vs max_tokens**：write_file 让模型输出几千行代码，极其消耗 Output Tokens，极易触发截断上限
2. **截断检测不可靠**：DeepSeek 返回 `finish_reason=tool_calls` 而非 `length`，`finish_reason=="length"` 检测不触发
3. **重写倾向**：模型收到"文件不完整"警告后，注意力机制趋向于重新发起 write_file，而非增量续写
4. **Cache 前缀破坏**：每轮追加 tool 结果破坏了前缀，导致 DeepSeek prompt cache 命中率低

**解法**（三层防线，对齐 OMP）：

| 层 | OMP 做法 | cjh 实现 |
|---|---|---|
| 工具契约层 | 拆分 write（骨架）+ edit（增量） | `AppendFileTool` 新增 + `WriteTool` content 软上限（150 行/4000 字符）超限警告但不阻断 |
| 截断打断层 | JSON 损坏时落盘已有片段 + 绝对指令打断 | `ModelResponse.truncatedPaths` + `StreamAccumulator` 记录被截断 write_file/edit_file 的 path → agent loop 注入 `[System Notice]` 绝对指令（已落盘、禁止重写、强制 append_file 续写到闭合），斩断"重写 → 截断 → 重写"死循环 |
| 前缀冻结层 | 静态 System Prompt + Tools 定义 + 尾部追加 History | messages 数组审计确认 append-only；`truncateToolResult` Tool Output 压缩 Hook（>6000 字符 Head/Tail 裁剪） |

**关键踩坑点**：

| 坑 | 现象 | 解法 |
|---|---|---|
| **finish_reason 不可靠** | DeepSeek 返回 `tool_calls` 而非 `length`，截断检测不触发 | 改用 `tryParseJson` 失败即标记 `truncated=true`（因 DeepSeek 不报告 `finish_reason=length`） |
| **repairTruncatedJson 方案选择** | JSON 被截断时，方案1（截断到上一个完整字段）丢弃 content，方案2（补 `"}`）保留 content | 方案2优先于方案1，保留被截断 content 让前半段落盘 |
| **enum 模式参数数量** | `PatchOp.LineAnchor` 加 String 参数后，`case LineAnchor(_)` 编译报 "enum pattern's parameters size is wrong" | 所有 `LineAnchor(_)` 改为 `LineAnchor(_, _)`，漏改一处即编译失败 |
| **提示词语言** | 中文 systemPrompt + 工具 description 浪费 token | 全改英文（bash/read_file/write_file/append_file/grep/list_dir/hashline_edit + systemPrompt + [System Notice]），保留 "answer in Chinese" 让模型回复中文 |

### 3.9 工具层潜伏 bug（第十二轮单测实测揪出，全部已修）

> 新增 `src/tests/`（62 用例）与 `src/core_funcs_test.cj`（根包 19 用例）后，实测暴露 6 个从未被发现的 bug。教训：**零测试覆盖 = 带病运行**（edit/hashline 两个核心工具此前从未真正工作过）。

| Bug | 现象 | 根因 | 修复 |
|---|---|---|---|
| **edit 替换毁文件** | 任何 `edit` 替换把文件变成数字串（`let x = 1` → `101010810111632...`） | `replaceString` 逐字节 `result.append(text[i])`，`StringBuilder.append(Byte)` 把字节当**十进制整数**追加 | 改整段 String 切片（`text[lastCopy..i]`）追加，UTF-8 安全 |
| **hashline 必抛异常** | `HashlineEditTool` 每次调用 `OverflowException: mul` | FNV-1a 用 UInt32 直接乘法，`hash * 16777619` 溢出，仓颉默认溢出检查抛异常 | 全程 UInt64 运算 + 每步 `& 0xFFFFFFFF` 截断 |
| **grep/glob 目录搜索不递归** | 目录搜索只覆盖第一层；遇 `.git` 直接停止整个搜索 | 误以为 `Directory.walk` 递归——实测**非递归**（只遍历直接子项），且回调返回 `false` **终止整个遍历** | 显式递归子目录；忽略目录返回 `true` 只跳过 |
| **append_file 静默创建** | append 到不存在文件成功（OpenMode.Append 自动建文件），与 spec "Fails if not exist" 不符 | 仓颉 `OpenMode.Append` 对不存在文件会创建 | execute 前显式 `exists(path)` 校验 |
| **会话 ID 毫秒碰撞** | `save` 与 `saveFork` 同毫秒调用生成相同 ID，后者覆盖前者（parent 链错乱） | `newSessionId` 只有 `秒.毫秒` 精度 | 追加进程内静态计数器 `秒.毫秒.计数器` |
| **tool 消息丢 name 字段** | 会话保存/恢复后 tool 消息工具名丢失 | `ChatMessage.toOpenAiJson()` 对 tool 角色只写 `tool_call_id`/`content` | 非空 name 补写 |
| **glob/list_dir 静态状态竞态** | V2d 并发执行 + 子代理共享 registry 时并发调用互相踩踏 | `GlobState`/`ListDirState` 用静态可变字段（为绕 lambda 捕获限制） | 改每调用实例状态（`let st = GlobCallState()`，对齐 GrepTool 的 GrepWalkState 模式） |
| **hashline 多锚点行号偏移缺失** | 前序锚点 Insert/Delete 后，后续 `@@N` 定位错行（内容校验必然误拒） | apply 无偏移跟踪（注释声称有，实际没有） | 加 `lineOffset` 累计校正 |
| **同锚点多行插入顺序颠倒** | `@@1\n+x\n+y` 得 `[y,x,...]` | 块内 Insert 用固定 `lineIdx`，未递增插入位置 | 恢复 `insertAfterLine` 递增 |
| **capability 资源检查缺口** | `append_file/edit_file/hashline_edit/glob` 完全跳过 fs 白名单检查；append/edit 写文件按读检查 | `executeGuarded` 的 path 检查列表只有 4 个工具；`isWrite` 只认 `write_file` | 补全 8 个带 path 工具 + 写类工具 isWrite=true |

**仓颉新踩坑**（测试编写时）：

| 坑 | 现象 | 解法 |
|---|---|---|
| **块注释嵌套** | 注释里写 `**/*`（glob 字面量）触发 `/*` 嵌套注释解析，报 `illegal character` | 注释里不写 `星号斜杠` 序列 |
| **无默认参数** | `func f(a: Bool = false)` 编译错 | 重载或调用处显式传参 |
| **无命名参数（普通参数）** | `f(x: 1)` 报 "target is not a named parameter" | 只有 `p!:` 声明支持命名；普通参数按位置传 |
| **零参 lambda** | `{ () => ... }` 编译错 | 写 `{ => ... }` |

### 3.10 Windows 交叉构建（跨平台终端层，第十四轮）

**目标**：Linux 上 `cjpm build --target x86_64-pc-windows-gnu` 直接产出 Windows exe（已验证 `dist/cjh-v1.3.2-windows-x64.exe`，PE32+ 7.97MB）。**不需要 Windows 版 SDK**——cangjie SDK 自带 `lib/windows_x86_64_cjnative` 平台 std 库，交叉编译自动切换。

| 坑 | 现象 | 解法 |
|---|---|---|
| **根 link-option 是 Linux 专属** | `lld: error: unknown argument: --disable-new-dtags / -rpath`（ld.lld -m i386pep 不认） | `[package] link-option` 清空；Linux 运行时库位置改由 `cj-env.sh` 的 `LD_LIBRARY_PATH` 提供（发布静态链接不依赖） |
| **target 段无法覆盖 link-option** | `[target.x86_64-pc-windows-gnu] link-option = ""` 不生效（cjpm 只读 [package] 级） | 根清空是唯一路径；stdx 路径用 `[target.X.bin-dependencies].path-option`（该段有效） |
| **stdx 按平台独立发布** | `can not find package 'stdx.net.http'`（linux stdx 无 windows 平台目录） | gitcode.com/Cangjie/cangjie_stdx/releases 下载 `cangjie-stdx-windows-x64-<ver>.zip`（asset 名规律，下载需登录 401）解压到 `~/.cangjie/stdx/` |
| **`os` 是仓颉内置条件** | 需 `@When[os == "Windows"]` 而非自定义 cfg | 编译期自动注入目标平台（值：`Windows Linux macOS HarmonyOS`，大小写敏感），无需 `--cfg` |
| **`@When` 只能用于声明** | `@When[os == "Windows"] { return WB() }` 报 "expected declaration" | 两个同名函数各带 `@When` 互斥（编译期只留一个）；类声明/foreign 函数同样支持 |
| **`&var` 不能取地址** | `CPointer(&mode)` 语法错 | `LibC.malloc` 缓冲 + 手写小端读写（同 termios FFI 模式）；FFI 指针参数统一 `CPointer<UInt8>`（`Void` 未导入） |
| **Windows 目标名** | `x86_64-pc-windows-msvc` 报 "environment msvc not found" | 用 `x86_64-pc-windows-gnu`（SDK 自带 mingw/lld 工具链，无需外部安装） |
| **`os` 条件编译验证** | 单向编译无法证明另一平台后端被排除 | 交叉编译产物 `strings` 查符号：无 `tcgetattr/termios`（POSIX 后端排除）、有 `GetConsoleMode/ReadConsoleInputW`（Windows 后端编入） |

**部署**：Windows 产物已**静态化 stdx**（link-option 加 `-lcrypt32 -lws2_32` + path-option 指 stdx `static/`）——依赖从 42 DLL 降到 **exe + libcangjie-runtime.dll + libboundscheck.dll（3 文件）**，`dist/cjh-<ver>-windows-x64.zip`（4.8MB）整包分发。**单文件 exe 不可达**：仓颉 SDK 1.0.5 未提供 Windows 静态 runtime（`libcangjie-runtime.a` 仅 Linux 有，Windows 只有 DLL + import lib），`cjc --static` 仅对 Linux 生效；runtime DLL 又依赖 libboundscheck.dll（传递依赖无法消减）——等待官方发布 Windows 静态 runtime。构建用 `./scripts/winbuild.sh`（自动临时替换 root link-option，结束恢复；root link-option 的 `-rpath` 是 Linux 专属，lld/mingw 不认）。**Linux 默认静态单文件**：cjpm.toml 默认 `--static` + stdx `static/` 路径，`cjpm build` 直接产出零依赖单文件（仅系统 libc）；**静态下 `cjpm test` 会 double free 崩溃（SIGSEGV，仓颉运行时/测试框架组合 bug，发布二进制正常）**——测试用 `./scripts/test.sh` 自动切动态配置跑完恢复静态。

### 3.8 Hashline 编辑协议（对齐 OMP Hashline Edits）

**设计动机**：OMP 的编辑协议不是全量 Write，而是 Hashline Edits——带 Hash 锚点的精准局部编辑。

**核心机制**：
- **Hash 锚点**（`@@{hash}`）：行内容 FNV-1a 32-bit，取低 16 位转 4 hex，遍历所有行算 hash 匹配定位
- **防漂移**：文件变了导致哈希对不上，patch 被拒绝（`LocateError("无匹配行")`）
- **碰撞处理**：多行匹配同一 hash → `LocateError("哈希碰撞")`，要求模型提供更多上下文

**cjh 与 OMP 的两点差异**：

1. **行号锚点优先于哈希锚点**：
   - cjh 同时支持 `@@N`（行号锚点，**推荐**）和 `@@{hash}`（哈希锚点，**向后兼容**）
   - 原因：模型无法预先计算哈希值，实测 LLM 反复尝试各种 hash 格式都失败
   - 行号锚点对 LLM 更友好——模型用 read_file 看到的行号直接引用

2. **行号锚点加可选内容校验**（本次新增）：
   - 格式：`@@N content` — 定位第 N 行**并校验该行内容必须等于 content**
   - 不匹配 → `ApplyError("行号 N 内容不匹配：期望「content」，实际「...」")`，patch 被拒绝
   - 与 `-old` 双保险互补：`@@N content` 锚点定位时就校验（防漂移），`-old` 删除/替换时校验（防打错地方）

**效率收益**（OMP 实测基准）：
- 编辑成功率 6.7% → 68.3%（10× 提升）
- 输出 Token 减少 61%（重试循环消失）

**实现文件**：`src/tools/hashline.cj`（489 行）
- `HashlineEditTool`：工具入口，读文件 → 解析 patch → 应用 → 写回
- `HashlineEditParser`：解析 patch 文本为 `ArrayList<PatchOp>`
- `HashlineEditApplier`：应用 patch 到原文件行列表
- `HashlineHash`：FNV-1a 32-bit 哈希计算 + 行定位
- `PatchOp` 枚举：`LineAnchor(Int64, String)` / `HashAnchor(String)` / `Insert` / `Delete` / `Replace`

### 3.11 仓颉 String 字节切片校验 UTF-8 边界 + spawn 未捕获异常静默杀线程（2026-09-01 僵尸忙态事故，v1.3.5）

**现象**：TUI 回合早已结束（日志 `Agent.run 正常结束`），但状态行永久冻结在 `Streaming… (127s · 第4轮)`，看门狗每 60s 重复无效中断，之后所有 Enter 全走"打断"分支、排队消息永不发送。

**根因链（两层叠加，缺一不可）**：

1. **仓颉 `String[0..N]` 按字节切片且校验 UTF-8 边界**：切点落在多字节字符中间 → 抛 `IllegalArgumentException: Invalid utf8 byte sequence`。实测（1.0.5）：72 个 CJK 字符 `size=216`（size 单位是字节），`[0..18]/[0..45]/[0..60]`（3 的倍数=字符边界）正常，`[0..20]` 抛异常。中文密集内容上**任意固定字节阈值都可能落字符中间**。
2. **spawn 任务内未捕获异常只杀任务线程、进程存活**（实测）：异常不打断主循环、无崩溃栈——收尾逻辑静默死掉，比崩溃更隐蔽。

**触发路径**：compaction 把历史压成 673 字节中文 `[历史摘要]` 作为首条 user 消息 → `summarizeForMemory()` 内 `task[0..60]`（第 60 字节=0x8B，CJK 中间）抛异常 → 该调用在 TUI spawn 收尾块（entries.cj）**try/catch 之外**求值（`saveProjectMemory(dir, agent.summarizeForMemory())`，实参先求值）→ 收尾线程死亡 → `setAgentRunning(false)` 永不执行 → `agentRunning=true` 僵尸态。**短消息（≤阈值）不切片所以不复现**——上一轮 user 仅 33 字节安然无恙，本轮 673 字节必炸，属于"偶发"形态。

| 坑 | 现象 | 解法 |
|---|---|---|
| **`String[0..N]` 校验边界** | 中文内容切片抛 `Invalid utf8 byte sequence` | 统一用 `cjutil.truncateUtf8(text, maxBytes)`（回退合法字符边界，不抛）；`tailUtf8` 取尾部。新增切片前先问：内容会是中文吗？ |
| **`spawn {}` 未捕获异常** | 只杀任务线程、进程存活、无栈——最隐蔽的静默死 | spawn 任务里**收尾关键路径**（状态复位、队列出队）必须 try/catch 兜底，或包进函数后调用点捕获；禁止让 `spawn` 闭包裸奔 |
| **`String(Rune(byte))` 摩尔化** | `Rune(0xE4)` 按 Latin-1 编成 2 字节，逐字节 append 重建的串不是原串、长度翻倍 | 重建字符串必须整段 String 切片，禁止逐字节 append（与 `StringBuilder.append(Byte)` 按十进制输出同源） |
| **实参在 try 外求值** | `f(x, g())` 中 `g()` 抛异常时 try 管不到 | 关键实参先 `let` 接住，再接着进 try |

**修复**（v1.3.5）：`summarizeForMemory()` 两处裸切片改 `truncateUtf8`；entries.cj spawn 收尾块记忆保存独立 try/catch（`summarizeForMemory()` 实参先求值再接住），保证 `setAgentRunning(false)` 必达。回归测试 `src/agent/summarize_memory_test.cj` 用事故真实数据（byte60=0x8B）钉死：前提自证（裸切片必抛）+ 修复后全绿。

**排查方法论（本次耗时最长的部分）**：日志铁证 `run 正常结束` 已打印 → 死点在 run 返回之后；`.4` 会话文件 mtime vs `bin.md` 记忆文件 mtime 二分定位到 `store.save` 之后、`setAgentRunning(false)` 之前；spawn 静默死无法 attach 活进程取栈（进程早已"健康"存活）→ 只能靠文件 mtime + 日志窗口二分 + 最小复现实验证伪各假设。

### 3.12 裸 socket connect/write 无超时 → 首个 LLM 请求卡死、abort() 空转（2026-09-02 Thinking 442s 事故，v1.3.6）

**现象**：TUI 首个 LLM 请求发出后**状态行永久冻结**在 `Streaming… (127s · 第4轮)`，空闲看门狗自 10:10:49 起每 61s 触发，8 次 interrupt 全部无效；之后所有 Enter 走"打断"分支、排队消息永不发送。与 §3.11 的关键区别：日志里**没有** `Agent.run 正常结束`——run 线程本身还卡在第一个 LLM 请求里没返回。

**根因链（三层叠加，缺一不可）**：

1. **仓颉裸 `TcpSocket.connect` 没有超时参数**（1.0.5 实测）：TCP + TLS 路径（含 DNS 解析）在 connect 阶段挂死时，`readTimeout` 完全不起作用——它只在数据可读性检查上生效，覆盖不到 connect 本身；`write()` 大 payload 经代理也可能挂死，同样无超时。
2. **`HttpStreamClient.abort()` 打不断 connect 阶段**：`abort()` 只做 `close(this.socket)`，而 `this.socket` 在 `connect()` 成功返回后才赋值（`Some(tls)`/`Some(sock)`）——connect 挂死期间 `socket == None`，`case None => ()` 空转。中断信号传得到、但关不到一个还没建好的连接。
3. **请求阶段整体无"可中断的超时"**：connect / 写请求 / 读响应头 三个阶段都在主请求线程上直接同步调用，任何一个挂死 = 整个 run 永久挂起，看门狗的 interrupt 既无超时兜底、abort 又空转 → 双重失效。

**触发路径**：网络瞬态异常（当时 DNS 40ms→挂死；当前已恢复）+ 首个请求复用连接失败走新建路径 → `connect()` 在 DNS/TCP/TLS 某一步挂死 → `socket` 永远 `None` → 看门狗 `interrupt()` → `cancelChecker=true` 但 connect 不响应、`abort()` close(None) 空转 → run 永不返回 → `agentRunning=true` 僵尸态。

| 坑 | 现象 | 解法 |
|---|---|---|
| **裸 socket `connect` 无超时** | DNS/TCP/TLS 挂死时 `readTimeout` 不起作用，无限阻塞 | 任何可能无限阻塞的阶段用 `cjutil.runWithBudget` 包一层（spawn + `Future.get(pollMs)` 轮询 + 预算判定），把"无限阻塞"变成"有界可中断" |
| **`abort()` 关不到未建好的连接** | connect 阶段 `socket==None`，`close(None)` 空转，中断失效 | 中断不再依赖"关 socket"，改由 `runWithBudget` 的 `cancelChecker` 在预算轮询中主动判定并抛 `BudgetCancelledException`，≤pollMs 内响应 |
| **写请求无超时** | 大 payload 经代理 `write()` 挂死，无读超时窗口 | `tr.request(...)` 同样套 `runWithBudget`（30s 预算） |
| **仓颉：捕获可变局部变量的 lambda 必须直接调用、不能传参** | `runWithBudget(..., { => tr.request(path, hdrs, body) })` 报 `lambda capturing mutable variables needs to be called directly`（`hdrs`/`body` 是 `var`） | 传参前用 `let` 接住不可变快照（`let reqHdrs = hdrs; let reqBody = body.toJsonString()`），lambda 只捕获 let 局部量 |
| **spawn 任务内异常额外打 stderr** | 未捕获异常会向 stderr 打印报告，污染 TUI 输入框 | `runWithBudget` 内部用 `BudgetOutcome` 载体收住异常，task 闭包不裸抛（与 §3.11 spawn 静默死同源治理） |

**修复（v1.3.6，初版）**：新增 `cjutil.runWithBudget<T>(label, budgetMs, pollMs, isCancelled, task)` 预算竞速原语（`libs/cjutil/src/concurrency.cj`）——spawn 子任务执行 task，主线程每 pollMs 轮询结果并查 `isCancelled`，超预算抛 `BudgetTimeoutException`、被取消抛 `BudgetCancelledException`、task 异常原样重抛。首版把预算包在 **openai.cj 的调用点**（connect×2 + request×2）。

**修复（v1.3.7，下沉通用化）**：首版只覆盖了 OpenAI 兼容协议——anthropic.cj / ollama.cj 的同构调用点（`transport.connect()` + `transport.request()`）同样裸奔，且 openai 的 `warmup()` 预热路径也漏了。把预算**下沉进 `HttpStreamClient` 内部**（一处管所有现有+未来协议）：
- `connect()` 整体包 `runWithBudget`（预算 = `idleTimeout`，中断 = 本对象 `cancelChecker`——provider 建连前就注入，零额外传参），**预算内重试一次**（首连超预算可能是 DNS 瞬态抖动；被中断不重试），重试超预算才抛 `BudgetTimeoutException`
- `request()` 的 `write()` 同样包 `runWithBudget`（预算 = 新增 `writeTimeout` 字段，默认 30s）
- openai.cj 四处调用点全部还原为直调 `tr.connect()` / `tr.request(...)`（删除冗余包装 + `let` 快照 hack），`warmup()` 缩建连预算到 15s
- **anthropic / ollama / 未来新协议：零改动自动获得同款保护**——新协议只要复用 `HttpStreamClient` 就天然有界可中断，不再需要每个调用点记得包预算

**回归测试**：`libs/cjutil/src/concurrency_test.cj` 5 用例（T=Int64 / T=Unit / 异常重抛保类型 / 超预算耗时≈预算 / 运行中取消）+ `http_transport_test.cj` 场景 16 黑洞地址用例：`192.0.2.1`（RFC 5737 TEST-NET，设计上不可路由，SYN 被丢弃）探针实测裸 connect 8s+ 挂起（= 事故形态），`idleTimeout=1s` 时 `connect()` 在 ~2s 内抛 `BudgetTimeoutException`，证明 connect 不再是无限阻塞死区。cjllm 包 31/0 全绿。

**排查方法论（本次耗时最长的部分）**：原 TUI 进程已退出、无法抓活线程栈，纯靠日志 + 代码推理。日志窗口（`10:09:48` 起无 `run 正常结束`、`10:10:49` 起看门狗每 61s 触发且 8 次全无效）钉死"run 未返回"；代码走读发现 `connect()` 无超时 + `abort()` 只关 `this.socket` + connect 挂死时 `socket==None` 三点交汇成死区；用独立探针项目（`/tmp/cjh_fut`）离线验证 `spawn + Future.get(timeout)` 的完整语义（异常经 `get()` 重抛、超时后可二次 `get()`、`Future<Unit>`/泛型/`T=Unit` 均可用），再落地为生产原语。

### 3.13 构建配置回归：静态链接配置被连带清空，发布包变动态二进制（2026-09-02 打 v1.3.7 发布包时发现）

**现象**：打 v1.3.7 发布包时 `ldd` 发现当前 `cjpm build` 产物依赖 40+ 个仓颉/仓颉 stdx 动态库（`libcangjie-runtime.so` + 一批 `libstdx.*.so`，rpath 绝对路径），而 README 明确写着"Linux 静态单文件，默认 `--static`"、v1.3.4 及以前的发布包都是 16MB 单文件。Windows 交叉包同样中招：exe 从 v1.3.4 的 13.3MB（`objdump -p` 导入仅 7 个系统/runtime DLL）缩水成 8.3MB，导入表冒出 **12 个 `libstdx.*.dll`**——stdx 从静态链接退化成动态依赖。

**根因链（两次配置漂移叠加）**：

1. `66f1095`（"build: 默认静态链接"）把 `compile-option` 设为 `--static --static-std --static-libs`、stdx `path-option` 指向 `static/stdx`；`test.sh` 靠"备份静态配置 → 切 `cjpm.toml.dynamic.bak` 跑测试 → 恢复"工作。
2. **`f7b5945`（"fix(llm): 协议结束标记提前终止"）提交时 cjpm.toml 处于动态测试态**（`compile-option = ""` + `dynamic/stdx`）——大概率是某次切动态配置后忘记恢复就提交了。此后所有构建都产出动态链接二进制，README/`test.sh` 注释却仍在描述静态行为，文档与配置脱节。
3. **`winbuild.sh` 的 `WINDOWS_STDX` 指向 `dynamic/stdx`**：动态 stdx 目录里只有 4 个 FFI 模块的 `.dll.a` 导入库（keysFFI/x509FFI/tlsFFI/dynamicLoader-opensslFFI），其余模块链接器直接取 `.dll` 作运行时依赖 → exe 动态挂 12 个 libstdx DLL；而 `static/stdx` 里是全套 33 个真 `.a` 静态库。"Windows stdx 静态链接"的效果实际依赖这个路径选择，cjpm.toml 漂移后它静默生效。

| 坑 | 现象 | 解法 |
|---|---|---|
| **临时切配置后忘恢复就提交** | `test.sh` 的 `trap restore EXIT` 只覆盖脚本自身；手动切动态配置（排障/实验）后忘恢复，动态态被 `git commit` 带走 | 发版/打包前先 `ldd`/`objdump` 核对产物依赖，与"静态单文件"预期比对；提交前 `git diff cjpm.toml` 扫一眼 |
| **文档与配置脱节** | README 写"默认静态"，实际 HEAD 产动态二进制，连续 3 个版本（v1.3.5~v1.3.7 首次构建）都是动态包而无人发现 | 发布包是"配置正确性"的天然验收点：**ldd 只应见系统 libc 系**；Windows 用 `objdump -p \| grep "DLL Name"` 核对导入表 |
| **动态 stdx 目录无全套导入库** | 指向 `dynamic/stdx` 时 exe 动态依赖 12 个 `libstdx.*.dll`（体积反而变小 8.3MB，部署却要拖一堆 DLL） | `winbuild.sh` 的 `WINDOWS_STDX` 指 `static/stdx`（33 个真 `.a`），脚本内注释"勿改回 dynamic" |

**修复**（v1.3.7 发布提交）：`cjpm.toml` 恢复 `--static --static-std --static-libs` + `static/stdx` 路径（以 `66f1095` 为基准）；`winbuild.sh` `WINDOWS_STDX` 改指 `static/stdx`。验证：Linux 产物 16MB、`ldd` 仅 6 个系统库、`env -i`（无 LD_LIBRARY_PATH）直接运行；Windows exe 13.3MB、`objdump` 导入回落为 v1.3.4 同款 7 个 DLL（CRYPT32/KERNEL32/msvcrt/SHELL32/WS2_32 + 2 个 runtime DLL）。

**教训**：`test.sh` 的"切配置-恢复"机制只保护脚本生命周期内的构建，**保护不了"人手动切配置后忘记恢复"的窗口期**。凡有"临时改配置"的工作流，配置漂移风险真实存在——验收必须落到**产物本身**（ldd/objdump 核对依赖表），不能只信配置文件的当前内容。

### 3.14 空闲看门狗误杀"前思考期"：连续多轮会话总被打断（2026-09-03 用户反馈"不能连续几轮对话"，v1.3.8）

**现象**：用户反馈 cjh 几乎没法用——连续几轮对话总被"⚠️ 模型 Ns 无响应（可能停滞），已请求中断"打断，连"生成一个 h5 射击小游戏"这种任务都跑不完，状态条还停在 `0.0K tokens`。

**排查铁证（curl 直连模型，逐帧打时间戳）**：
- 相同 prompt（"生成 h5 射击小游戏"）下，glm-5.3-flash **300s 发了 12269 帧、全部是 `reasoning_content`（思考帧）、0 帧正文**；帧间隔最大仅 **0.7s**、平均 24ms。

**根因（三个叠加，都在 cjh 客户端侧）**：

| # | 根因 | 机制 |
|---|---|---|
| 1 | **`agentLastActivity` 跨 run 不重置** | 该锚点只被 `onDelta`/`onReasoning` 更新、跨轮不清零。上一轮 run 结束后锚点停在旧帧；新一轮 run 启动后，"建连 + 响应头 + 模型前思考期"（推理模型大 prompt 可数十秒~分钟无首帧）从**陈旧锚点**累计，超 `idleTimeoutSecs` 即把正在思考的模型当停滞杀掉。日志铁证：15:26:01 上轮结束 → 15:26:56 提交新轮 → 15:27:02（新轮仅 6s，还在建连）看门狗报"idle 61s"并打断——锚点还停在上轮。 |

| 3 | **token 估算跨轮残留** | `setAgentTokenEstimate` 只增不减、`addAgentTokens` 用上轮 usage 覆盖，跨轮不清零 → 状态条残留上一轮值或显示陈旧（用户看到的 `0.0K`）。 |

**修复（v1.3.8）**：
- `setAgentRunning(true)` 与 `onThinking`（每轮 chatStream 前）都 `markAgentActivity()` 重置锚点——每次 run/每轮 LLM 调用从此刻计前思考期，不再被旧帧污染。
- `defaultIdleTimeout()` 与 TUI 看门狗默认 60s → **180s**（恢复 doc 声明的设计值；keep-alive 空帧仍由 SSE 事件级预算兜底，不会永久卡死）。
- 新增 `resetAgentTokens()`，`onThinking` 每轮清零 token 计数，本轮从零重估。
- 回归测试（`tui_app_test.cj` +3 用例）：`setAgentRunning(true)` 重置锚点 / `markAgentActivity` 刷新锚点 / `resetAgentTokens` 清残留估算。

**验证**：
- 单测 `cjpm test` 275/0 全绿（基线 272 + 新增 3）。
- **真实模型 PTY 连续 3 轮对话**（状态行窗口法：每轮等状态行出现再等其 3s 消失才发下一轮）——3 轮全部正常完成（10s/6s/7s，期间 Thinking→Streaming 持续吐帧），**看门狗/停滞中断 0 条、忙时强制插入 0 条**。修复前同样的"每轮都打断"场景现已跨轮稳定跑通。

**教训**：
1. **"模型停滞"的判断必须排除"推理模型在思考"**——reasoning 帧要算活动、前思考期（首帧前的黑盒期）要给足预算，不能拿"60s 没数据"当停滞的铁证。
2. **跨轮状态（时间锚点、token 计数）必须在 run/轮边界显式重置**，否则上轮的残留会污染下一轮的判定。
3. **排查"是不是模型/网络问题"先 curl 直连逐帧打时间戳**——一次 curl 就把"模型没停滞"钉死，避免在客户端代码里瞎猜。
4. **测试脚本要忠实模拟用户时序**：v1 脚本把"启动残留 ready"误判成"上轮完成"、连发两条 → 触发 cjh 的"忙时强制插入"（这是 cjh 的正常设计行为，不是 bug）。验证"跨轮不打断"必须用状态行窗口法真正等每轮完成。

### 3.15 工具输出中文乱码：字节流逐字节当单字节字符（2026-09-03 用户反馈"显示乱码"）

**现象**：用户看到工具输出乱码 `éè¯»äºåä¸éä»£ç...`（原文是"读懂代码 — 快速赢 — 玩法 — 工程 — 案例…"）。解码特征：**每个 UTF-8 字节被当成一个独立 Latin-1 码点**（"读"=E8 AF BB → U+00E9 U+00E8 U+00AF U+00BB 四个字符）。

**根因（两处同类 bug）**：
1. `bash_session.cj` 的 `readUntilMarker`（bash 工具会话路径）：`for i in 0..n { sb.append(String(Rune(Int32(buf[i])))) }` —— **每个 stdout 字节直接转 Rune**。中文 stdout 必然乱码；且 ASCII marker（`__CJH_END_N__`）混在字节流里被逐字节处理虽能碰巧匹配（纯 ASCII 单字节），但一旦输出含中文全错。
2. `web_search.cj` 的 `urlDecode`：`%XX` 解码后同样 `String(Rune(byte))` 逐字节追加（代码注释自己都写着"非 ASCII 字节可能显示乱码"）——搜索结果中文标题/URL 参数乱码（旧会话落盘里也有 web_search 中文乱码实例）。

**修复**：
- `readUntilMarker`：累积字节，每轮在**最后一个完整 UTF-8 字符边界**处整段 `safeFromUtf8` 解码（从末尾向前探测多字节起始字节，序列不完整则尾字节留 pending 等下个块）；marker 为纯 ASCII，其字节永远落在已解码段，搜索不受影响。EOF 时 flush 残留（容错替换）。
- `urlDecode`：连续 `%XX` 累积为字节数组，遇到非编码字符（或结尾）时整段 `safeFromUtf8` 解码追加；ASCII 段原样通过；无效 `%` 序列原样保留。
- 复用 `cjutil.safeFromUtf8`（UTF-8 安全解码通用工具，非法字节→U+FFFD），未新增重复实现。
- 回归测试：bash 中文输出（>4096 字节强制跨读取边界，**先红后绿**——旧逻辑下断言失败、新逻辑绿）+ urlDecode 中文/混合/无效序列 3 组用例。

**教训**：
1. **字节流→String 禁止逐字节 `String(Rune(byte))`**——多字节字符（中文/emoji）必坏；要么整段 `safeFromUtf8`，要么维护跨块 pending 字节在字符边界解码。仓颉 String 迭代/`[i]` 返回 Byte，"逐字节拼"是隐蔽陷阱（ASCII 测试全过、一上中文就露馅）。
2. **修复时全仓搜同类模式**（`Rune(Int64(byte))`/`Rune(Int32(buf)`）——一个文件发现、同模式另一文件（web_search）一起修，避免"修一处漏一处"。
3. **乱码排查先精确解码**：把乱码码点转回字节再看 UTF-8——"每字节一个码点"vs"整体二次编码"（cp1252/GBK）是不同 bug、不同修法，先定性再动手。

### 3.16 cjlog 异步日志 sleepMs 忙等空转 → TUI 假死无法输入但进程"活着"（2026-09-03 用户反馈"cjh 无法输入、MobaXterm 未断线"）

**现象**：远程会话中 cjh 画面冻结、无法输入，但 `ps` 显示进程存活、CPU 100%（累计 8000+s）、对应 sshd 的 `Send-Q=0`（SSH 链路没堵，MobaXterm 不报断线）——"进程活着却像死了"。

**根因**：`libs/cjlog/src/cjlog.cj` 异步日志 sink 的空闲节流 `sleepMs` 写成了**纯整数忙等**：

```
internal func sleepMs(ms: Int64): Unit {
    var i: Int64 = 0
    while (i < ms * 1000) {   // ← 只自增整数，不消耗任何时间！
        i += 1000
    }
}
```

`sinkLoop` 设计是"队列空 → sleepMs(50) 降低轮询频率"，但空转 sleep 不等待，sink 协程实际以满速自旋。更致命的是它跑在**仓颉主 worker 线程**上（gdb 采样：8 次采样 6 次落在 `LogSink.sinkLoop → MArray::NewArray`），把唯一的用户态 worker 占满，饿死了 TUI 的 `run()` 主循环（5ms 轮询 readKey/render）——所以输入进不来、画面不刷新、但进程和 SSH 连接都"活着"。

**排查路径（可复用）**：
1. `ps -ef` + `ps -o etime,time,%cpu -p PID`：进程存活但 CPU 100%、累计时间巨大 → 自旋而非阻塞
2. `ss -tnp`：对应 sshd `Send-Q=0` → 排除远端/SSH 链路堵塞
3. `strace -p PID -f -c`：`futex + epoll_wait(timeout=0)` 高频 → 忙轮询特征
4. `gdb -p PID -batch -ex "bt"` 多次采样看热点帧：反复落在 `cjlog.LogSink.sinkLoop` → 锁定
5. 源码核对：`sleepMs` 是整数空循环 → 定性

**修复**：改真实 sleep（`sleep(Duration.millisecond * ms)`，仓内统一 `std.time` 用法）。

**经验**：
1. **节流/退避绝不用"计数空循环"假装 sleep**——它不耗时，等于没有；想要节流就用 runtime 的 `sleep`/`select`。
2. **"进程活着 + CPU 100% + 界面无响应"≠ 阻塞**：阻塞是 `State=S/D`、CPU 低；先量 CPU 和累计时间区分自旋与阻塞，再 gdb 采样热点。
3. **远程 TUI "卡死"先查本机**：`sshd Send-Q=0` 时问题 100% 在被控端进程，不在 SSH 链路。
4. 后台协程若跑在主 worker 上，其忙等会**饿死 UI 主循环**——协程里的空转比业务线程的空转危害大得多。

### 3.17 长会话 TUI 主协程停摆 + 泄漏 bash/僵尸：裸 `Mutex.lock` 异常泄漏 + 退出不清理（2026-09-03 51 轮 43 分钟会话后停摆，v1.3.11）

**现象**：一次 51 轮、43 分钟的重 bash 会话结束后，`Agent.run` 正常收尾（13:27:22 日志），但 TUI 主循环随之停摆——按键无响应、画面冻结；进程存活但**终端停留 raw**（`restoreTerminal` 未执行）；现场含 **4 个未回收僵尸子进程** + **1 个泄漏约 2 小时的会话 bash**，`stderr→/dev/null`。

**关键定性（gdb 全线程栈）**：7 个线程全 idle/park——
- 主线程 `CJ_CJThreadMpark ← CJ_ProcessorSchedule ← CJ_ProcessorCJThreadGet ← CJ_ProcessorStopWithLastCheck ← CJ_ThreadStop ← CJ_ThreadSleep`，**`abstime=0x0`（无限等待、无待管定时器）**；
- 两个 schd-worker 在 `do_futex_wait(abstime=0x0)`，schmon 在 `epoll_wait(timeout=10)`，gc 在 `cond_wait`。

这是仓颉运行时的**"无可运行协程" stop 路径**（`CJ_ProcessorStopWithLastCheck` = 调度器发现无就绪协程、进入停止检查并无限休眠），**不是** OS 级锁死锁（无两线程互持）。即：主任务 + agent 任务都 park 在一个**永不释放的受管原语**上。

**根因（两条叠加）**：
1. **主循环停摆 = 裸 `Mutex.lock()` 在持锁临界区抛异常导致锁永久泄漏**。`TuiApp` 多处 `lock()` 未用 `try/finally` 守护（`renderInner` 读 `outputView.content()` 判断欢迎视图、`requestApproval` 置审批态、`handleKey` 读 `pendingApproval`、`appendReasoning`/`clearReasoning`/`toggleReasoning`/`setAgentTokenEstimate` 调 `outputView`、`dequeueInput` 重建列表）。其中 `renderInner` 的 `outputLock` 泄漏最致命：**主循环每帧 `render` 与 agent 线程每帧流式回调都抢 `outputLock`**——一旦泄漏，两个任务都卡在 `outputLock.lock()` 上 → 无可运行协程 → 进入 stop 路径（`abstime=0x0`），`run()` 循环提前终止、`restoreTerminal` 永不执行（终端 raw）。长会话 + 51 轮 bash 大输出（超大 `OutputView` 缓冲）把"临界区抛异常"的概率放大到命中。
2. **泄漏 bash + 僵尸 = 退出路径从不清理子进程 + `killSession` 只 `terminate` 不 `wait`**：
   - `BashSession.killSession` 只 `terminate(force:true)`（发 SIGKILL）不 `wait()`——每个超时/关闭的会话进程都留一个**未回收僵尸**（长会话累计 4 个）。
   - `runTui` 退出路径**从不**关闭 `BashTool` 会话、断开 MCP、`Log.shutdown()`——`Log` sink 协程（`ensureInit` 后长生命周期）与 bash 会话在退出后继续残留。事故进程泄漏的"约 2 小时会话 bash"即主进程停摆后一直持着 bash stdout 管道（读协程阻塞在管道 read、bash 不收 EOF）所致。

**排查路径（可复用）**：
1. `gdb -p PID -batch -ex "thread apply all bt"`：主线程落在 `CJ_CJThreadMpark / CJ_ProcessorStopWithLastCheck` 且 `abstime=0x0` → 定性"无可运行协程"的 stop 路径，而非 OS 锁死锁或忙等。
2. 区分"stop 路径"与"忙等"：忙等是 CPU 100% + 采样落 `LogSink.sinkLoop`（§3.16）；stop 路径是 CPU 0% + 全线程 park + 主线程 `CJ_ProcessorStopWithLastCheck`。
3. 主循环 `readKey` 用非阻塞 `select`（0 超时）+ 5ms 轮询，正常路径**绝不**无限阻塞 → 主任务若 park 且 `abstime=0x0`，必是卡在 `Mutex.lock`（无超时等待）。
4. 审计 `lock()` 是否 `try/finally` 守护：grep `\.lock\(\)` 后一行非 `try {` 即嫌疑；重点看"持锁期间调可抛异常方法"的临界区（`outputView.*`、`ArrayList` 重建、`confirmDialog.show`）。

**修复（v1.3.11，6 文件）**：
1. `src/tui/app.cj`：`renderInner`/`requestApproval`/`handleKey`(2 处审批读)/`appendReasoning`/`clearReasoning`/`toggleReasoning`/`setAgentTokenEstimate`/`dequeueInput` 共 9 处裸 `lock()` 全部 `try/finally` 守锁；`run()` 主循环**每帧 try/catch**（单帧异常不得终止事件循环）+ **`finally → restoreTerminal`**（任何退出路径都恢复终端 raw）。
2. `src/tools/bash_session.cj`：`killSession` `terminate` 后 **`wait(timeout:5s)` 回收僵尸**；加 `testReapedCount()` 观测。
3. `src/tools/builtin.cj`：`BashTool.close()`（退出钩子，委托 `session.close()`）。
4. `src/entries.cj`：`runTui` `finally` 退出清理——`match(registry.getTool("bash")) { case Some(b: BashTool) => b.close() }` + `mcpManager.disconnectAll()` + `Log.shutdown()`（各独立 try/catch）。
5. `libs/cjllm/src/mock.cj`：`CJH_MOCK_BASH=1` 门控让 mock 第 2 轮发 bash（additive，默认 4 步链不变），供退出路径 PTY 回归驱动真实 `BashSession`。
6. `src/tests/bash_session_test.cj`：新增 3 例回归（`testTimeoutKillsReapsZombie`/`testCloseReapsZombie`/`testBashToolCloseReaps`），断言 `testReapedCount` 证明进程被 `wait` 回收、非僵尸。

**验证**：`./scripts/test.sh` 全绿（241 例）+ `cjpm build` + `--mock` 通过 + TUI PTY 14 场景全过 + 退出路径 PTY 回归（`CJH_MOCK_BASH=1` 驱动真实 bash 会话后 `/quit` 与 Ctrl+C：0.1s 退出、**无残留子进程**、终端 `raw=False`）。

**经验**：
1. **仓颉 `Mutex.lock()` 必须 `try/finally` 守护**——裸 `lock(); ...; unlock()` 在临界区任何异常下都泄漏锁，跨线程共享锁（TUI 的 `outputLock`/`approvalLock`/`reasoningLock`）一旦泄漏就是"主循环 + 业务线程双双停摆"。审计方法：grep `\.lock\(\)` 后一行非 `try {` 即嫌疑。
2. **主循环每帧要 try/catch 兜底 + `finally` 恢复终端**——任何单帧异常都不该终止事件循环；终端 raw 恢复放 `finally`，异常崩溃也能还原 ECHO。
3. **进程退出路径必须显式清理子进程 + 回收僵尸**：`terminate` 后必须 `wait`（否则僵尸）；长生命周期后台（`Log` sink、`BashSession`、MCP）退出时逐一关闭，别依赖"进程退出自动收"——主进程若先停摆，这些子进程/协程会一直残留。
4. **"进程活着 + CPU 0% + 全线程 park + 主线程 `CJ_ProcessorStopWithLastCheck`"= 仓颉"无可运行协程"stop 路径**，根因通常是某协程 park 在无超时的受管原语（多为异常泄漏的锁）上，区别于"忙等饿死 UI"（§3.16，CPU 100%）。

### 3.18 粘贴中文乱码：bracketed paste 逐字节 `Rune(byte)` 拼接（与 §3.15 bash 输出乱码同款，v1.3.11）

**现象**：从外部（文件/剪贴板）复制**中文**粘贴进 TUI 输入框，显示成 `å¥½` 一类 Latin-1 乱码（"好"=UTF-8 三字节 `E5 A5 BD` 被拆成 `å`+`¥`+`½` 三个独立字符）。

**根因**：`term_posix.cj` `readBracketedPaste()`（处理 `ESC[200~...ESC[201~` 包裹的 bracketed paste）**逐字节** `sb.append(Rune(Int32(b.read(0))).toString())` 拼接——把每个 UTF-8 字节当成一个独立 Latin-1 码点。这与 §3.15 的 bash 输出乱码**是同一个病**（旧 `readUntilMarker` 也是逐字节 `String(Rune(byte))`），只是粘贴这条入口当时没覆盖到。

**为什么"打字中文正常、只有粘贴乱码"**：手动输入的中文走 `readKey()` 的多字节分支（L205 起），那里**正确**地按 UTF-8 长度累积字节后用 `String.fromUtf8(bytes)` 整段解码；而 bracketed paste 是**独立**的读取路径，走了逐字节拼接。是否触发取决于终端是否发送 bracketed paste 标记（`ESC[?2004h`，MobaXterm / iTerm2 / Terminal 等主流终端粘贴时都会发）。

**修复**：
1. `readBracketedPaste` 改为**累积原始字节**到 `ArrayList<Byte>`（不再边读边解码），结束标记 `ESC[201~` 在**字节层**尾部匹配（纯 ASCII，字节匹配与字符匹配等价且不受解码影响）。
2. 返回前**整段 `safeFromUtf8` 解码**（`libs/cjutil`，非法字节容错为 U+FFFD 不抛异常）+ 原有 `stripEscapeSequences` 剥离 ESC 控制序列。
3. 依赖：`cjterm` 新增 `cjutil` 依赖（复用底层安全解码函数，符合"通用基础设施抽独立底层包供上层复用"规范；`cjllm` 已有此依赖先例）。

**验证**：`src/tests/term_paste_decode_test.cj` 8 例（中文/emoji 解码、结束标记剥离、非法字节容错、ESC 序列剥离、边界）；`scripts/tui_pty_test.py` 场景13（真实 PTY 发 `ESC[200~粘贴测试🚀ok~ESC[201~` 进输入框，断言中文正确 + 无 `å` 乱码 + 不误提交）。

**经验**：
1. **"逐字节 `Rune(byte)` 拼串"是把多字节 UTF-8 当单字节码点的经典乱码根因**——所有从字节流构造 `String` 的路径（粘贴、管道读、socket 读）都必须**累积字节到字符边界后整段 `safeFromUtf8`**，禁止 `Rune(Int32(byte))` 逐字节 append。审计方法：grep `Rune(Int32` / `Rune(b` 后跟 `.toString()` 拼接即嫌疑。
2. **同一类 bug 常在"平行的第二条读取路径"上复发**——§3.15 修了 bash 输出，但粘贴这条独立入口漏网。修一类解码 bug 时，grep 全仓所有"字节→String"路径逐一核对，别只修报告的那一条。

### 3.19 TUI 边框恒灰：主题字段"已接线、未填充" + 整行背景卡片的三条渲染规矩（2026-09-05~06，v1.3.13）

**现象**：用户反馈"输入框的灰色分割线不醒目"——状态栏 `+--` 边框、输入行 `╰─` 提示符恒为中灰，`/theme` 切换主题边框也不变色。

**根因**："已接线、未填充"——`Theme.apply()` 早已写回 `Ansi.THEME_BORDER = p.border`（接线存在），但**主题表里无一处**给 `.border` 赋值，10 个主题全部静默回退 `Palette()` 默认 `border = 244`（中灰）。接线正确 ≠ 数据正确，回退是静默的（无告警、无差异，肉眼看不出"少配了一项"）。

**修复**：每个内置主题显式设 `.border`（starfrost 73 星霜青 / classic 51 / dracula 177 紫 / nord 110 冰蓝青 / gruvbox 208 橙 / tokyo-night 33 蓝 / catppuccin 111 柔蓝 / rose-pine 30 松石青 / solarized 37 青绿 / monokai 81 青绿），`244` 降级为"未设主题"的回退。部分意图色取自主题注释声明（dracula=purple 等），太暗的（nord base01、solarized base01）调同色系亮档保证醒目。

**同批沉淀的整行背景卡片三规矩（P2b）**：
1. **卡片行中间禁 `Ansi.reset()`**——reset 会连 bg 一起清，卡片断裂；行内换色只用 `fg()`，行尾 reset 由 `padBg()` 统一补。连带坑：`Logo.badge()` 内部含 `reset()`，不能直接嵌进整行 bg 卡片，嵌入点改 `fg()` 重设。
2. **`padBg` 补空格到 `cols-1` 而非 `cols`**——`truncate` 的防折行预算是 `maxVisible = cols - 1`，按 `cols` 补会把行尾字符（含行尾 reset 后的空列）裁掉。
3. **有意的样式变更必须同步改测试断言**（不弱化测试）——行内代码改芯片样式后 `MarkdownRenderTest` 4 处断言同步更新；PTY 断言先 grep 确认（只匹配 `❯`/`╰─` 等子串且先剥 ANSI），确认不受影响再动。

**经验**：
1. **新增 `Palette` 字段后，必须在每个内置主题里显式赋默认值**，否则静默回退 `Palette()` 构造值——审计方法：grep `apply()` 写回的字段集 vs 主题表赋值的字段集，差集即"已接线未填充"。
2. **ANSI 整行背景是"行级不变式"**：一行内任何 `reset()`/`bg` 缺失都让该位置之后的背景断裂；设计辅助函数（`padBg`）集中管理补空格 + 行尾收尾，禁止各渲染点各自拼。

### 3.20 Windows TUI 框线混排：现代终端恒 UTF-8 不读代码页 + 测试代码进静态产物必须平台守卫（2026-09-08，v1.3.16）

**现象**：用户 Windows 截图（v1.3.7）——logo/标题栏/状态栏是 ASCII（`+--`、`+` 角），同屏的输入框/任务面板/markdown 表格却是 UTF-8 框线（`╰─ ❯`、`╭╮`、`┌┬┐`），混排。Linux 完全不可复现（LANG 恒含 UTF-8，`isUtf8()` 恒 true，bug 被掩盖——§3.15 同款"ASCII 测试全过、平台特定露馅"）。

**根因（双因子叠加）**：
1. **判据缺陷**：`WindowsTerminalBackend.isUtf8()` 仅判 `GetConsoleOutputCP()==65001`。Windows Terminal 内部**恒按 UTF-8 渲染、根本不读控制台代码页**——中文系统控制台 CP 仍是 936（GB18030），判据却只认 65001 → WT 上误判 false → 该降级的没降、不该降的降了。
2. **组件不一致**：InputBox/StatusBar/TabBar/TasksPanel/markdown 表格/`titleBarFull` 硬编码 UTF-8 框线、无视 utf8 标志——即使判据正确，这些组件也永不降级。标志的"权威性"被组件架空。

**修复三件套**：
1. **判据补全**（`term_util.cj`）：新增 `isModernTerminalEnv()` 纯函数——`CJH_FORCE_UTF8`（用户强制开关）/`WT_SESSION`/`WT_PROFILE_ID`（Windows Terminal 注入的环境变量）/`ConEmuANSI`/`ConEmuTask`（ConEmu）任一非空即 true；`isUtf8()` 改「代码页 65001 ∪ 现代终端环境」双判据。原理：cjh TUI 渲染的前提是终端支持 VT（`enableRaw` 失败直接报错退出），任何能渲染 VT 的终端都是恒 UTF-8 的现代终端。
2. **主动切代码页**（`term_windows.cj`）：`enableRaw()` VT 开启成功后 CP≠65001 则 `SetConsoleOutputCP(65001)` 并记原值，`disableRaw()` 恢复——不依赖用户手动 `chcp 65001`，且退出后用户控制台会话不受影响。
3. **组件降级统一**（`term_util.cj` `BoxChars`）：统一边框字符集（圆角/直角/T 型连接 × utf8/ascii 双形态），所有组件从它取字符，消灭"各自 `if (utf8)` 硬编码"的重复定义（项目"可复用函数集中"规范的落地）。

**踩坑（本批新增两条）**：
1. **POSIX FFI 无 `@When[os != "Windows"]` 守卫 → Windows exe 链接失败**：测试辅助 `setenv` FFI 声明后 winbuild 报 `undefined symbol: setenv`——**仓颉 exe 是静态库聚合体，`*_test.cj` 测试代码同样编进产物**（`cjpm test` 与 `cjpm build` 编译范围一致），libs 包新增任何 foreign 函数必须先确认符号在目标平台存在，平台专属的一律加 `@When[os == ...]`/`@When[os != ...]` 守卫（`term_posix.cj`/`term_windows.cj` 的既有模式）。
2. **`TasksPanel.render` 的 `availRow` 语义是输出区底部行号**（面板从底部向上长）：测试传 0 → `startRow<0` 静默不渲染 → 断言全空；且面板高被 `outH/2` 截断、宽被 `cols*2/5` 钳制（<30 不渲染），测试尺寸要按几何公式反推（cols=120 → 宽 48、outH=16 → 面板高 8）。

**经验**：
1. **"终端是否 UTF-8"不能只看代码页**——现代终端（WT/ConPTY/iTerm2/VS Code 内置）恒 UTF-8，代码页是遗留判据；判据应为「显式 65001 ∪ 现代终端特征（环境变量）」，且应用侧应**主动设置**代码页而非被动检测。Linux 恒 UTF-8 的环境会让这类 bug 永不复现，Windows 特定缺陷只能靠交叉编译 + 判据纯函数化（环境注入）单测兜底。
2. **标志必须"一处权威、处处消费"**：utf8 能力一旦判定，所有渲染点统一经 `BoxChars` 取字符；`TuiApp.run()` 在 `enableRaw()`（可能改变判据）之后统一重设各组件标志——组件构造早于 `enableRaw` 的初值视为"可能过时"，以 run 时刻为准。新增组件必须暴露 `setUtf8`（或 init 参数）二选一，否则就是下一个硬编码。

### 3.21 Windows bash 工具调用 /bin/bash 不存在：Shell 降级 + 平台感知缺失（2026-09-08，v1.3.17）

**现象**：Windows 上 `bash` 工具调用 `tail -c 100 file; echo; wc -l file` 报 `ProcessException: Created process failed, errMessage: "The system cannot find the file specified."`。根因：`BashSession.ensureStarted()` 硬编码 `launch("/bin/bash", ...)`，Windows 上 `/bin/bash` 不存在（除非安装 Git for Windows）；`BashTool` 的 timeout 路径同理硬编码 `/bin/bash`。

**根因**：cjh 的 bash 工具完全没区分宿主平台——所有 shell 路径、命令语法（`{ cmd; } 2>&1` bash 专有）、超时机制（`timeout --kill-after=2s` GNU 专有）都假设 POSIX 环境。

**修复**：
1. **ShellProvider**（`term_util.cj`）：平台感知 shell 解析器——Windows 通过 `OS=Windows_NT`/`windir` 环境变量检测，候选 Git Bash 三路径（系统级 ×2 + 用户级 portable）→ Unix 默认 `/bin/bash`；`CJH_SHELL` 环境变量可强制覆盖；不做文件存在性校验（避免 `std.fs` 依赖，launch 失败由 BashTool 捕获报错）。
2. **BashSession**（`bash_session.cj`）：`ensureStarted()` 改为 `launch(ShellProvider.shellPath, ...)`；`execute()` 命令模板按 `isBash` 分支——bash 保持 `{ cmd; } 2>&1` 语法，PowerShell 用 `$LASTEXITCODE`。
3. **BashTool**（`builtin.cj`）：timeout 路径按 `isBash` 分支——bash 用 `timeout --kill-after=2s`，PowerShell 用 `cmd.exe /c timeout`。

**踩坑**：
1. **cjterm 包无法 import std.fs**：`std.fs.exists()` 在 cjterm 构建范围内不可用（`error: undeclared identifier 'std'`）。解法：不做文件存在性校验，launch 失败由 BashTool 捕获并给出明确提示。
2. **PowerShell 命令语法不兼容 bash**：PowerShell 不支持 `{ cmd; }` 分组语法、`$?` 是布尔值（用 `$LASTEXITCODE`）。Git Bash 是唯一无缝兼容现有语法的 Windows shell。

**经验**：
1. **跨平台工具必须区分 shell**：bash/sed/grep/tail 等 POSIX 工具在 Windows 上不存在；`/bin/bash` 路径在 Windows 上不存在。任何涉及 shell 调用的代码都必须经过平台感知的 shell 解析器，禁止硬编码路径或语法。
2. **文件存在性校验不必强求**：在库包中引入 `std.fs` 依赖可能有构建范围限制；更实用的做法是"先选路径，launch 失败再报错"——错误信息给出明确的安装指引，而非静默失败。

### 3.22 仓颉 @Test 宏不支持 for(i in 0..N) 循环：编译报 "note: which is expanded as follows"（2026-09-08，v1.3.18）

**现象**：`InputBoxHistoryTest.testPasteCollapseLarge` 编译报错 `for(i in 0 .. 1500)`，无论上限是 1500 还是 200 都报错，减少上限无效。

**根因**：仓颉 `@Test` 宏展开器会尝试展开测试类中所有语句，但对 `for(i in 0..N)` 有隐式支持限制——宏展开器无法正确处理 range-based for 循环，无论上限大小都会触发 "note: which is expanded as follows" 编译错误。

**修复**：将 `for (i in 0..N)` 改为 `var cnt = 0; while (cnt < N) { ... cnt += 1 }`。while 循环不受宏展开限制。

**经验**：仓颉 `@Test`/`@TestCase` 宏对循环体的展开有未文档化的限制——在测试代码中需要循环构造数据时，一律使用 while 循环而非 for-in 循环。

### 3.23 TUI 粘贴不折叠 + Windows 长路径状态栏折行：折叠阈值按字节误判 + 截断缺失 + 裸流粘贴无合并（2026-09-09，v1.3.19）

**现象**（三处同属"TUI 对超长内容无防护"）：
1. 复制一段中文/长文本粘贴进输入框**不折叠**成 `[Paste #N]`，整段铺开挤满输入行；
2. Windows 下工作目录是深层长路径时，底部状态栏**折行**叠到输入区上方，布局错乱（Linux 短路径难复现）；
3. Windows 控制台粘贴长文本时，TUI **逐键卡顿**（每来一个字符重画一帧）。

**根因**：
1. **折叠阈值按字节计**：`pasteCollapseChars = 1000` 比较的是 `clean.size`（UTF-8 字节数）。中文 1 字 = 3 字节，需 333 汉字才触发；日常粘贴（一两句中文/一段代码）远达不到 → 看似"不折叠"。按码点（`toRuneArray().size`）算才是用户感知的"字符数"。
   叠加一个更隐蔽的**数据丢失 bug**：折叠分支直接 `this.text_ = "[Paste #N…]"` **整段替换**，把光标前已输入的内容（↑ 恢复的历史、手打的命令前缀）**静默丢掉**。终端粘贴语义应是"在光标处插入"，不是"覆盖"。
2. **状态栏无截断**：`StatusBar.render` 把 `content`（模型名 + cwd + 状态 + 提示）原样 `setLine`，从不按行宽截断。`TuiCanvas.setLine` 只存不截，行可见宽度 > 终端列宽时**终端自己折行**，把状态栏下半截挤到下一行。`truncate`/`displayWidth`/`padBg` 都按字节/CJK 正确算，唯独这条入口没调用截断。
3. **Windows 无 bracketed paste**：POSIX 端启用 `ESC[?2004h`，终端用 `ESC[200~…ESC[201~` 包裹粘贴，`readBracketedPaste` 一次性读出整段 → 单个 `isPaste` 事件。Windows 控制台**没有**这套包裹标记，粘贴以离散 `KEY_EVENT` 涌入，`readKey` 一次只返回一个字符、上层 `handleKey` 每个字符都整帧 render → 长粘贴卡顿。

**修复**：
1. `input.cj`：阈值改**码点** `200`（≈ 120 列屏宽的 2.5 倍）；折叠分支改 `this.insertAtCursor(marker)`（保留前缀，marker 仍是原子 token）；`parsePasteMarker` 重构为 `findPasteMarker`（返回字节区间，支持 marker 前后有文本/多 marker）+ `indexOf`；`expandedText` 展开**全部** marker。
2. `statusbar.cj`：新增 `truncateContent`（ANSI 转义序列整体复制不计宽 + CJK=2 列 + 尾部 `…`），`content` 显示宽度 > `width-5`（预算扣前缀 3 列 `┌─`+空格、尾 1 空格、1 列省略号）时截断。
3. 裸流粘贴合并（`term.cj` + `term_backend.cj` + 双后端）：接口加 `supportsBracketedPaste()`（POSIX=`true` 走自身解析、Windows=`false`）+ `readPendingBytes()`（POSIX=FIONREAD 字节数、Windows=`GetNumberOfConsoleInputEvents` 待读事件数）。`Term.readKey` 在裸流后端积压超 `BULK_PASTE_MIN(48)` 时，`hasInput` 非阻塞循环吞读可打印字符（上限 `BULK_PASTE_MAX(2000)` 码点）合并为**单个** `isPaste` 事件；中途的控制键（↑↓←→/Enter/ESC）停止合并并原样返回（不丢事件）。POSIX 分支直通 backend，**不**抢先吞字节（否则破坏 `ESC[200~` 包裹标记）。

**踩坑**：
- `indexOf` 逐字节窗口比较时，窗口起点可能落在多字节 UTF-8 字符的**后续字节**（0x80-0xBF）上，`s[pos..pos+len]` 切在字符中间 → 抛 `IllegalArgumentException: Invalid utf8 byte sequence`（与 §3.15 乱码同族：字节切片必须落字符边界）。修法：`(s[pos] & 0xC0u8) == 0x80u8` 时 `pos += 1` 跳过后续字节；切片仍可能因窗口**终点**落字符中间而抛异常 → `try/catch` 捕获后推进重试。
- 仓颉 `String` 无 `indexOf`：自建逐窗口 `s[pos..pos+sub.size] == sub` 比较（单行输入框长度有限，O(n·m) 可接受）。
- **平台差异判据要放进 backend 接口**：bracketed paste 是否可用是**终端能力**而非"平台"，Windows Terminal/ConPTY 未来可能支持。用 `supportsBracketedPaste()` 让每个 backend 自报，Term 层据此分流，避免 `if (os == Windows)` 硬编码。

**经验**：
1. **折叠/截断阈值一律按码点（`toRuneArray().size`）而非字节（`.size`）**——用户感知的是"字符"，中文 1 字 3 字节会让字节阈值高估 3 倍，中文输入场景下阈值形同虚设。
2. **粘贴/插入语义 = 在光标处插入，不是覆盖整段**——整段替换会静默丢掉用户已输入的前缀（↑ 历史/手打内容），这类丢数据的 bug 比"不折叠"更危险且更难被用户察觉。
3. **终端是"按行宽折行"的**——任何 `setLine` 写入的行，可见宽度必须 ≤ 终端列宽，否则终端自己折行把布局挤乱。渲染组件写入前必须按 `displayWidth` 截断，不能依赖终端"将就着显示"。
4. **跨平台输入能力差异用 backend 接口自报**（`supportsBracketedPaste`/`readPendingBytes`），上层按能力分流——比 `if (os == X)` 硬编码更可维护、可扩展到新终端。

### 3.24 输入框长粘贴软换行 + [Paste #N] 折叠：宽度预算/行段截断/marker 切片三坑（2026-09-09，v1.3.20）

**现象**：
1. 软换行初版**把 150 个 ASCII 包成了 4 行**（预期 2 行），单测 `testDisplayHeightWrap` 先红。
2. 修复后用户报告**粘贴 CJK+markdown 多段落文本后光标未移到末尾**、光标移动异常。
3. 恢复折叠后，中文输入框**每次退格抛 `Invalid utf8`**（`testPasteUtf8Safe` ERROR）。

**根因**：
1. **宽度预算写反（核心 bug）**：`wrappedLines` 里维护 `avail`（剩余可用宽度）逐字符 `avail -= cw`，判断换行用 `if (col + cw > avail)`。但 `col` 是当前行已用列数、`avail` 是剩余列数（= 行宽 - col），两者相加再比 `avail` 等于拿"已用+新字符"去比"剩余"——**把行宽砍了一半**（col 越大越早换行）。正确写法是固定 `budget`=行总宽不变，判断 `if (col + cw > budget)`（累计列+新字符 是否超行总宽）。
2. **行段截断 vs 视口滚动（光标错位 bug）**：`wrappedLines` 把 pairs **截断到前 `maxVisibleRows`(5) 行**，`render` 与光标列计算用"视口内偏移" `pairs[k]` 取段。视口滚到第 7 行后，`pairs[0..4]` 仍是**第 1..5 行的段**——render 画的是正确视口行号但段内容取自首行，光标 CUP 落在错误行/错误列（"光标不在末尾"）。**行数可以 clamp 到视口，段数据必须全量**。
3. **marker 前缀切片落多字节中部（§3.15 同族）**：`markerSpanAt` 用 `t[hit..hit + 8] != "[Paste #"` 比较前缀——hit=0 且文本前 8 字节含 CJK（每字 3 字节，字节 8 落在第 3 个字中部）时切片抛 `Invalid utf8`。`Backspace` 每次退格都调 `parsePasteMarker` → `markerSpanAt`，中文输入框每次退格必崩。
4. **单行组件假设被打破**：`InputBox` 原是"1 行"组件，`TuiApp.renderInner` 硬编码 `inputBox.render(canvas, inputTop, cols, 1)`，状态行/分隔线/输出区高度都按"输入区恒 1 行"推算。改多行后必须把输入区高度变成**动态量**（`displayHeight(cols)` 1..5），状态行/输出区随之上移；否则多行内容会画到状态栏/屏幕外。
5. **提示符宽度是 5 不是 4**：`promptText = "╰─ ❯ "` = `╰`(1) `─`(1) 空格(1) `❯`(1) 空格(1) = **5 码点**。首行软换行预算 = `cols - promptWidth`（80 列时 = 75），续行预算 = `cols - 2`（续行 2 列缩进）。算行数/光标列时必须用同一套预算，否则 render 画的行与 `displayHeight`/`cursorVisualLine` 算的行不一致（光标错位、行数对不上）。

**修复**：
1. `input.cj` `wrappedLines(width)`：`'\n'` 强制断行 + 显示宽度超 `budget` 软断行，输出每行 `(startByte,endByte)` 区间；CJK/全角=2 列对齐 `TuiCanvas.displayWidth` 规则；行宽预算下限 8 列防窄屏死循环。**`budget` 固定为行总宽，判断 `col + cw > budget`**（不再逐字符递减 avail）；**返回全部行段（不截断）**。
2. `render` 行段**按绝对行号取**（`pairs[lineNo]`、光标行段 `pairs[curLineNo + curRowOff]`），不再用视口内偏移；`displayHeight(width)` = 软换行后总行数（clamp 1..5）；`cursorVisualLine(width)` = 光标所在软换行行号（与 render 同源）。
3. **恢复 [Paste #N] 折叠（阈值对齐 atomcode `PASTE_FOLD_LINES=5` / `PASTE_FOLD_CHARS=400`）**：`addPasteLine` 先 CRLF→LF 归一化，`countLines`（**有效内容行**：`'\n'` 计数、末尾换行不计新行——`"l1\nl2\nl3\nl4"`=4 不折叠，`"l1\nl2\nl3\nl4\nl5"`=5 折叠）**≥5** 或 `runeCount`（**码点数** `toRuneArray().size`，对齐 atomcode `text.chars().count()`——CJK 每字计 1，区别于字节/显示宽度）**≥400** → 折叠为 `[Paste #N, +X lines]`（多行）/`[Paste #N, X chars]`（单行；原文存 `pasteStore`、不进输入框），未达阈值 → 原文 `insertAtCursor`。展开 `expandedText()` 扫描文本内所有 marker 替换为原文（**保留前缀/后缀**，支持 `pre [Paste #1, +5 lines]` 混合；同形但序号无效的按字面处理）；marker 是**原子 token**（光标在末尾时退格整体删除）；Enter 提交 `expandedText()`（展开原文，多行换行保留），历史与回显均存展开原文。
4. `markerSpanAt` 前缀 8 字节**逐字节比较**（读单字节 UTF-8 安全），不用 `t[hit..hit+8]` 切片。
5. `app.cj`：非编辑模式 `editBoxH0 = inputBox.displayHeight(cols)`（输入区 1→最多 5 行）；`inputBox.render(canvas, inputTop, cols, editBoxH0)`；welcome 视图居中块高 = `1 + editBoxH0`；`/` 下拉 picker 渲染上限 `lineIdx < inputTop`（不压状态行）；帮助文本同步（软换行 + 超 5 行/400 字折叠）。

**踩坑**：
- **`if` 表达式两分支类型必须一致**：`this.text_[i]` 是 `UInt8`（`Byte`），兜底 `0` 是 `Int64`，`let b1 = if (i+1 < len) { this.text_[i+1] } else { 0 }` 报 "types UInt8 and Int64 of the two branches of this 'if' expression mismatch"。兜底分支写 `0u8`。
- **仓颉 `String` 无 `\x` 转义**：测试里要拼 ESC 字符用 `Rune(27).toString()`（仓内 `tui_test.cj` 既有先例），写 `"\x1b"` 报 `unrecognized escape '\x' in string literal`。
- **仓颉 lambda 捕获可变 `var` 不能作为回调存储**：`ib.onSubmit = { s => submitted = s }`（submitted 是 var）报 `lambda capturing mutable variables needs to be called directly`。解法：`let submitted = ArrayList<String>()` + `submitted.add(s)`（绑定不可变、对象内容可变）。
- **探针定位法**：单测断言值（预期行数 2）与实现行为（实际 4 行）对不上、且纸面推演"算法正确"时，加一个临时 `@TestCase` 探针把 `text().size`/`displayHeight`/`promptWidth` 拼进一个字符串断言（`@Assert("sz=… dh=… pw=…", "")`）一次读出真实值定性——比反复纸面推演快，且能顺手发现"提示符实为 5 码点"这类算错的常量。

**经验**：
1. **软换行/截断的宽度判断一律用"固定行总宽 budget + 累计 col"**（`col + cw > budget`），不要用"逐字符递减的 avail + col+cw"——后者把 col 计了两次，行宽减半、换行过密。这是"剩余量 vs 总量"的经典笔误。
2. **行数、光标行、渲染行三者必须共用同一个 `wrappedLines` 数据源**（预算/缩进/宽字符规则单一来源），任何一处另写一份预算逻辑都会漂移成"光标错位/行数对不上"。
3. **视口滚动组件的段数据必须全量返回、按绝对行号索引**：行数可以 clamp 到视口高度，但 (start,end) 段数组不能截断到视口——否则滚动后读到过期首行段（内容错位 + 光标错位）。`render` 内"视口内偏移"与"绝对行号"是两套索引，混用必错。
4. **UTF-8 文本的固定长度前缀比较逐字节读、不切片**（`t[hit+k] != prefix[k]`）：切片终点落多字节字符中部抛 Invalid utf8（§3.15 同族）；高频路径（退格）会把它放大成"每次按键都崩"。
5. **单行组件改多行，布局层必须同步动态化**：`render(row,width,height)` 的 `height` 参数从常量 1 变成 `displayHeight()`，且所有"输入区上方有多少行"的推算（状态行、分隔线、输出区、弹窗、picker 上限）都要跟随这个动态高度，否则多行内容越界。
6. **折叠与软换行并存时的分界指标要按"有效内容行"而非字节/码点**：>3 行折叠、≤3 行软换行；末尾换行不计新行（`"l1\nl2\nl3\n"`=3 行不折叠），与"真实换行符计数"（该文本=3）不同口径——折叠判定与显示行数（4，含空尾行）是两回事，各用各的口径并在注释里写明。

CJH_MOCK=1 ./target/release/bin/cjh

## 七、可复用模块抽离（生态贡献）

遵循"可复用模块独立成库"原则，已抽离：

### cjterm — 仓颉终端 UI 库（`libs/cjterm/`）

**零外部依赖的纯仓颉终端库**，任何需要终端界面的仓颉项目可复用：

| 模块 | 能力 |
|---|---|
| `Ansi` | ANSI 转义（颜色 256 色/光标/清屏/隐藏光标） |
| `Screen` | 差分渲染（期望状态网格 + 仅输出差异行） |
| `Term` | **纯 libc FFI**：termios 原始模式、非阻塞按键、ioctl 终端尺寸 |

**关键设计**：termios 用纯 FFI 直调 libc（tcgetattr/tcsetattr/read/ioctl/select），
**无外部 .so 依赖**——`@C struct` 布局手写（Linux x86_64 termios 60 字节），
标志位用 UInt32 位运算（仓颉按位取反是 `!` 一元运算符，非 `~`）。

**使用**：主项目 `[dependencies] cjterm = { path = "./libs/cjterm" }`。

### 抽离原则

- 零/低依赖优先（cjterm 零依赖 → 最先抽）
- 业务耦合的留在主项目（config 依赖 llm、tools/agent 是 agent 专属）
- 候选后续抽离：`cjh.llm`（LLM 客户端，依赖 model）、`cjh.model`（消息模型）
