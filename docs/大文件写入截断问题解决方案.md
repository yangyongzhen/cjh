# cjh 技术实现方案：攻克大文件写入截断难题

> 版本：v1.3.0
> 日期：2026-08-24
> 状态：已落地，端到端验证通过

## 一、问题背景

### 1.1 现象

让 cjh 生成一个 H5 射击小游戏（`shooter-game/index.html`），文件大约 5000~8000 字符。结果：

- LLM 用 `write_file` 一次性输出整个 HTML
- 输出到 `if (lives <= 0) gameOver();` 处被截断
- 文件缺少 `</script></body></html>` 闭合标签
- LLM 收到"文件不完整"警告后，**重新发起 `write_file`**
- 再次截断，陷入死循环

```
write_file(全量HTML) → max_tokens截断 → 文件不完整
    ↑                                           ↓
    └── 收到警告 → 重新write_file ←───── LLM重写倾向
```

### 1.2 影响范围

这不是单个 bug，而是**架构级缺陷**：

- 任何超过模型单轮 max_tokens 的大文件写入都会触发
- DeepSeek/Kimi 等国产开源模型尤为严重（max_tokens 上限低、finish_reason 报告不规范）
- 传统"加 prompt 提示别写太长"的方案无效——模型在生成 tool_call JSON 的瞬间就已经进入长文本输出状态

### 1.3 业界参照

成熟 CLI 工具（OMP/Aider/Cursor）都不靠 prompt 提示解决问题，而是通过**架构和工具协议约束**：

| 工具 | 核心机制 |
|------|---------|
| OMP (oh-my-pi) | Hashline Edits（带 Hash 锚点的精准局部编辑）+ 状态机强行打断 |
| Aider | Search/Replace 块编辑 + repo map 上下文压缩 |
| Cursor | 应用层 diff 协议 + LSP 语义锚点 |

cjh 的解法对齐 OMP 的三层防线，但做了适配仓颉生态和 DeepSeek 模型特性的调整。

## 二、根因分析

### 2.1 Payload 膨胀 vs max_tokens 限制

`write_file` 工具的 JSON payload 结构：

```json
{
  "name": "write_file",
  "arguments": {
    "path": "shooter-game/index.html",
    "content": "<!DOCTYPE html>...</script></body></html>"  // 几千字符
  }
}
```

`content` 字段承载完整文件内容，直接膨胀 tool_call JSON 体积。当 content 超过模型单轮 max_tokens 上限时，JSON 在 content 中间被截断。

### 2.2 截断检测不可靠

OpenAI 标准协议规定：输出被 max_tokens 截断时返回 `finish_reason: "length"`。但实际观测：

| 模型 | finish_reason 实际值 | 标准协议值 |
|------|---------------------|-----------|
| DeepSeek-v4-flash | `tool_calls` | `length` |
| GPT-4o | `length` | `length` |
| Claude | `max_tokens` | `max_tokens` |

DeepSeek 即使在 max_tokens=16384 的情况下，截断时仍返回 `tool_calls` 而非 `length`。这意味着依赖 `finish_reason=="length"` 的截断检测**完全不触发**。

### 2.3 重写倾向（注意力陷阱）

模型收到"文件不完整，请修复"的警告后，其注意力机制趋向于**重新生成整个文件**，而非在现有文件基础上增量续写。

这是 transformer 架构的固有特性：模型在训练数据中见到的"修复文件"模式大多是"重写整个文件"，而非"在末尾追加"。一旦进入重写模式，就会再次触发截断，形成死循环。

### 2.4 Prompt Cache 前缀破坏

DeepSeek 支持 prompt cache，但命中率低。根因：每轮追加的 tool_result 破坏了 messages 数组的前缀一致性。

```
[system, user, assistant(tool_calls), tool(result)]  ← 前缀
[system, user, assistant(tool_calls), tool(result), assistant, tool(result)]  ← 前缀变了
```

如果 tool_result 过长（如 read_file 读了个几千行日志），巨大的 tool 结果会冲垮前缀，导致后续 cache 失效。

## 三、三层防线架构

### 3.1 架构总览

```
┌─────────────────────────────────────────────────────────┐
│  第一层：工具契约层（Tool Contract Layer）                │
│  - write_file：content 软上限 150 行/4000 字符           │
│  - append_file：增量追加工具（新增）                      │
│  - hashline_edit：带锚点的精准局部编辑                    │
├─────────────────────────────────────────────────────────┤
│  第二层：截断打断层（Truncation Interception Layer）      │
│  - JSON 被截断 → repairTruncatedJson 救回前半段落盘       │
│  - ModelResponse.truncatedPaths 记录被截断文件            │
│  - agent loop 注入 [System Notice] 绝对指令               │
│  - 斩断"重写 → 截断 → 重写"死循环                         │
├─────────────────────────────────────────────────────────┤
│  第三层：前缀冻结层（Prefix Freeze Layer）                │
│  - messages 数组 append-only（审计确认）                  │
│  - truncateToolResult：Tool Output 压缩 Hook              │
│  - >6000 字符的 tool_result 裁剪成 Head/Tail 摘要         │
└─────────────────────────────────────────────────────────┘
```

### 3.2 第一层：工具契约层

#### 设计原则

不让 `write_file` 接收完整的大文件 content。拆分工具语义：

- `write_file`：创建文件骨架（HTML 头部 + 空 body/script 标签）或写入小文件
- `append_file`：增量追加（多次调用，每段追加一部分内容）
- `hashline_edit`：基于行号/哈希锚点的精准局部编辑

#### write_file 软上限

```cangjie
// src/tools/builtin.cj - WriteTool.execute()
let lines = content.split('\n').size
if (content.size > 4000 || lines > 150) {
    File.writeTo(path, content.toArray())
    return ToolResult(
        "Written ${path} (${content.size} chars).\n" +
        "WARNING: content exceeds the recommended limit " +
        "(${lines} lines / ${content.size} chars); " +
        "risk of max_tokens truncation. If the file turns out " +
        "incomplete, switch to: write_file for the skeleton + " +
        "append_file for incremental chunks.", false)
}
```

**关键设计决策**：软上限**警告但不阻断**。

- 阻断会破坏工具的通用性——小文件也可能超 4000 字符
- 警告让 LLM 自行决定是否拆分，同时给 agent loop 留出截断检测的余地

#### append_file 增量追加

```cangjie
// src/tools/builtin.cj - AppendFileTool
public class AppendFileTool <: CjhTool {
    public func spec(): ToolSpec {
        return ToolSpec("append_file",
            "Append content to the end of an existing file " +
            "(incremental write). Used for multi-chunk writing " +
            "of large files: first create the skeleton with " +
            "write_file, then call append_file multiple times " +
            "to append each part. Single-call content should " +
            "stay under 150 lines / 4000 chars.", ...)
    }

    public func execute(args: JsonObject): ToolResult {
        let existing = String.fromUtf8(File.readFrom(path))
        let newContent = existing + content
        File.writeTo(path, newContent.toArray())
        return ToolResult("Appended ${content.size} chars to ${path} " +
            "(now ${newContent.size} chars total)", false)
    }
}
```

**关键设计决策**：append_file 通过 try/catch 读文件判断存在性（仓颉 `File` 无 `exists` 方法），文件不存在时返回错误提示"请先用 write_file 创建文件骨架"。

### 3.3 第二层：截断打断层

#### 截断检测：tryParseJson 失败即标记

由于 DeepSeek 不报告 `finish_reason=length`，改用 **JSON 解析失败**作为截断信号：

```cangjie
// libs/cjllm/src/provider.cj - StreamAccumulator.finish()
let parsed = tryParseJson(raw)
match (parsed) {
    case Some(obj) => args = obj  // 正常解析
    case None =>
        // tryParseJson 失败 = JSON 被截断
        this.truncated = true
        let repaired = repairTruncatedJson(raw)  // 救回前半部分
        match (tryParseJson(repaired)) {
            case Some(obj) =>
                args = obj
                // 记录被截断的 write_file/edit_file 的 path
                if (name == "write_file" || name == "edit_file") {
                    match (obj.get("path")) {
                        case Some(p) =>
                            match (p.kind()) {
                                case JsonKind.JsString =>
                                    this.truncatedPaths.add(p.asString().getValue())
                                case _ => ()
                            }
                        case None => ()
                    }
                }
            case None => args.put("_raw", JsonString(raw))
        }
}
```

**关键设计决策**：

1. **不依赖 finish_reason**：DeepSeek 的 `finish_reason=tool_calls` 不可靠，改用 `tryParseJson` 失败作为截断信号
2. **repairTruncatedJson 方案2优先于方案1**：
   - 方案1：截断到上一个完整字段（丢弃被截断的 content）
   - 方案2：补 `"}` 闭合字符串（保留被截断的 content）
   - 选方案2，让前半段落盘，后续用 append_file 续写

#### 截断打断：[System Notice] 绝对指令

```cangjie
// src/agent/loop.cj
if (response.truncatedPaths.size > 0) {
    var notice = "\n[System Notice - ABSOLUTE DIRECTIVE, MUST EXECUTE]\n"
    notice += "The previous write_file was truncated by the model's " +
        "max_tokens. The file has been saved to disk but is INCOMPLETE.\n"
    notice += "Truncated files:\n"
    for (i in 0..response.truncatedPaths.size) {
        notice += "  - ${response.truncatedPaths[i]}\n"
    }
    notice += "\n[FORBIDDEN] Absolutely DO NOT call write_file again " +
        "to rewrite these files -- it will truncate again and fall " +
        "into an infinite loop.\n"
    notice += "[MANDATORY] For each truncated file, execute immediately:\n"
    notice += "  1. read_file <path> to confirm the current end of the file\n"
    notice += "  2. append_file <path> \"<next chunk of remaining content>\" " +
        "(each chunk <= 1500 chars)\n"
    notice += "  3. Repeat step 2; the final chunk MUST append the closing " +
        "tags </script></body></html>\n"
    notice += "  4. read_file <path> to verify the file is complete and " +
        "properly closed\n"
    notice += "Do NOT perform any other action until the above steps " +
        "are complete."
    this.messages.add(ChatMessage("user", notice))
}
```

**关键设计决策**：

1. **绝对指令语气**：`[FORBIDDEN]`、`[MANDATORY]`、`ABSOLUTE DIRECTIVE` —— 用最强语气斩断 LLM 的"重写"倾向
2. **明确步骤**：read_file → append_file → 重复 → 验证 —— 给 LLM 一个清晰的执行路径，避免它自由发挥
3. **注入为 user 消息**：不是 system 消息（system 消息可能被模型忽略），而是 user 消息（模型必须响应）

### 3.4 第三层：前缀冻结层

#### messages 数组 append-only 审计

审计 `src/agent/loop.cj` 中所有 `messages.add()` 和 `messages[i]` 修改点：

| 位置 | 操作 | 是否破坏前缀 |
|------|------|--------------|
| `loop.cj:141` | 初始化时 `add(system)` | ✅ 只在初始化 |
| `loop.cj:210` | `run()` 入口 `add(user)` | ✅ 尾部 push |
| `loop.cj:244` | `add(asstMsg)` | ✅ 尾部 push |
| `loop.cj:273/307` | `add(tool result)` | ✅ 尾部 push |
| `loop.cj:292/325` | `add(user, [System Notice])` | ✅ 尾部 push |

**结论**：cjh 的 messages 构造**已经符合 OMP 的尾部追加模式**，没有发现"更新已存在 Message 的 token 统计/改 ID"这类破坏前缀的操作。

#### Tool Output 压缩 Hook

```cangjie
// src/agent/loop.cj - truncateToolResult()
private func truncateToolResult(content: String, toolName: String): String {
    let MAX_CHARS: Int64 = 6000   // 单个 tool_result 存入历史的字符上限
    if (Int64(content.size) <= MAX_CHARS) {
        return content
    }
    let headLen: Int64 = MAX_CHARS / 2
    let tailLen: Int64 = MAX_CHARS - headLen
    let head = content[0..Int64(headLen)]
    let tailStart = Int64(content.size) - tailLen
    let tail = content[Int64(tailStart)..Int64(content.size)]
    let skipped = Int64(content.size) - MAX_CHARS
    return head + "\n\n…[截断 " + skipped.toString() + " 字符]…\n\n" + tail
}
```

**关键设计决策**：

1. **Head/Tail 裁剪而非只保留 Head**：保留文件头部和尾部，中间截断。因为代码文件的头部（import/声明）和尾部（闭合标签/return）通常最重要
2. **6000 字符上限**：经验值，平衡 token 预算和信息保留。OMP 用 `toolResultMaxChars` 硬性裁剪，cjh 对齐该机制

## 四、数据流与关键代码路径

### 4.1 完整数据流

```
LLM 流式输出 tool_call JSON
    │
    ├─ StreamAccumulator.feed() 累积 delta.function.arguments
    │
    ├─ StreamAccumulator.finish()
    │   ├─ tryParseJson(raw) 成功 → 正常解析 args
    │   └─ tryParseJson(raw) 失败 → truncated=true
    │       ├─ repairTruncatedJson(raw) 救回前半段
    │       ├─ 解析出 path → truncatedPaths.add(path)
    │       └─ 透传到 ModelResponse.truncatedPaths
    │
    ├─ Agent.run() 收到 ModelResponse
    │   ├─ 执行 write_file（被截断的 content 落盘）
    │   ├─ tool result 回填（经 truncateToolResult 压缩）
    │   └─ 检测 truncatedPaths 非空
    │       └─ 注入 [System Notice] 绝对指令
    │
    └─ 下一轮：LLM 看到 [System Notice]
        ├─ read_file 确认截断位置
        ├─ append_file 续写剩余内容
        └─ read_file 验证文件完整闭合
```

### 4.2 关键文件清单

| 文件 | 职责 | 关键代码 |
|------|------|---------|
| `libs/cjllm/src/message.cj` | ModelResponse 数据模型 | `truncatedPaths: ArrayList<String>` 字段 |
| `libs/cjllm/src/provider.cj` | 流式累积 + 截断检测 | `StreamAccumulator.finish()` — tryParseJson 失败标记 truncated + 记录 truncatedPaths |
| `libs/cjutil/src/jsonrepair.cj` | JSON 修复工具 | `repairTruncatedJson()` — 方案2优先于方案1 |
| `src/tools/builtin.cj` | 工具契约层 | `WriteTool` 软上限 + `AppendFileTool` 增量追加 |
| `src/agent/loop.cj` | 截断打断层 + 前缀冻结层 | `[System Notice]` 注入 + `truncateToolResult` 压缩 Hook |
| `libs/cjcfg/src/config.cj` | 默认 systemPrompt | 「大文件写入策略」段（英文） |

## 五、踩坑记录

### 5.1 finish_reason 不可靠

| 维度 | 内容 |
|------|------|
| **现象** | DeepSeek 返回 `finish_reason=tool_calls` 而非 `length`，`finish_reason=="length"` 截断检测不触发 |
| **根因** | DeepSeek 的 finish_reason 实现不遵循 OpenAI 标准协议 |
| **解法** | 改用 `tryParseJson` 失败作为截断信号（JSON 被截断必然解析失败） |
| **代价** | 误判风险：合法的 JSON 解析失败也会被标记为截断。但实际场景中，tryParseJson 失败的 99% 原因就是截断 |

### 5.2 repairTruncatedJson 方案选择

| 维度 | 内容 |
|------|------|
| **现象** | JSON 被截断时，需要修复才能解析出已生成的 content |
| **方案1** | 截断到上一个完整字段（丢弃被截断的 content）—— 安全但浪费 |
| **方案2** | 补 `"}` 闭合字符串（保留被截断的 content）—— 激进但高效 |
| **决策** | 方案2优先于方案1。保留被截断 content 让前半段落盘，后续用 append_file 续写 |
| **风险** | 方案2可能在某些边缘情况下修复出错误的 JSON。但配合 tryParseJson 二次校验，风险可控 |

### 5.3 enum 模式参数数量

| 维度 | 内容 |
|------|------|
| **现象** | `PatchOp.LineAnchor` 加 String 参数后，`case LineAnchor(_)` 编译报 "enum pattern's parameters size is wrong" |
| **根因** | 仓颉 enum 构造子参数数量变化后，所有 match 模式必须同步更新 |
| **解法** | 所有 `LineAnchor(_)` 改为 `LineAnchor(_, _)`，漏改一处即编译失败 |
| **教训** | 仓颉 enum 改参数数量时，grep 全部引用点逐一更新，不要遗漏 |

### 5.4 提示词语言

| 维度 | 内容 |
|------|------|
| **现象** | 中文 systemPrompt + 工具 description 浪费 token，DeepSeek prompt cache 命中率低 |
| **根因** | 中文字符 UTF-8 编码占 3 字节，token 开销比英文大 |
| **解法** | 全改英文（工具 schema description + systemPrompt + [System Notice]），保留 "answer in Chinese" 让模型回复中文 |
| **效果** | token 开销降低，模型对英文指令的遵循度更高 |

### 5.5 File.exists 不存在

| 维度 | 内容 |
|------|------|
| **现象** | `AppendFileTool` 用 `File.exists(path)` 判断文件是否存在，编译报 "'exists' is not a member of class 'File'" |
| **根因** | 仓颉 `File` 类没有 `exists` 静态方法 |
| **解法** | 改用 try/catch 读文件判断存在性：`let existing = String.fromUtf8(File.readFrom(path))`，读取失败说明文件不存在 |

## 七、后续优化方向

### 7.1 硬性截断阻断（未实现）

当前 write_file 软上限只警告不阻断。未来可考虑硬性阻断：content 超过阈值时直接拒绝执行，强制 LLM 拆分。

**风险**：可能破坏小文件写入的通用性。需要更精确的阈值判断。

### 7.2 Hashline Edits 深化

当前 hashline_edit 支持行号锚点（`@@N`）+ 可选内容校验（`@@N content`）。未来可考虑：

- **区间操作**：`@@N1..N2` 定位行区间，批量删除/替换
- **正则锚点**：`@@/pattern/` 用正则匹配定位行（比哈希更灵活）
- **上下文感知**：自动检测缩进/语法结构，智能选择插入位置

### 7.3 Prompt Cache 命中率量化

当前只做了前缀冻结的架构改造，没有量化 prompt cache 命中率的提升。未来可加日志统计 cached_tokens / prompt_tokens 比率，验证前缀冻结的效果。
