# 后台任务与槽位 · 设计方案

> 状态：**已实现（B-1，2026-11-06）**——基线 v1.6.5，实现见 `src/tools/background_task.cj`。
> 本文定义 cjh 的「后台任务」层：非阻塞派发 + 槽位上限 + 轮询收割。
> 评审焦点：§5.6 的生命周期归属（OA）与 §6.5 与方案D 的合并方式（OB），均已按评审结论落地
> （OA：任务跨回合存活、无开关；OB：一期用 `bash_*` 命名，二期接子代理时再评估统一 `task_*`）。
> 与方案 D 的有意分歧见 §6.5；实现与本文的差异只在于 `formatElapsedMs` 补零这类细节修正。

## 1. 背景与动机

### 1.1 触发点

对标主流 agent（AtomCode / omp / pi）时发现一类效率差距：**它们把"执行"和"等待"分开了**。

典型浪费场景（cjh 现状）：

| 场景 | 现状 | 代价 |
|---|---|---|
| 连跑 3 个长构建（`cjhpm build` / `npm install` / `hvigor`） | 3 次同步 `bash`，每次阻塞到结束 | 总耗时 = 3 段之和 |
| 长测试（5 分钟）期间想同时读代码 | 做不到——`bash` 不返回，父回合不产生任何新 token | 串行空等 |
| 长命令忘了调大 `timeout` | 到点杀掉会话，已花的时间全废 | 见 `docs/开发文档与踩坑记录.md` 的"发起 build 后卡死"一类事故 |
| 官方建议的土办法：`<cmd> > build.log 2>&1` + `read_file` 轮询 | 可行但要人肉构造、无退出码、无超时兜底、kill 不到 | 易流失在"日志文件写哪、怎么判断跑完" |

`bash` 工具的工具描述里其实已经写了这条土办法（`src/tools/builtin.cj:162`），
说明需求真实存在——只是缺一层**一等公民的后台任务抽象**。

### 1.2 现状盘点（哪些已经有了，不要重做）

写本文前逐项核对过源码，避免重复设计：

| 能力 | 现状 | 位置 |
|---|---|---|
| 并行子代理 | `SubagentScheduler` 信号量 `max_subagents`、DAG 拓扑组内并发、错峰派发、token/墙钟预算闸门、`AgentNode` 面板 | `src/agent/scheduler.cj`、`src/agent/loop.cj:865` |
| 回合内消息不阻塞 | TUI `enqueueInput` 不阻塞输入；每轮 LLM 请求前 `onRequestPendingInput` 拉队列注入 | `src/tui/app.cj:1059`、`src/agent/loop.cj:751` |
| 同批工具并发 | V2d DAG：只读工具并行、写工具串行、结果按 LLM 原始顺序回填 | `src/agent/loop.cj:865-930` |
| 压缩摘要后台化 | `pendingCompact` 用 `spawn` 在后台跑，不阻塞主循环 | `src/agent/loop.cj:1317` |
| 工具注册与并发分类 | `CjhTool.isReadOnly()` 决定能否进 DAG 并行组 | `src/tools/registry.cj:64` |

**结论：并行子代理与消息不阻塞 cjh 已经有**，缺的只有第一件事——**bash 执行本身仍是同步阻塞**。

### 1.3 同步阻塞的两处根因（实现时必须认清）

1. **`BashTool.execute` 同步等**：`BashSession.execute`（`src/tools/bash_session.cj:42`）写命令进持久 bash 的 stdin，
   起读线程阻塞读 stdout 直到完成标记，**主线程 50ms 轮询等标记或超时**——命令行不返回，工具调用就不返回。
2. **整个会话被一把 `Mutex` 串行化**：`BashSession.lock` 保证同一时刻只有一条命令在跑
   （这是对的——一个 bash 进程的 stdin 只能顺序喂）。**所以后台任务不能复用它**，
   必须走独立进程；这决定了下文的进程模型。

## 2. 目标与非目标

### 2.1 目标

1. **G1 非阻塞派发**：`bash_start` 启动命令后**立即返回** `task_id`，父回合继续干活。
2. **G2 有界并发**：槽位上限（默认 8），**满则直接拒绝并给出可行动提示**（评审已定：不排队）。
3. **G3 增量可读**：`bash_poll` 只回"上次之后的新增"，不重复灌上下文；进程退出后仍能读到完整输出。
4. **G4 可终止**：`bash_kill` 能杀掉**整个进程树**并回收僵尸。
5. **G5 可观测**：任务状态在 TUI 面板 / Web 帧可见，与子代理面板同源呈现。
6. **G6 同源安全**：后台执行**不得绕过** capability 审批——审批发生在 `bash_start` 时刻（命令内容已知）。

### 2.2 非目标（本期明确不做）

| 项 | 理由 |
|---|---|
| 后台任务间管道 / 依赖编排 | `&&`、`;`、`\|` 在命令内部自己写；跨任务编排是无底洞 |
| 后台任务 stdin 交互 | 没有 stdin 写入口 → 交互式程序会在后台静默等输入。与其"看起来能交互实则死锁"，不如**承诺不能**，并让 poll 在检测到"无输出且仍在运行"时提示这条 |
| 跨会话共享任务表 | 任务归会话所有，会话切换不串 |
| 后台任务的持久化 / 重启恢复 | 进程没了任务就没了，恢复的是"日志文件"，不是"可续跑的进程" |
| 复用一个持久 bash 会话跑多命令 | 见 §1.3，stdin 只能顺序喂，做不到真并行 |

## 3. 继承红线（不得破坏）

沿用 `docs/异步子代理与进阶能力-方案D.md` §2 的不变量，并新增两条：

1. **权限单调**：后台任务的风险等级 = `bash`，走**完全相同**的 capability 审批链路；
2. **有界资源**：槽位 / 墙钟 / 输出体量三者都有上限——"后台"不等于"无界"；
3. **可观测**：每个任务全程可定位（状态机 + 日志落盘 + 面板行）；
4. **可回收**：任务终态必须 `wait()` 回收，禁止留下僵尸进程（`bash_session.cj:28-32` 记着"4 个未回收僵尸"事故）；
5. **诚实降级**：做不到的能力（stdin 交互、PowerShell 下的进程组 kill）必须**明确报错**，
   不许静默假装在跑（同 `AGENTS.md` 里"诊断分支不能假装在跑"的教训）。

## 4. 核心设计

### 4.1 任务模型与状态机

```cangjie
public enum TaskState {
    Running | Succeeded | Failed | Killed | Timeout
    // 终态 = Succeeded / Failed / Killed / Timeout；Running 是唯一非终态
}
```

**没有 `Pending`**：评审已定"槽位满则直接拒绝"，任务表里不存在排队态——要么已启动（Running），要么根本没被创建。
（Python `ThreadPoolExecutor(max_workers=8)` 超了会挂起等待，那是另一种语义；这里明确**不学**，理由见 §4.2。）

任务记录：

```cangjie
public class BackgroundTask {
    public let id: String          // "bg-1"；会话内自增
    public let kind: String        // "bash"（二期 "subagent" 复用同一张表）
    public let label: String       // 面板显示行，默认取命令前 60 字符
    public let command: String     // 原始命令（诊断 / 回看）
    public let startedAt: DateTime
    public var state: TaskState = TaskState.Running
    public var exitCode: Int64 = -1
    public var endedAt: Option<DateTime> = None
    public let logPath: String     // 全量输出落盘路径
    public var readOffset: Int64 = 0    // poll 游标（已交付给模型的字节偏移）
    public var totalBytes: Int64 = 0
    public var pid: Int64 = 0
    // ★ 解耦点：kill 行为由回调注入，任务表不认识"进程"也不认识"子代理"
    public let killer: () -> Unit
}
```

`killer` 回调是整个设计里唯一为**二期合并**留的口子（§6.5）：任务表只管
"谁在跑 / 跑到哪 / 怎么停"，具体是 `terminate(force)` 还是"中断传播给子代理"，由注册方决定。

### 4.2 槽位语义

| 项 | 定义 |
|---|---|
| 配置键 | `max_background_tasks`，默认 **8**，`0 = 不限`（与既有四键 `max_subagents` 等的语义一致，见 `libs/cjcfg/src/config.cj:276`） |
| 占用计数 | **非终态**任务数。终态任务留在表里供 `bash_poll` 回看，但**不占槽** |
| 满时行为 | `bash_start` 返回 `is_error=true`，内容含 (a) 当前存活任务清单 `id / label / 运行时长`，(b) 可行动提示"先 `bash_poll` 收割或 `bash_kill` 释放槽位" |

**为什么不排队**（评审已定，这里写清理由以免日后被"改成排队更友好"翻案）：

1. 排队会让 `bash_start` 返回"成功"而命令**根本没在跑**，模型据此继续推进 → 后果不可预测；
2. 排队任务在会话结束 / 中断时属于哪种语义，是第二套生命周期，收益不抵复杂度；
3. 直接拒绝让模型**立刻**知道被挡，并拿到"谁占着槽、怎么释放"的信息，能自行收拾——
   这与 `SubagentScheduler.tryBeginSpawn`（`src/agent/scheduler.cj:128`）"判定 + 计数同一把锁内完成"的
   TOCTOU 教训同源：**判定必须和执行耦合，中间不留窗口**。

终态任务清理：表内保留最近 `16` 个终态记录供回看，更早的从表里剔除（**日志文件保留**，路径可查）。

### 4.3 输出采集与游标

```
        ┌──────── stdOut ────────┐
子进程 ─┤                        ├──► 读线程 ──► 内存 ring（末尾 256KB）+ 追加落盘
        └──────── stdErr ────────┘                        │
                                                 readOffset 游标 ──► bash_poll 增量交付
```

三条关键决定：

**① 不需要完成标记（marker）**。同步路径（`bash_session.cj:47`）要靠 `__CJH_END_N__`
判断"这条命令跑完了"，因为多个命令复用同一个 bash 进程。后台任务是**独立进程**：
进程退出 → 管道 EOF → 读线程自然结束 → `wait()` 拿退出码。比同步路径干净，
也天然避开"标记被 `exec 1>file` 带走"那一整类坑（`bash_session.cj:59-64`）。

**② stdout/stderr 合并**，与同步 `bash` 的对外行为一致（现行 `bash` 也是 `2>&1` 合并后回一个
`exit code: N`）。两条管道分别读需要合并排序，收益为零。

**③ 游标按字节偏移推进**，不按行：
`bash_poll` 返回 `[readOffset, min(totalBytes, readOffset + 单次上限))` 这一段，然后把
`readOffset` 推到该段末尾。这样模型连轮询不会重复吃同样的输出。

补充读取方式（解决"游标推过去了但我想回看"）：

| 参数 | 语义 |
|---|---|
| 默认 | 增量：从 `readOffset` 往后 |
| `from_start: true` | 游标重置为 0，从头读（不影响后续增量起点） |
| `tail_lines: N` | 只回最后 N 行（内部换算成字节区间，仍受单次上限约束） |

**UTF-8 安全是硬要求**（已踩两次坑，必须写进实现要点）：
- 字节切片后用 `cjutil.safeFromUtf8` 解码，**禁止** `String(Rune(byte))` 逐字节拼（会把中文打成 `éè»`，见 `bash_session.cj:204-212`）；
- **禁止** `StringBuilder.append(Byte)`（按十进制整数输出，见 `AGENTS.md`）；
- 读线程累积字节时，多字节字符被管道切断处要留 pending 等下一块（照抄 `readUntilMarker` 的边界探测逻辑）。

### 4.4 进程模型与回收

```cangjie
// 要点：独立进程 + 独立（或关闭）stdin + PATH 补齐 + 2>&1 合并
let wrapped = shellPathFix(shellPath, true) + "cd <cwd> 2>/dev/null; { " + cmd + "\n} 2>&1\n"
let p = launch(shellPath, ["-c", wrapped], stdIn: <关闭>, stdOut: Pipe)
```

| 关注点 | 设计 |
|---|---|
| **不复用持久会话** | 根本原因见 §1.3：`BashSession` 的 stdin 只能顺序喂，一把 `Mutex` 串行化。后台要真并行 → 必须独立进程 |
| **stdin** | 关闭，不提供输入。理由见 §2.2：交互式程序会在后台静默等输入。`bash_poll` 在"运行中且长时间无新输出"时给出这条提示 |
| **cwd** | 默认 = cjh 进程工作目录；可选 `cwd` 参数。**不继承持久会话的 cwd**（做不到，见下） |
| **env** | 继承 cjh 进程环境。**不继承**会话里 `export` 过的变量（同上） |
| **PATH 补齐** | 必须包 `shellPathFix`（`src/tools/shell_path.cj`）。`bash -c` 的独立进程一样会遇到"`cat`/`sed` 是 127"，见 `bash_session.cj:65` |
| **kill 粒度** | 一期：`terminate(force: true)` + `wait(5s)`；随后用进程树快照比对，若仍有残留则按 pid 兜底清理。Windows PowerShell 无进程组 → **明确提示"仅终止顶层进程"**，不假装已全清 |
| **僵尸回收** | 终态必 `wait()`。`bash_session.cj:28-32` 记着"4 个未回收僵尸"事故；只 `terminate` 不 `wait` 就会累积 |
| **统一回收** | `main` 退出 + `SessionMgr` 关闭会话 → `killAll()`，逐个 `wait` |

**cwd/env 不继承是个体验损失，必须诚实处理**：同步 `bash` 的工具描述承诺
"Working directory and env persist across commands"（`builtin.cj:88`），而后台任务做不到。
处理方式 = **在工具描述里正面说明差异**，而不是让模型自己撞墙：

> Backend tasks run in a FRESH process: they do NOT share the persistent shell session's
> cwd/env. Pass `cwd` explicitly, or `cd` inside the command. Env vars set by earlier
> `bash` calls (`export X=1`) are NOT visible here.

这条写进 `bash_start` 的 `spec().description`。项目风格一贯如此（"宁可明确失败，不要假装在跑"）。

> 可选增强（列入开放问题 OB2）：`BashSession` 维护一个 `lastCwd` 缓存，每次同步执行后
> 顺带记录会话 `pwd`；`bash_start` 不传 `cwd` 时用它作默认值。代价是多一次 `pwd` 采集。

## 5. 工具契约

三个新工具，全部注册进 `ToolRegistry`（`src/entries.cj` 的四处 registry 组装点同步补齐，
注意 `registry.register(BashTool())` 一共出现 4 次，漏一处就有入口拿不到新工具）。

### 5.1 `bash_start` — 非阻塞派发

```jsonc
{
  "command": "npm install",        // 必填
  "cwd": "/path/to/proj",          // 可选，默认 cjh 进程 cwd
  "timeout": "900",                // 可选，秒，夹 1..3600；默认 background_task_timeout_ms/1000
  "label": "安装依赖"               // 可选，默认取命令前 60 字符
}
```

返回（成功）：

```
task bg-3 started (pid 41287, timeout 900s)
--- 首批输出（≤200ms 抢跑窗口）---
added 12 packages in 1s
--- 用 bash_poll 继续读（bash_poll(task_id: "bg-3")）---
```

- **立即返回**是硬指标：`bash_start` 自身耗时必须 < 500ms（对 `sleep 2` 这类命令也一样），
  这条直接进验收（§12）。
- **抢跑窗口**（≤200ms）：启动后短等一批输出，让"命令不存在 / 语法错 / 立即崩"这类错误
  **当场就暴露**，而不是等模型下一次 poll 才发现。窗口内的输出也算进 `readOffset`。
- **不检查命令是否立即结束**：`sleep 0` / `true` 这类会立刻终态，`bash_start` 仍返回成功 +
  task_id，模型首次 poll 就能看到 `Succeeded`。保持语义单一。

### 5.2 `bash_poll` — 读增量与状态

```jsonc
{
  "task_id": "bg-3",     // 省略 → 返回全部存活任务的状态摘要（不含输出）
  "wait_ms": 5000,       // 可选，0..30000，有限等待：有新输出或终态即返回
  "tail_lines": 50,      // 可选，只回最后 N 行
  "from_start": false    // 可选，游标重置到 0 从头读
}
```

运行中返回：

```
[bg-3] running · 42.3s · 已产出 12.4KB（本次新增 1.2KB）
--- 新增输出 ---
added 12 packages in 1s
```

终态返回：

```
[bg-3] succeeded · 退出码 0 · 用时 48.1s · 共 15.8KB（本次新增 3.4KB）
--- 新增输出 ---
...
```

- **默认非阻塞**；`wait_ms` 给**有限**等待（上限 30000）。**不提供无限等待**——
  "等到跑完"请用同步 `bash`，否则后台就退化成了前台，还多一层嵌套超时。
- `wait_ms` 到点仍无新输出 → 返回 `running` + 空增量 + 一句提示
  （"仍在运行，无新输出；若是交互式程序，后台任务**不提供 stdin**"）。
- **终态可重复 poll**（幂等）：游标到底后只回状态行，不报错。
- 省略 `task_id` 时的摘要形态是**"我还有什么在跑"的一站式查询**，模型收尾前应当用它自检。

### 5.3 `bash_kill` — 终止

```jsonc
{ "task_id": "bg-3" }
```

- 成功：`task bg-3 killed（已回收进程，僵尸已 wait）`
- **幂等**：对已终态任务返回"已处于终态（succeeded），无需 kill"，`is_error=false`（不是错误）。
- 不存在的 id → `is_error=true`。

### 5.4 与同步 `bash` 的分工（最容易被做坏的地方）

**必须**在 `bash_start.spec().description` 里给判定表，否则模型会对每条 `ls` 都开后台，
把简单路径的成本抬高（多一次工具往返 + 一轮上下文）。草案：

```
用 bash_start 当且仅当：
- 预计耗时 > 30s（build / test / install / 长时间下载 / 训练）
- 需要与其它工作真正并行的命令
- "只是让它跑着"，结果稍后再看的命令
否则用 bash（同步）：短命令、要立刻拿结果、要按顺序执行的命令链。

红线：不要对 read/grep/ls/git status 这类快命令用 bash_start —— 多一层轮询只增加成本。
不确定耗时 → 先用 bash 同步跑；超时了再改后台（超时提示里也会指这条路）。
```

反向也要写：同步 `bash` 的超时提示（`builtin.cj:160`）目前引导模型"改成后台执行"，
落地后应改成**点名 `bash_start`**，形成闭环。

### 5.5 失败矩阵

| 情形 | `bash_start` / 工具返回 | 任务状态 |
|---|---|---|
| 槽位满 | `is_error=true` + 存活清单 + 释放提示 | **不创建** |
| `command` 缺参 | `is_error=true` | 不创建 |
| `cwd` 不存在 | `is_error=true`（启动前校验，不浪费进程） | 不创建 |
| 命令本身不存在（`foo: not found`） | `bash_start` **成功** + 抢跑窗口里带出 `not found` | `Failed`（127） |
| 命令立即崩 | `bash_start` 成功，首次 poll 见 `Failed` + exit code | `Failed` |
| 墙钟超时 | poll 见 `Timeout` + 诊断快照（`procSnapshotOf`） | `Timeout`（自动 kill） |
| `bash_kill` | 成功提示 | `Killed` |
| 对终态任务 `bash_kill` | 成功提示"无需 kill"，`is_error=false` | 保持原终态 |
| `bash_poll` 不存在的 id | `is_error=true` | — |
| `bash_poll` 终态且游标到底 | 成功 + 仅状态行 | 保持终态 |

### 5.6 生命周期与归属（评审焦点 **OA**）

三个备选：

| 备选 | 语义 | 取舍 |
|---|---|---|
| **OA-A 回合内**（同方案D 的 OA-A1） | 父回合结束前强制收割/杀掉全部后台任务 | 一致性最好（回合=边界，会话保存无需引用任务）。但**后台 bash 的核心用途就是跨回合的长构建**——回合结束时构建可能还剩 5 分钟，杀掉等于白干 |
| **OA-B 会话内**（推荐） | 任务归**会话**所有，跨回合存活；会话关闭 / 进程退出统一回收 | 长构建能真正跑完，下一回合 `bash_poll` 接着读；语义干净。成本：回合总结条要显示存活任务数 |
| **OA-C 开关** | `background_survive_turn`，默认 true | 多一个配置面，默认值又是大家想要的那个 → 不如不设 |

**推荐 OA-B，且不设开关。** 理由要写清，因为这与方案D 对子代理的选择（OA-A1 回合内）
**故意不一致**，评审时最可能被挑战：

> 子代理与 bash 任务的成本结构不同。
> 子代理**消耗 token、持有对话上下文**，跨回合存活要重做归账、上下文单向流、会话保存边界（方案D §2 红线）；
> bash 任务只占一个 OS 进程，不产生 token、不读父消息，跨回合的成本仅是一张内存表 + 一个日志文件。
> **同一个"边界"原则套在两类任务上，收益与代价不对称**，所以结论不同：
> 子代理回合内（OA-A1），bash 任务会话内（OA-B）。

配套语义：

1. **回合结束**：把存活任务清单 + `task_id` + `bash_poll` 提示注入**回合总结条**，模型下一回合自然接上；
2. **中断**（Ctrl+C / `interruptSession`）：**只打断本轮工具链，不杀后台任务**——
   用户按 Ctrl+C 表达的是"别再说了"，不是"杀掉我刚起的构建"（对齐 `disconnectAction` 那次
   "客户端断开 ≠ 用户要停"的教训，`AGENTS.md` 已记）；
3. **显式终止**：`bash_kill`，或会话关闭 / 进程退出；
4. **待审批请求**：后台任务在 `bash_start` 时刻已审批完（§6.2），运行中不产生新的审批请求，
   所以"中断时立刻拒绝待审批"的既有语义不受影响。

## 6. 与既有机制的交互

### 6.1 V2d DAG 并发引擎

`isReadOnly()` 是 DAG 分组的唯一依据（`src/tools/registry.cj:64`），三个新工具的分类：

| 工具 | `isReadOnly()` | 理由 |
|---|---|---|
| `bash_start` | `false` | 有副作用。但它是**立即返回**的，串行化几乎无耗时——这恰好是设计目标：同批 5 个 `bash_start` 即使串行，总耗时也只有 5 × <500ms，而实际命令并行跑 |
| `bash_poll` | `true` | 只读输出。游标推进需要 `BackgroundTask` 内部锁保护（两个并发 poll 串行化游标，最坏情况是重复交付同一段，不损坏数据） |
| `bash_kill` | `false` | 有副作用 |

**收益正好落在旧模型的痛点**：老模型下 5 个长构建要 5 次同步阻塞（5 × 超时）；
新模型下 5 个 `bash_start` 在 DAG 里快速串完 → 命令真并行 → 一次 `bash_poll` 收全部。

### 6.2 capability 审批（**红线**，不新开权限面）

后台执行是"延迟执行的 bash"。如果审批不在 `bash_start` 时做，就等于**绕过审批**——
命令内容在启动时完全已知，所以审批必须发生在**启动时刻**，运行中不再审批。

关键是**不给存量严格模式用户增加断裂**：`libs/cjcfg` 的 `capability.tools` 是按工具名登记的
（默认宽松，`enabled: true` 才严格）。若把 `bash_start` 做成独立工具名，所有
`tools: ["bash", "read_file", ...]` 的严格模式用户会突然被拒——这正是历史上
"用户配了 capability 段后 bash 被拒"的同类投诉。

**决定：三个新工具在权限判定上全部映射到 `bash` 这一个授权面。**

```
toolPermNeeded("bash_start" | "bash_poll" | "bash_kill") → "bash"
commands 白名单校验 → 对 bash_start 的 command 参数照旧执行（与同步 bash 同一套规则）
```

- 这样 `bash` 被允许 ⇔ 后台任务被允许；`bash` 被拒 ⇔ `bash_poll` 也读不到任何输出（不会泄漏）；
- **`capability_test.cj` 必须同批更新**（`AGENTS.md` 硬性要求：改安全/权限语义必须同批改该测试），
  补三例：严格模式只授 `bash` → `bash_start` 通过；不授 `bash` → `bash_start` 拒绝且
  `bash_poll` 不可读；`commands` 白名单拦住后台命令时 `bash_start` 拒绝且**不创建任务**（不占槽）。

### 6.3 中断传播

| 触发 | 行为 |
|---|---|
| Ctrl+C / `interruptSession` / WS `cancel` | **只打断本轮工具链**；后台任务继续跑（§5.6 决定 2） |
| `bash_kill` | 终止指定任务 + `wait` 回收 |
| 会话关闭 / 进程退出 | `killAll()` 逐个 terminate + wait |
| 任务墙钟超时 | 自动 terminate + wait，状态置 `Timeout`，输出尾部带 `procSnapshotOf` 诊断快照 |

**为什么中断不杀后台任务**：`AGENTS.md` 已记过一次同类误判——「客户端断开」曾被当成
「用户要停」，把无人值守的长任务整轮作废。把 Ctrl+C 解释成"杀掉我刚起的 30 分钟构建"
是同一个错误的另一面。要杀有 `bash_kill`，语义显式。

### 6.5 与方案 D 异步子代理的合并（评审焦点 **OB**）

`docs/异步子代理与进阶能力-方案D.md` §4 已经设计了 `task(async=true)` + `task_wait` + `task_status`。
本文的任务表与它**是同一个东西**，只是 kind 不同。合并方式：

| 本文（bash 任务） | 方案D（子代理） | 合并后 |
|---|---|---|
| `BackgroundTask.kind = "bash"` | `AgentNode` | 统一为 `kind = "bash" / "subagent"` |
| `killer: () -> Unit` 回调 | 中断传播给子代理 | 同一个 `killer` 槽位，注册时注入 |

| `readOffset` 游标 | 子代理无输出流，只有"当前工具" | 子代理 task 的 poll 回 `currentTool` + 已有结果摘要 |

`task_start`（`bash_start` 广义化）/ `task_poll` / `task_kill`。

**但本文一期不改名**（见 §10 分期）：一期只落 `bash_*` 三个名字，避免一次动太多；
二期接子代理时再评估是否统一命名。**接口形状为此预留**：`BackgroundTask.kind` +
`killer` 回调已解耦，改名的成本只在工具层（`spec().name` + 注册点），不触及任务表。

| **B-2** | TUI 面板行 + Web `bg_task` 帧 + 协议 v6 + 回合总结条存活提示 | 中 |
| **B-3** | 与方案D 合并：子代理注册进同一张表（`kind="subagent"`），工具面命名统一评估 | 中（依赖 D-A） |

B-1 是自包含可交付的最小完整件；B-2 是可观测性补齐；B-3 必须等方案D 的 D-A 落地。

> **命名一致性提醒**：本文一期固定用 `bash_*` 三个名字（模型对 `bash_start/poll/kill`
> 的既有认知最通用，且和同步 `bash` 形成直观对照）。二期若合并为 `task_*`，属于
> 兼容性破坏改动，需要做别名过渡——那时再评估，不要现在提前抽象。

## 11. 开放问题（请评审拍板）

1. **OA（生命周期归属）**：推荐 OA-B（会话内，跨回合存活，不设开关）。理由见 §5.6——
   bash 任务与子代理的成本结构不同，不该套同一个"回合边界"。
   **这是本文与方案D 故意不一致的一处**，请确认。
2. **OB（与方案D 合并方式）**：一期固定 `bash_*` 命名、二期再统一为 `task_*`？
   还是现在就一步到位用 `task_start/poll/kill`（代价：一期文档/测试/提示词都要按终态命名写）？
3. **OB2（cwd 默认值）**：`bash_start` 不传 `cwd` 时，用 cjh 进程 cwd（简单、可预测），
   还是让 `BashSession` 缓存会话 `pwd` 作默认（体验更连贯，多一次采集）？
4. **进程树 kill 的深度**：Linux 下用 `setsid` + `kill(-pgid)` 一次到位（需要确认仓颉
   `launch` 是否支持设进程组），还是终止顶层 + 快照比对兜底（简单，可能残留）？**实现前需查证**。
5. **输出落盘位置**：会话目录 vs 系统临时目录。前者可回看、跟着会话走；后者不污染用户家目录。
6. **是否要"后台任务总数"进总结条**：会影响 `--mock` 端到端与 pty 场景的期望输出，需同批改。
