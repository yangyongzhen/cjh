32. **TUI truncate CSI off-by-one 致 status bar 宽度塌缩**（2026-08-23，隐藏极深）：
    - 现象：177 列终端，状态栏右侧填充线 `------` 只渲染十几列就截断，
      `displayWidth(sb)=176`（正确）但 `canvas.truncate(sb, cols)` 输出可见宽度 `truncW=81`
      —— 两个宽度函数对同一字符串算出 95 列差
    - 根因：`TuiCanvas.truncate()` 处理 `ESC[` CSI 序列时，进入 while 循环前
      **没有先消费 `[` 字节**。`[` = 0x5B 正好落在终结字母区间 `0x40..0x7E`，
      第一次循环就把 `[` 误判为终结符并 break → CSI 参数和真正终结字母（`m`）
      残留流中，被后续主循环当作可见字符计入宽度，可见宽度反而偏小
    - 对照：`displayWidth()` 的 CSI 处理是对的（先 `i += 1` 跳过 `[`），
      两个函数对 `[` 的处理不一致是 bug 温床
    - 修复（libs/cjterm/src/component.cj）：CSI 分支先 `sb.append('['); i += 1`
      再进参数/终结字母循环，与 `displayWidth()` 严格对齐
    - 教训：**两个等价宽度函数（displayWidth / truncate）必须共享同一段
      ANSI 解析逻辑**，否则一处改了一处忘改，差一个字节就是几十列误差。
      排查时同时打两个函数的宽度日志，对比同一字符串的输出，差异点即 bug
    - 附带清理：删除 component.cj 的 `diagLog` 函数和 3 处诊断埋点；
      statusbar.cj 删除临时 `_renderReal()` / `getHomeStr()` / 诊断行 /
      `import std.fs.*`；状态栏改 ASCII 边框（`+-- ... ->`、`# ` 模型前缀、
      `[ cwd ]` 目录段）规避 emoji/box-drawing 宽度歧义
