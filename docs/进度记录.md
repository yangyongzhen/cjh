### 本次会话（2026-08-26，第九轮）完成事项
> 主题：V3 信任链 Step 2（SM2 签名验证）

**背景**：原方案 Ed25519，调研发现仓颉 `stdx.crypto.keys` 只有 RSA/ECDSA/SM2，无 Ed25519 原生支持。调外部 openssl CLI 破坏单文件自包含原则，被否决。改用 SM2（国密标准，仓颉原生支持，签名 64 字节与 Ed25519 一致）。

**1. SM2 验签实现**（`libs/cjutil/src/sm2.cj`）

- `Sm2VerifyResult` 枚举：Verified / Invalid / BadKey / BadSignature / Error
- `verifySm2(pubkeyHex, signatureHex, checksum)` 函数：
  - pubkey hex → `DerBlob` → `SM2PublicKey.decodeDer` 重建公钥
  - signature hex → `Array<Byte>`（DER 编码的签名）
  - checksum → `hexToBytes`（被签名的数据）
  - `SM2PublicKey.verify(dataBytes, signatureBytes)` 验签
- `signSm2(privateKey, data)` 函数：用于发布工具签名
- import：`stdx.crypto.keys.*` + `stdx.crypto.x509.DerBlob`

**2. loadPlugin 集成 SM2 验签**（`src/tools/plugin.cj`）

- 替换"V3 Step 2 预留：仅解析记录"为真正的 SM2 验签逻辑
- 三字段齐全（pubkey + signature + checksum）时强制验签：
  - `verifySm2(pubkeyHex, signatureHex, expectedChecksum)` 返回 `Verified` → 通过
  - 返回 `Invalid` / `BadKey` / `BadSignature` / `Error` → Log.warn + 拒绝加载
- 部分字段存在但不全 → Log.warn "签名字段不完整"，跳过验签（兼容过渡）

**3. 文档更新**（`docs/插件签名与贡献指南.md`）

- 2.3 签名字段：Ed25519（64 字节固定）→ SM2（DER 编码，变长）
- 4.3 生成密钥对：openssl/Python → 仓颉原生 `SM2PrivateKey()` / `SM2PublicKey(privateKey)`
- 4.4 签名：openssl pkeyutl → `SM2PrivateKey.sign(hexToBytes(checksum))`
- 4.6 完整发布流程：bash+openssl+python 脚本 → 仓颉原生 `publish.cj` 程序
- 5.1 验证流程：合并 Step 1 + Step 2，标注"当前已实现"
- 5.2 信任管理 CLI：标注"V3 Step 3 将实现"

**4. 方案决策记录**

- **签名算法选型**：SM2（仓颉原生）> Ed25519（无原生支持）> RSA（签名过长）
- **零外部依赖原则**：信任链核心逻辑不外包给 openssl/Python，全部用仓颉原生 API
- **兼容过渡策略**：部分签名字段存在但不全时，记录警告但不拒绝加载，平滑迁移
- **DER 编码选择**：SM2 公钥/签名用 DER 编码（`encodeToDer` / `sign` 自动生成），而非 Raw 字节，符合 X.509 标准

**验证**：`cjpm build success`；SM2 验签 API 用法正确（`SM2PublicKey.verify(data, sig): Bool`，SM3 摘要内置）

- **DAG 依赖分析**（`extractResourceAccess` + `buildDependencyGraph`）：
  - 从 `ToolCall` 提取资源访问 `(path, isWrite)`
  - 资源识别规则：`read_file`/`grep`/`list_dir` → path, read；`write_file`/`append_file`/`edit_file` → path, write；`bash` → command, write；其他 → "", write（保守）
  - 依赖规则：同一 path 且至少一个 isWrite → 串行依赖边；不同 path → 可并发（即使都是 write）；bash 的 command 当 path 处理（不同 bash 命令可并发）
- **拓扑分组调度**（`topologicalGroups`）：
  - 按依赖关系分组：同一组的工具调用可并发执行；下一组必须等当前组全部完成
  - 组内顺序保持 LLM 原始顺序（结果回填顺序）
  - 单元素组直接串行执行（避免 spawn 开销）；多元素组 spawn 并发
- **Provider 连接预热**（`OpenAiProvider.warmup`）：

  - 首次 `chatStream` 不再付 TLS 冷启动开销
  - 预热失败静默（预热是优化，不是必需）
- **性能基线测量**（`RunSummary` 新增 3 字段）：
  - `parallelBatches`：并发执行的批次数
  - `parallelSavedMs`：并发相比串行节省的毫秒数（`假设串行总耗时 - 并发实际耗时`）
  - `maxParallelism`：最大并发度（单组最多工具数）
  - spawn 分支记录每个工具的实际耗时，累加得假设串行耗时，对比并发实际耗时计算节省

### 设计决策记录

- **DAG 依赖分析粒度**：文件资源级别（path + isWrite），不是工具级别。两个 `write_file` 操作不同文件可并发，操作同一文件串行

### 本次会话（2026-08-25，第五轮）完成事项
> 主题：修复长 completions 场景下 token 统计为 0 的问题 + SSE 空闲超时

**问题现象**：生成 H5 游戏等长任务时，状态行一直显示 `↑ 0 tokens`，且偶发 `IllegalArgumentException: Invalid utf8 byte sequence`。

**根因定位**（通过加调试日志 + 真实长任务复现）：

1. **`readTimeout(60s)` 超时切断 SSE 流**（`openai.cj`）
   - DeepSeek 长 completions 60 秒后触发 `HttpTimeoutException: Read body timeout`
   - 异常被 `SseParser.run()` 的 catch 捕获 → `onError` → **带数值的最后一帧 usage 丢失** → token=0

2. **`usage: null` 帧不更新 token**（预期行为，非 bug）
   - DeepSeek 流式响应每一帧都带 `usage` 字段，但绝大多数是 `null`（`JsonKind.JsNull`）
   - 只有最后一帧（`stream_options.include_usage=true`）的 `usage` 才是 `JsObject` 且带数值
   - `match (u.kind())` 落到 `case _ => ()`，token 不更新——这是正确的

**修复**：

1. **SSE 空闲超时机制**（`sse.cj` + `openai.cj` + `message.cj` + `loop.cj`）
   - `readTimeout(60s)` 是**每次 read 的空闲超时**（非绝对超时），实测长任务 chunk 持续到达不会触发
   - `SseParser` 新增 `timedOut: Bool` 标志 + `HttpTimeoutException` 专用 catch
   - timeout 时 `flushRemaining()` 保留已收数据 + `onDone` + 标记 `timedOut`
   - `ModelResponse` 新增 `timedOut: Bool` 字段
   - `OpenAiProvider` 把 `parser.timedOut` 传到 `ModelResponse`
   - `agent/loop.cj` 检查 `response.timedOut`，给用户显示提示 + 给 LLM 注入 `[System Notice]`

2. **`StreamAccumulator.feed` usage 解析健壮性**（`provider.cj`）
   - 原来只处理 `JsInt`，遇到 `JsFloat`/`JsString` 会静默丢弃 token 用量
   - 新增 `extractNum` 闭包：统一支持 `JsInt`/`JsFloat`/`JsString` 三种形态
   - `prompt_tokens`/`completion_tokens`/`prompt_cache_hit_tokens`/`cache_read_input_tokens` 全部走 `extractNum`
   - 注意：仓颉 `stdx.encoding.json.JsonKind` 只有 7 个成员（`JsObject`/`JsArray`/`JsInt`/`JsFloat`/`JsString`/`JsBool`/`JsNull`），**没有 `JsInt64`**；`JsonValue` 也没有 `asInt64()`。`JsonInt.getValue()` 本就返回 `Int64`，已覆盖整数场景

3. **`resetAgentTimer` 每轮重置计时**（`main.cj`/`app.cj`）
   - `onThinking` 回调里调 `tui.resetAgentTimer()`，让 Agent 状态行耗时从每轮开始计算

**验证**：
- 编译通过（`cjpm build success`）
- 短任务（1+1=）：1.3s · 2.2K tokens · 99% cached，正常
- 真实长任务（生成 H5 我的世界游戏）：10 rounds · 10 tools · 112.9s · 133K tokens · 99% cached
- token 持续累加：`54888 → 69307 → 85071 → 101811 → 118751`
- **无 timeout、无 error** —— `readTimeout(60s)` 空闲超时没有误切断长任务
- usage 解析单元测试：JsInt/JsFloat/JsString 三种形态 15/15 全过

### 设计决策记录
- **`readTimeout` 语义**：文档说「读取一个响应的最大时长」，但实测是**每次 read 的空闲超时**。长任务 chunk 持续到达，60s 空闲超时不会触发；网络卡住 60s 无新数据才断
- **三个 Provider 的覆盖情况**：
  - OpenAI/DeepSeek/通义/Moonshot：✅ 用 `SseParser`，`readTimeout(60s)` 空闲超时生效
  - Ollama：✅ 复用 `SseParser`，`sse.cj` 的 timeout catch 对它生效（Ollama 没设 readTimeout，走默认）
  - Anthropic：✅ 复用 `SseParser`，同上（Anthropic 也没设 readTimeout）
- **Ollama/Anthropic 不显式设 readTimeout**：它们原本没设，走默认无超时。这次改动只修了 OpenAI 路径，Ollama/Anthropic 的 `SseParser` timeout catch 是「保险绳」而非「日常路径」

    - 现象：177 列终端，状态栏右侧填充线 `------` 只渲染十几列就截断，

    - 对照：`displayWidth()` 的 CSI 处理是对的（先 `i += 1` 跳过 `[`），
      两个函数对 `[` 的处理不一致是 bug 温床
    - 修复（libs/cjterm/src/component.cj）：CSI 分支先 `sb.append('['); i += 1`

    - 附带清理：删除 component.cj 的 `diagLog` 函数和 3 处诊断埋点；

      `HashlineEditParser`（patch 文本 → PatchOp 列表）+

      `HashlineHash`（FNV-1a 哈希 + locate 行匹配）+
      `ArrayListOps`（仓颉 ArrayList 无 insert/removeAt，手动构造新列表）。
    - **注册到 4 处 ToolRegistry**：verifyTests/cli/json/tui 四处都 register HashlineEditTool。
    - **效率收益**（omp 实测基准）：编辑成功率 6.7%→68.3%（10× 提升），
