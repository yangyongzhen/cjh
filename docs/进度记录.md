### 本次会话（2026-08-25，第五轮）完成事项
> 主题：修复长 completions 场景下 token 统计为 0 的问题 + SSE 空闲超时

**问题现象**：生成 H5 游戏等长任务时，状态行一直显示 `↑ 0 tokens`，且偶发 `IllegalArgumentException: Invalid utf8 byte sequence`。

**根因定位**（通过加调试日志 + 真实长任务复现）：

1. **`readTimeout(60s)` 超时切断 SSE 流**（`openai.cj`）
   - DeepSeek 长 completions 60 秒后触发 `HttpTimeoutException: Read body timeout`
   - 异常被 `SseParser.run()` 的 catch 捕获 → `onError` → **带数值的最后一帧 usage 丢失** → token=0

2. **`usage: null` 帧不更新 token**（预期行为，非 bug）
   - DeepSeek 流式响应每一帧都带 `usage` 字段，但绝大多数是 `null`（`JsonKind.JsNull`）
   - 只有最后一帧（`stream_options.include_usage=true`）的 `usage` 才是 `JsObject` 且带数值
   - `match (u.kind())` 落到 `case _ => ()`，token 不更新——这是正确的

**修复**：

1. **SSE 空闲超时机制**（`sse.cj` + `openai.cj` + `message.cj` + `loop.cj`）
   - `readTimeout(60s)` 是**每次 read 的空闲超时**（非绝对超时），实测长任务 chunk 持续到达不会触发
   - `SseParser` 新增 `timedOut: Bool` 标志 + `HttpTimeoutException` 专用 catch
   - timeout 时 `flushRemaining()` 保留已收数据 + `onDone` + 标记 `timedOut`
   - `ModelResponse` 新增 `timedOut: Bool` 字段
   - `OpenAiProvider` 把 `parser.timedOut` 传到 `ModelResponse`
   - `agent/loop.cj` 检查 `response.timedOut`，给用户显示提示 + 给 LLM 注入 `[System Notice]`

2. **`StreamAccumulator.feed` usage 解析健壮性**（`provider.cj`）
   - 原来只处理 `JsInt`，遇到 `JsFloat`/`JsString` 会静默丢弃 token 用量
   - 新增 `extractNum` 闭包：统一支持 `JsInt`/`JsFloat`/`JsString` 三种形态
   - `prompt_tokens`/`completion_tokens`/`prompt_cache_hit_tokens`/`cache_read_input_tokens` 全部走 `extractNum`
   - 注意：仓颉 `stdx.encoding.json.JsonKind` 只有 7 个成员（`JsObject`/`JsArray`/`JsInt`/`JsFloat`/`JsString`/`JsBool`/`JsNull`），**没有 `JsInt64`**；`JsonValue` 也没有 `asInt64()`。`JsonInt.getValue()` 本就返回 `Int64`，已覆盖整数场景

3. **`resetAgentTimer` 每轮重置计时**（`main.cj`/`app.cj`）
   - `onThinking` 回调里调 `tui.resetAgentTimer()`，让 Agent 状态行耗时从每轮开始计算

32. **TUI truncate CSI off-by-one 致 status bar 宽度塌缩**（2026-08-23，隐藏极深）：
    - 现象：177 列终端，状态栏右侧填充线 `------` 只渲染十几列就截断，
      `displayWidth(sb)=176`（正确）但 `canvas.truncate(sb, cols)` 输出可见宽度 `truncW=81`
      —— 两个宽度函数对同一字符串算出 95 列差
    - 根因：`TuiCanvas.truncate()` 处理 `ESC[` CSI 序列时，进入 while 循环前
      **没有先消费 `[` 字节**。`[` = 0x5B 正好落在终结字母区间 `0x40..0x7E`，
      第一次循环就把 `[` 误判为终结符并 break → CSI 参数和真正终结字母（`m`）
      残留流中，被后续主循环当作可见字符计入宽度，可见宽度反而偏小
    - 对照：`displayWidth()` 的 CSI 处理是对的（先 `i += 1` 跳过 `[`），
      两个函数对 `[` 的处理不一致是 bug 温床
    - 修复（libs/cjterm/src/component.cj）：CSI 分支先 `sb.append('['); i += 1`
      再进参数/终结字母循环，与 `displayWidth()` 严格对齐
    - 教训：**两个等价宽度函数（displayWidth / truncate）必须共享同一段
      ANSI 解析逻辑**，否则一处改了一处忘改，差一个字节就是几十列误差。
      排查时同时打两个函数的宽度日志，对比同一字符串的输出，差异点即 bug
    - 附带清理：删除 component.cj 的 `diagLog` 函数和 3 处诊断埋点；
      statusbar.cj 删除临时 `_renderReal()` / `getHomeStr()` / 诊断行 /
      `import std.fs.*`；状态栏改 ASCII 边框（`+-- ... ->`、`# ` 模型前缀、
      `[ cwd ]` 目录段）规避 emoji/box-drawing 宽度歧义
