## 一、对比结论（源码实证）

### omp 快的构成（按对体感贡献排序）

1. **单轮工具并行**：`agent-loop.ts:2718-2729`，一轮多 tool_calls 用 `Promise.allSettled` 批量并发（shared 并发 / exclusive 串行）。
2. **工具执行引擎**：ripgrep/brush 等 58 个 builtin 为 **Rust in-process**（N-API，零 fork/exec），grep 大仓达 C 级速度。
3. **非关键路径异步化**：compaction、会话标题、commit message 用 smol/tiny 小模型**后台跑**，不阻塞主循环。
4. **LLM 连接 keepalive 池化**（Node undici 默认复用）。
5. **thinking 可调**：thinking level 可配 off/low/high，快模型不背推理开销。

### cjh 已有、不输的

- **并行**：V2d 并发引擎（`src/agent/loop.cj:694-770`）DAG 依赖分析（同 path 写冲突检测）+ 拓扑分组，组内 spawn 并发、组间串行，含并发节省统计——**比 omp 的 shared/exclusive 二分更细，无需优化**。
- **连接复用**：`libs/cjllm/src/openai.cj` pooledTransport（takePooled/putPooled，L111-144）跨轮复用 TCP+TLS。
- **grep/glob 不 fork rg**：仓颉原生实现（显式递归 `Directory.walk`，`glob.cj:142`；`builtin.cj:704` GrepTool）。

### 真实差距（cjh 相对 omp）

| # | 维度 | omp | cjh | 定性 |
|---|---|---|---|---|
| G1 | grep/glob 速度 | Rust in-process（ripgrep 级） | 仓颉 JIT+GC 单线程逐文件 walk+正则 | **最大体感差距**，中大型仓 10-100×，每轮 grep 都慢 |
| G2 | compaction | 后台异步不占主循环 | 主循环内同步（8000 token 阈值，`loop.cj:1001` 串行等 summaryProvider） | 长会话一次 compaction 卡一轮 |
| G3 | thinking 控制 | 7 层 model role + thinking level | 未暴露 reasoning_effort/thinking | 高推理模型每轮 reasoning token 拖慢且关不掉 |
| G4 | 渲染 | ink/React 差分 | `renderInner` 每帧 canvas.begin 全量重绘，流式逐帧 O(总长) | 大输出帧开销 + 主协程同线程竞争 |
| G5 | 连接池深度 | undici 多连接 | 单槽 pooledTransport（1 条） | 小，主/摘要 provider 交替时撞串行 |
| — | 并行度/DAG | 二分 | DAG path 冲突 | **cjh 领先**，不动 |

> 注：单任务端到端大头仍是 LLM 调用本身（网络往返+token 生成），两家同命；omp 的快 = 把可控开销压到近零。

## 二、分期计划

### P0：grep/glob 文件枚举快速路径（G1）——find 枚举 + 原生渲染

> **设计修正（已实证）**：初稿计划"fork rg / fd 解析输出"，实测发现 `rg --files` 跳过
> symlink、`fd` 对 symlink 处理不同，均与原生 `Directory.walk` 的枚举**不字节一致**
> （symlink 语义 + readdir 顺序）。故改为 **find 只枚举、cjh 原生渲染**。

- **做法**：GrepTool/GlobTool 的目录搜索先走快速路径——`find base \( -type f -o -type l \) -printf '%P\0'`
  一次 C 级枚举全部 常规文件+符号链接（原生 readdir 同序），**重建精确原生 `fi.path`**
  = `FileInfo(base).path + "/" + findRel`，再走**未改动的原生** 过滤 / 正则匹配 / 渲染
  （grep=`GrepTool.grepSearchFile`，glob=`considerGlobFile`）⇒ 输出字节级一致（parity by
  construction，彻底避免 rg/fd 与 std.regex 在行尾/\r/多字节/上下文渲染上的分歧）。
  find 不存在 / fork 异常 / 退出码非 0 / base 非目录 ⇒ 回退原生递归（行为与现状一致）。
  开关：`CJH_DISABLE_FIND_FASTPATH=1` 强制原生（排障/基准对比）。
- **为何 find（而非 rg/fd）**：`-type f -o -type l`（不 follow）与原生 `FileInfo.isDirectory()`
  一致——symlink 当文件列出、不递归 symlink 目录；find 无排序的 readdir 预序 == 原生显式
  递归 DFS 顺序。
- **关键等价性（已实测）**：`fi.path` 重建对 `./`、`//`、尾 `/`、绝对/相对 base 全部成立（含
  双斜杠 quirk）；忽略目录"跳过不递归" ⇔ find 平铺列表按"任一路径组件命中忽略规则"后置过滤。
- **实现**：`src/tools/search_common.cj`（`enumerateFilesWithFind` + 组件过滤 + 共享忽略目录
  常量 GREP/GLOB_IGNORED_DIRS）；快速路径 `builtin.cj` `GrepTool.searchDirectoryFast`、
  `glob.cj` `walkTreeFast`（均回退原生）。
- **验收**：`fastpath_parity_test.cj` 7 个字节级对等用例（grep/glob fast==native、symlink 文件
  计入且 symlink 目录不递归、悬空 symlink 安全、隐藏/忽略目录过滤、basePath 尾 `/`/`//` 形态、
  非目录 base 回退原生错误）；全量 297 用例不回归 + `cjpm build` + `--mock` 通过。

### P1a：暴露 reasoning_effort + max_tokens 配置（G3）

- **做法**：settings.json 增加 `reasoning_effort`（off/low/medium/high，缺省=不发该参数维持现状）与 `max_tokens`（已有 16384 默认，显式可配）；`src/cfg`（配置包）读入 → `openai.cj`/`anthropic.cj` 请求体穿透。
- **边界**：未知值忽略（不报错）；OpenAI 与 Anthropic 的字段名不同（reasoning_effort vs thinking budget），按 provider 各自映射，不支持的 provider 静默忽略。
- **验收**：单测断言请求体字段；缺省行为与现状字节级一致。

### P1b：compaction 后台异步化（G2）

- **做法**：主循环每轮结束检查 token 阈值（真实 `lastPromptTokens`）；达到 **70% 阈值**即后台 `spawn` 摘要（不阻塞）；下一轮开始前若已完成则换装 messages，未完成顺延（当前轮照常跑）。摘要用既有 summaryProvider（无则主 provider）。
- **竞态**：messages 换装需与主循环单线程协调（spawn 只读快照生成摘要，主线程独占写 messages）；摘要失败静默重试一次，再失败退回同步路径（行为降级不崩）。
- **验收**：mock 驱动单测：阈值触发→下轮应用；未完成顺延；失败回退同步；未达阈值不触发。

### P2（后续轮次）：renderInner 差分渲染（G4）

- 只重绘变化行（记录上帧行数/内容哈希），流式 append 只画增量；大输出帧开销 O(增量) 而非 O(总量)。
- 风险：TUI 核心路径，需 PTY 15 场景全回归 + 差分正确性专项用例。
