## 一、对比结论（源码实证）

### omp 快的构成（按对体感贡献排序）

1. **单轮工具并行**：`agent-loop.ts:2718-2729`，一轮多 tool_calls 用 `Promise.allSettled` 批量并发（shared 并发 / exclusive 串行）。
2. **工具执行引擎**：ripgrep/brush 等 58 个 builtin 为 **Rust in-process**（N-API，零 fork/exec），grep 大仓达 C 级速度。
3. **非关键路径异步化**：compaction、会话标题、commit message 用 smol/tiny 小模型**后台跑**，不阻塞主循环。
4. **LLM 连接 keepalive 池化**（Node undici 默认复用）。
5. **thinking 可调**：thinking level 可配 off/low/high，快模型不背推理开销。

### cjh 已有、不输的

- **并行**：V2d 并发引擎（`src/agent/loop.cj:694-770`）DAG 依赖分析（同 path 写冲突检测）+ 拓扑分组，组内 spawn 并发、组间串行，含并发节省统计——**比 omp 的 shared/exclusive 二分更细，无需优化**。
- **连接复用**：`libs/cjllm/src/openai.cj` pooledTransport（takePooled/putPooled，L111-144）跨轮复用 TCP+TLS。
- **grep/glob 不 fork rg**：仓颉原生实现（显式递归 `Directory.walk`，`glob.cj:142`；`builtin.cj:704` GrepTool）。

### 真实差距（cjh 相对 omp）

| # | 维度 | omp | cjh | 定性 |
|---|---|---|---|---|
| G1 | grep/glob 速度 | Rust in-process（ripgrep 级） | 仓颉 JIT+GC 单线程逐文件 walk+正则 | **最大体感差距**，中大型仓 10-100×，每轮 grep 都慢 |
| G2 | compaction | 后台异步不占主循环 | 主循环内同步（8000 token 阈值，`loop.cj:1001` 串行等 summaryProvider） | 长会话一次 compaction 卡一轮 |
| G3 | thinking 控制 | 7 层 model role + thinking level | 未暴露 reasoning_effort/thinking | 高推理模型每轮 reasoning token 拖慢且关不掉 |
| G4 | 渲染 | ink/React 差分 | `renderInner` 每帧 canvas.begin 全量重绘，流式逐帧 O(总长) | 大输出帧开销 + 主协程同线程竞争 |
| G5 | 连接池深度 | undici 多连接 | 单槽 pooledTransport（1 条） | 小，主/摘要 provider 交替时撞串行 |
| — | 并行度/DAG | 二分 | DAG path 冲突 | **cjh 领先**，不动 |

> 注：单任务端到端大头仍是 LLM 调用本身（网络往返+token 生成），两家同命；omp 的快 = 把可控开销压到近零。

## 二、分期计划

### P0：grep/glob 文件枚举快速路径（G1）——find 枚举 + 原生渲染

> **设计修正（已实证）**：初稿计划"fork rg / fd 解析输出"，实测发现 `rg --files` 跳过
> symlink、`fd` 对 symlink 处理不同，均与原生 `Directory.walk` 的枚举**不字节一致**
> （symlink 语义 + readdir 顺序）。故改为 **find 只枚举、cjh 原生渲染**。

- **做法**：GrepTool/GlobTool 的目录搜索先走快速路径——`find base \( -type f -o -type l \) -printf '%P\0'`
  一次 C 级枚举全部 常规文件+符号链接（原生 readdir 同序），**重建精确原生 `fi.path`**
  = `FileInfo(base).path + "/" + findRel`，再走**未改动的原生** 过滤 / 正则匹配 / 渲染
  （grep=`GrepTool.grepSearchFile`，glob=`considerGlobFile`）⇒ 输出字节级一致（parity by
  construction，彻底避免 rg/fd 与 std.regex 在行尾/\r/多字节/上下文渲染上的分歧）。
  find 不存在 / fork 异常 / 退出码非 0 / base 非目录 ⇒ 回退原生递归（行为与现状一致）。
  开关：`CJH_DISABLE_FIND_FASTPATH=1` 强制原生（排障/基准对比）。
- **为何 find（而非 rg/fd）**：`-type f -o -type l`（不 follow）与原生 `FileInfo.isDirectory()`
  一致——symlink 当文件列出、不递归 symlink 目录；find 无排序的 readdir 预序 == 原生显式
  递归 DFS 顺序。
- **关键等价性（已实测）**：`fi.path` 重建对 `./`、`//`、尾 `/`、绝对/相对 base 全部成立（含
  双斜杠 quirk）；忽略目录"跳过不递归" ⇔ find 平铺列表按"任一路径组件命中忽略规则"后置过滤。
- **实现**：`src/tools/search_common.cj`（`enumerateFilesWithFind` + 组件过滤 + 共享忽略目录
  常量 GREP/GLOB_IGNORED_DIRS）；快速路径 `builtin.cj` `GrepTool.searchDirectoryFast`、
  `glob.cj` `walkTreeFast`（均回退原生）。
- **验收**：`fastpath_parity_test.cj` 7 个字节级对等用例（grep/glob fast==native、symlink 文件
  计入且 symlink 目录不递归、悬空 symlink 安全、隐藏/忽略目录过滤、basePath 尾 `/`/`//` 形态、
  非目录 base 回退原生错误）；全量 297 用例不回归 + `cjpm build` + `--mock` 通过。

### P1a：暴露 reasoning_effort + max_tokens 配置（G3）

### P1b：compaction 后台异步化（G2）

- **做法**：主循环每轮末用真实 `lastPromptTokens` 判 `compactionOverThreshold()`（双阈值，与同步路径共用）；超限且无 pending 即后台 `spawn` 摘要（`compactLock` 守护读 messages 快照、spawn 持独立拷贝，不阻塞）；下一轮 LLM 请求前 `Future.tryGet()` 非阻塞检查——完成则换装 messages（system+摘要+工具链+最近 keep 条，主线程独占写持锁、`lastPromptTokens=0` 抑 churn）、未完成顺延。摘要用既有 summaryProvider（无则主 provider）。
- **竞态**：messages 快照读/换装写用 `compactLock` 串行（手动 `/compact` 在独立线程调用，共享此锁防竞态）；摘要失败 spawn 内静默重试一次，再失败置 `SyncFallback` 回退同步压缩（行为降级不崩）。
- **决策**：不做设计稿的"70% 提前触发"——核心收益在"后台不阻塞"而非提前量；提前量会引入快照/当前历史摘要重叠且每轮超 70% 反复 spawn。严格超阈值 + 换装后清零 token 更干净。
- **验收**：scripted provider 驱动单测（递减 usage 防 churn + release-gate 确定性时序）：阈值触发→下轮应用；未完成顺延；失败回退同步；未达阈值不触发；手动路径不回归。

### P2：OutputView 增量行缓存（G4）—— 设计（2026-09-05）

**纠正旧表述**："renderInner 每帧 canvas.begin 全量重绘"已过时——`TuiCanvas.flush()` 已按 `prevLines` 逐行差分（写到终端的字节已是增量，`component.cj:125-142`）。当前真正的 O(总量) 热点是 `OutputView.render()`（`outputview.cj:207`）：每帧对**整个累积缓冲**做 `output.toString().split("\n", -1)` 再取可见窗口——不管本帧变了多少，CPU 成本随会话总长线性涨，且整段持 `outputLock` 进行，直接卡主循环（输入响应 / spinner / resize）。

**设计：OutputView 内部增量行缓存（非视觉变更，渲染输出逐位一致）**
- `OutputView` 增 `private var lineCache: ArrayList<String>`，语义恒等于 `output.toString().split("\n", -1)`
- 三条 mutate output 的路径**增量维护** lineCache（render 不再计算）：
  - `append(text)`：拆 text 自身。无 `\n` → 拼到最后一行；含 `\n` → 末行 += 首段、中间段逐段 add；以 `\n` 结尾 → 末尾补空行（对齐 split -1 尾空串）；以 `\n` 开头 → 首段为空（末行不变）
  - `endStream`（思考段替换）：定位思考段起始行移除，finished text 逐段 add 回（finished 可能含 `\n`）
  - `setThinking` / `save()`（旧缓冲换出）/ resize：置 lineCache 失效（低频路径），下次 render 全量重建
- `render()`：缓存有效 → 直接用 lineCache 算可见窗口（`startIdx = size - height - scrollOffset`）；失效 → 全量重建再算。**取行 / 滚动 / 高度 / 滚动锁定语义一律不动**——纯性能优化
- 复杂度：流式 append 从 O(总量) 降到 O(本帧新增文本)；canvas 行级差分不变
- **不变式（测试锁死）**：lineCache 与 `output.toString().split("\n", -1)` 逐位等价，尤其"尾空串"（结尾 `\n`）与"首空串"（开头 `\n`）两条边界语义

**测试布点**：纯数据结构 → 新增 `src/tests/outputview_linecache_test.cj`（package `cjh.tests`，无需 PTY）；TUI 视觉回归 = 既有 PTY 15 场景 + `src/tests/tui_test.cj`。用例：
1. 连续单行 append（缓存增量维护，与参考 split 一致）
2. 多行 append（含 `\n` 在中间 / 以 `\n` 结尾 / 以 `\n` 开头）
3. `endStream` 思考段替换（替换后行数与内容与参考一致）
4. `setThinking` / resize 失效后全量重建，与参考一致
5. 可见窗口计算优化前后不变（PTY 15 场景覆盖滚动 / 思考块 / 中文 / resize）

**风险**：中。增量逻辑简单但等价性须严格（边界语义逐位一致）；视觉输出不变，PTY 15 场景预期**原样通过**（即回归探测器）。

### P2b：TUI 视觉层次美化（新增项，2026-09-05）

**背景**：用户反馈当前 TUI 较难看——状态栏边框（即输入区上方 `+-- # model > [ cwd ] > ready ->-----+`，ASCII `-` 细线）不明显；输出区无层次。omp（pi）好看的原因：不同内容用**背景色卡片**区分（用户输入 / 工具 / 思考 / 状态栏各有独立 bg）、边框连续实线、markdown 有层次色。

**设计（参考 omp `dark.json` 实际色值，xterm-256 近似）**

1. **边框 → 彩色 Unicode 实线**（`statusbar.cj`，即"输入框 -- 线"）

   - 状态栏整行铺背景 `THEME_STATUS_BG`（234 ≈ omp statusLineBg `#121212`），文字颜色维持现状
   - 输入行 `╰─ ❯ `（`input.cj`）：`╰─` 用 `THEME_BORDER`（随主题），`❯` 保持 accent——与状态栏下边框视觉衔接
2. **输出区内容背景色卡片**（核心改进）

   |---|---|---|
   | 用户输入回显行 | 237 | userMessageBg `#221d1a` |

3. **NO_COLOR 支持**（`ansi.cj`，标准语义）：`Ansi` 缓存读 `ProcessEnv.get("NO_COLOR")`，设了则 fg/bg/bold 等返回空串（`--mock`/CI 纯文本输出保持干净；PTY 测试不设 NO_COLOR 不受影响）

5. **改动落点清单**
   - `libs/cjterm/src/ansi.cj`：+ NO_COLOR + 新色常量（THEME_STATUS_BG 234 / THEME_USER_BG 237 / THEME_TOOL_BG 236 / THEME_THINKING_BG 233 / THEME_CODE_BG 236 / THEME_LINK 51 / THEME_BORDER 244）+ `padBg`
   - `libs/cjterm/src/statusbar.cj`：边框 Unicode 实线 + 着色 + 整行 bg 234
   - `libs/cjterm/src/input.cj`：`╰─` → THEME_BORDER
   - `libs/cjterm/src/theme.cj`：10 个主题各设 `.border`（随主题变色，默认 244 仅回退）

- **风险**：低-中。PTY 测试断言纯文本子串（`ready`/`❯`/`+--`），边框字符变更需**同步更新** `scripts/tui_pty_test.py` 断言串；整行 bg 补空格依赖 displayWidth 正确计算中文宽字符，否则卡片边缘错位。
- **验收**：PTY 15 场景全过（断言串同步后）+ `src/tests/tui_test.cj` 视觉断言 + 截图级人工目检（暗色终端下层次可见）。
- **踩坑（P2b 已踩，勿重踩）**：
  1. **整行 bg 卡片禁止中途 `Ansi.reset()`**——reset 清全部属性（含 bg），会把卡片背景截断成两段；卡片行内只可用 `fg()`/`italic()` 等改色（不清 bg），行尾 reset 由 `Ansi.padBg` 统一补。`Logo.badge()` 内含 reset，进卡片时已内联为 fg-only；用户回显卡片把 `❯ accent → reset` 改成 `❯ accent → COLOR_TEXT 重设`。
  2. **卡片补空格须到 `cols-1` 而非 `cols`**——`TuiCanvas.truncate` 只保留 `cols-1` 可见列（防终端折行的边距，`maxVisible = cols-1`）；组件 render 收到的 `width` 等于 canvas `cols`，若按 `width` 补，行尾字符（状态栏 `┐`/卡片尾）会被 truncate 裁掉。`padBg` 各调用点统一传 `width-1`；agent 线程追加卡片（用户/工具行）用 `TuiApp.lastCols`（renderInner 每帧刷新）补 `lastCols-1`。
  3. **markdown.cj 无列表/引用/链接渲染器**——头注释只列粗体/行内代码/代码块/表格/ATX 标题；设计第 4 条的 `•` 列表 / `>` 引用 / 链接 `[..](..)` 属新增流式状态机（非美化），本批未做，留后续。标题 bold+accent 原已具备（`flushHeading`）。
  4. **PTY 断言无需改**——`tui_pty_test.py` 只断言 `❯`/`╰─`/`ready` 等，未断言状态栏 `+--` 边框；Unicode 边框（`┌─`）与整行 bg 不影响这些子串匹配（PTY 缓冲先剥 ANSI）。
  5. **边框色曾恒灰（已修）**——`apply()` 写回 `Ansi.THEME_BORDER = p.border`，但主题表**无一处**赋值 `.border`，导致 10 个主题全部回退 `Palette.border` 默认 244（中灰），`/theme` 切换边框不变色。修：每个主题显式设 `.border`（同色系醒目色），`Palette.border=244` 仅作未设主题的回退。教训：`apply()` 已写回的字段 ≠ 主题表已填充——新增 `Palette` 字段后须在**每个**内置主题里赋默认值，否则静默回退。
