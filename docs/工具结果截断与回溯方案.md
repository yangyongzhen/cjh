# 工具结果截断与回溯方案

> 创建：2026-08-25
> 性质：V2d 并发引擎配套 / 上下文管理优化
> 参考：Pi spill extension（tool-result pruner + spill file + read_tool_result）
> 背景：DSH 的 8192 字符朴素截断会造成「主动失忆」——被裁掉的中间区段永久丢失，模型未来需要时无回溯路径

---

## 一、问题

cjh 当前的 `truncateToolResult`（`loop.cj:439`）是朴素截断：

```
原始结果 [前3000][中间内容][后3000]
    ↓
模型看到 [前3000][…截断 N 字符…][后3000]
```

- **阈值**：6000 字符（硬编码，头尾各半）
- **中间内容**：**永久丢弃**，不落盘，无回溯路径

**真实案例**（参考头条文章）：
- Agent grep 出 21,800 字符的日志，错误堆栈在第 7000 字符附近
- 按 6000 阈值截断，错误堆栈正好落在被丢弃的中间区段
- 模型基于残缺信息推理，大概率给错误结论
- 一个下午遇到 7 次截断，每次都迫使模型从头重新生成整个插件源码

**根因**：截断本身不是问题（Context 有限，必须裁），问题是**被裁掉的信息没有回溯路径**。模型「现在看不到」和「永远找不到」是两回事。

---

## 二、设计目标

```
截断可以有，但截断必须透明。
透明之后，还得给模型留一条回去的路。
```

1. **透明截断**：超长结果在上下文里只保留头尾 + 省略标记（省 token）
2. **完整落盘**：被截断的完整结果写入磁盘文件（信息不丢）
3. **回溯路径**：省略标记里包含落盘文件路径（这把「钥匙」），模型可用 `read_file` 按需读回

**与 DSH 朴素截断的本质区别**：
- DSH：Context 裁了，中间永久丢失，模型找不到
- cjh（本方案）：Context 裁了，完整结果在磁盘，模型随时可读回

---

## 三、技术设计

### 3.1 截断 + 落盘流程

```
工具执行完毕，返回 result.content（可能很长）
    ↓
truncateToolResult(content, toolName, toolCallId, spillDir)
    ↓
if (content.size <= MAX_CHARS) → 原样返回，不落盘
    ↓
if (content.size > MAX_CHARS) →
    1. 完整 content 写入 spillDir/<toolCallId>.txt
    2. 构造省略标记，包含：跳过字符数 + 落盘文件路径
    3. 返回：head + 省略标记 + tail
```

### 3.2 省略标记格式

```
\n\n…[已截断 15800 字符，完整结果已保存：~/.cjh/spill/<sessionId>/call_abc123.txt，可用 read_file 读取]…\n\n
```

包含三个信息：
- **跳过字符数**：让模型知道省了多少
- **落盘路径**：这把「钥匙」，模型用它读回完整结果
- **回溯提示**：告诉模型用 `read_file` 读取

### 3.3 回溯方式

**复用现有 `read_file` 工具**，不新增工具。

理由：
1. `read_file` 已经支持 `offset`/`limit` 参数，天然能按区段读取
2. 模型对 `read_file` 已经很熟悉，不需要学习新工具
3. 落盘文件就是普通文本文件，`read_file` 能直接读

模型回溯示例：
```
模型看到省略标记：…[已截断 15800 字符，完整结果已保存：~/.cjh/spill/sess_xxx/call_abc.txt]…
    ↓
模型调用：read_file(path="~/.cjh/spill/sess_xxx/call_abc.txt", offset=6000, limit=2000)
    ↓
模型拿到第 6000-8000 字符区段（错误堆栈所在）
```

### 3.4 截断阈值设计

**不是所有工具都用同一个阈值**。对标 Pi v0.13.2 的工具差异化截断。

| 工具 | 阈值（字符） | 说明 |
|------|-------------|------|
| `bash` | 8000 | 命令输出可能很长，但头尾通常够用 |
| `grep` | 6000 | 搜索结果多时截断 |
| `read_file` | 不截断 | 已有 skeleton 机制，大文件返回符号摘要 |
| `list_dir` | 4000 | 目录树过长时截断 |
| 其他 | 6000 | 默认值 |

**全局阈值**：`toolResultMaxChars`（settings.json 可配，默认 6000）
**单工具阈值**：未来可通过工具声明覆盖全局阈值（本次先硬编码）

### 3.5 落盘目录设计

```
~/.cjh/spill/<sessionId>/<toolCallId>.txt
```

- `sessionId`：会话隔离，不同会话的落盘文件不混
- `toolCallId`：LLM 生成的 tool_call ID（如 `call_abc123`），唯一标识这次工具调用的完整结果
- 文件权限：默认 0644（与 sessions/ 一致）

**生命周期**：
- 落盘文件在会话存续期间一直可用
- 会话删除时（`/new` 或手动删 session），对应的 spill 目录一并删除
- **不自动清理**：模型可能在任意轮次回溯，提前清理会丢失信息

## 四、改造点

### 4.1 `truncateToolResult` 升级（`loop.cj:439`）

**现状**：
```cangjie
private func truncateToolResult(content: String, toolName: String): String {
    let MAX_CHARS: Int64 = 6000
    if (Int64(content.size) <= MAX_CHARS) { return content }
    let headLen: Int64 = MAX_CHARS / 2
    let tailLen: Int64 = MAX_CHARS - headLen
    let head = content[0..Int64(headLen)]
    let tailStart = Int64(content.size) - tailLen
    let tail = content[Int64(tailStart)..Int64(content.size)]
    let skipped = Int64(content.size) - MAX_CHARS
    return head + "\n\n…[截断 " + skipped.toString() + " 字符]…\n\n" + tail
}
```

**改造后**：
```cangjie
private func truncateToolResult(
    content: String,
    toolName: String,
    toolCallId: String
): String {
    let maxChars = this.toolResultMaxChars(toolName)
    if (Int64(content.size) <= maxChars) { return content }

    let headLen = maxChars / 2
    let tailLen = maxChars - headLen
    let head = content[0..Int64(headLen)]
    let tailStart = Int64(content.size) - tailLen
    let tail = content[Int64(tailStart)..Int64(content.size)]
    let skipped = Int64(content.size) - maxChars

    // 落盘完整结果
    let spillPath = this.spillPath(toolCallId)
    this.writeSpill(spillPath, content)

    // 省略标记包含落盘路径（这把钥匙）
    return head
        + "\n\n…[已截断 " + skipped.toString()
        + " 字符，完整结果已保存：" + spillPath
        + "，可用 read_file 读取]…\n\n"
        + tail
}
```

### 4.2 新增辅助方法（`loop.cj`）

```cangjie
// 工具差异化阈值
private func toolResultMaxChars(toolName: String): Int64 {
    match (toolName) {
        case "bash" => 8000
        case "grep" => 6000
        case "list_dir" => 4000
        case _ => 6000
    }
}

// 落盘路径：~/.cjh/spill/<sessionId>/<toolCallId>.txt
private func spillPath(toolCallId: String): String {
    return this.spillDir + "/" + this.sessionId + "/" + toolCallId + ".txt"
}

// 落盘写入
private func writeSpill(path: String, content: String): Unit {
    try {
        let dir = path.substring(0, path.lastIndexOf("/"))
        if (!exists(dir)) { Directory.create(dir, recursive = true) }
        File.writeAllText(path, content)
    } catch (e: Exception) {
        Log.warn("spill 落盘失败: ${e}")
        // 落盘失败不影响截断本身，只是丢了回溯路径
    }
}
```

```
## 工具结果截断

当工具返回的结果过长时，cjh 会自动截断：
- 保留结果的头部和尾部

- 省略标记里会显示完整结果的保存路径

```

## 六、会话清理

### 6.1 `/new` 新建会话

`/new` 时删除当前会话的 spill 目录：

```cangjie
case "/new" =>
    // 清理当前会话的落盘文件
    let spillSessionDir = cjhCfg.spillDir + "/" + CliSession.id
    if (exists(spillSessionDir)) {
        Directory.delete(spillSessionDir, recursive = true)
    }
    // ...其余新建会话逻辑...
```

### 6.2 会话恢复

`--resume <id>` 时**不清理** spill 目录——恢复的会话可能需要回溯之前的落盘结果。

### 6.3 启动时清理孤儿

cjh 启动时扫描 `~/.cjh/spill/`，删除没有对应 session 文件的孤儿目录（session 已删但 spill 没清的情况）。

```cangjie
func cleanOrphanSpills(sessionsDir: String, spillDir: String): Unit {
    if (!exists(spillDir)) { return }
    Directory.walk(spillDir, { fi =>
        // fi 是会话级子目录
        let sessionId = fi.name
        let sessionFile = sessionsDir + "/" + sessionId + ".json"
        if (!exists(sessionFile)) {
            Directory.delete(fi.path, recursive = true)
        }
    })
}
```

### 7.1 单元测试

| `testToolSpecificThreshold` | bash 阈值 8000、list_dir 阈值 4000 |

### 7.2 端到端测试

1. 让 Agent 跑一个会产生超长输出的 bash 命令（如 `find / -name "*.log"`）
2. 确认：
   - 上下文里是截断后的头尾 + 省略标记
   - `~/.cjh/spill/<sessionId>/<toolCallId>.txt` 文件存在
   - 文件内容是完整的原始输出
3. 让 Agent 用 `read_file` 读取落盘文件的指定区段
4. 确认 Agent 能拿到中间被截断的内容

### 7.3 性能验证

- 截断 + 落盘的耗时是否可接受（应该 < 10ms，只是字符串切片 + 一次磁盘写入）
- 落盘文件大小是否合理（完整 result.content，可能几 KB 到几十 KB）

## 八、风险与对策

| 风险 | 对策 |
|------|------|
| 落盘文件占用磁盘空间 | 每个文件就是一个工具结果的完整文本，通常几 KB；会话清理时删除；启动时清理孤儿 |
| 模型不知道怎么回溯 | 系统提示明确说明「用 read_file 读取省略标记中的路径」；省略标记本身就包含路径和提示 |
| 模型回溯时读到的还是截断后的 | 落盘的是**完整原始结果**，不是截断后的；`read_file` 读落盘文件拿到的是完整内容 |
| `toolCallId` 可能为空 | LLM 生成的 tool_call 通常带 ID；如果为空，用 `call_<timestamp>` 兜底 |
| 并发执行时多个工具同时落盘 | 落盘文件名包含 `toolCallId`，不会冲突；`File.writeAllText` 是原子写入 |

## 十、后续扩展

### 10.1 按区段摘要（替代朴素截断）

当前方案是头尾保留 + 中间丢弃。未来可以用 LLM 对中间区段做摘要：

```
[前4096][LLM摘要的中间区段][后1024]
```

好处：模型不用主动回溯就能看到中间内容的概要。
代价：每次截断多一次 LLM 调用（延迟 + token 成本）。

### 10.2 落盘结果索引

当落盘文件很多时（长会话 + 多次截断），模型可能不知道**哪个**落盘文件包含它需要的信息。

未来可以维护一个索引：

```
~/.cjh/spill/<sessionId>/index.json
[
  {"toolCallId": "call_abc", "tool": "bash", "command": "grep error log.txt", "path": "call_abc.txt", "chars": 21800},
  {"toolCallId": "call_def", "tool": "grep", "pattern": "TODO", "path": "call_def.txt", "chars": 8300}
]
```

模型可以先读索引，再精确定位需要回溯的落盘文件。

### 10.3 主动预读

模型回溯时通常是「我发现需要中间那部分信息」——这是被动回溯。

未来可以加启发式：如果模型在后续轮次提到了截断结果中的关键词，主动把对应区段注入上下文。
