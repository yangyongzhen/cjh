# cjh vs omp 工具执行效率差距分析

> 存档时间：2026-08-23
> 对照文档：`docs/omp agent的核心卖点.md`
> 背景：阅读 omp 卖点文档后，对照 cjh 当前工具实现，分析执行效率差距与优化优先级

## 一、omp 核心机制 vs cjh 当前实现

| omp 机制 | 效率收益 | cjh 当前实现 | 差距 |
|---------|---------|------------|------|
| **Hashline 哈希锚点编辑** | 编辑成功率 6.7%→68.3%（10×），输出 Token 减 61% | `write_file` 全文覆盖 | **最大差距**：全文重打→Token 燃烧，文件被改过就失效 |
| **read 结构化摘要** | Tree-sitter 提取符号，省一半 Token | `read_file` 全文 dump | 全文进上下文，大文件爆窗口 |
| **进程内 ripgrep/glob** | 零 fork/exec，搜索快 5-10× | `GrepTool` 逐行 `Regex.matches` | 纯仓颉实现，无 fork 开销，**这点 cjh 反而和 omp 同思路** |
| **并行子 Agent + 快照隔离** | 大任务并行，APFS clone/reflink | V2d 只做了**工具级并发**（read-only 批次 spawn） | 子 Agent 隔离未实现 |
| **LSP 14 操作** | 重命名/跳转/诊断走协议 | 无 LSP | 纯文本猜结构 |
| **流规则** | 正则命中→中断流→注入规则→重试 | 靠 system prompt | 规则占 Token 且模型常无视 |
| **Hindsight 项目级记忆** | 跨会话项目心智模型 | V2c 只做了**会话内 Compaction** | 跨会话项目级记忆未实现 |

## 二、工具执行效率具体分析

### 1. read_file：全文 dump vs 结构化摘要（omp 省一半 Token）

**cjh 现状**（builtin.cj:70-81）：
```cangjie
let bytes = File.readFrom(path)
return ToolResult(String.fromUtf8(bytes), false)  // 全文进上下文
```

**问题**：读一个 500 行文件，500 行全部进上下文窗口。omp 的 `read` 返回 Tree-sitter 结构化摘要（函数名/类名/重要注释），Agent 需要细节时再 `read` 展开具体行段——**省一半 Token**。

**cjh 的优势**：仓颉 std.fs 是进程内读取，零 fork/exec，和 omp 的进程内思路一致。但 omp 的结构化摘要才是真正的 Token 效率提升。

### 2. grep：进程内搜索，cjh 和 omp 同思路

**cjh 现状**（builtin.cj:135-162）：
```cangjie
let regex = Regex(pattern)
let content = String.fromUtf8(File.readFrom(path))
let lines = content.split("\n", -1)
for (line in lines) { if (regex.matches(line)) { ... } }
```

**对比**：omp 把 ripgrep 链接进进程，零 fork/exec。cjh 的 `GrepTool` 也是纯仓颉进程内实现（`std.regex.Regex` + 逐行匹配），**无 fork 开销**，和 omp 同思路。

**cjh 的差距**：
- 只搜单文件（`path` 参数），omp 的 ripgrep 搜整个目录树
- 无 `.gitignore` 感知，omp 的 ripgrep 自动跳过 `node_modules`/`target`
- 无上下文行（`-A/-B/-C`），omp 返回匹配周围几行

### 3. write_file：全文覆盖 vs Hashline 哈希锚点（最大差距）

**cjh 现状**（builtin.cj:102-114）：
```cangjie
File.writeTo(path, content.toArray())  // 全文覆盖
```

**问题**：模型必须输出完整文件内容。改一个 500 行文件里的一行，要重打 500 行——**Token 燃烧**。而且文件被其他工具改过，全文覆盖会丢改动。

**omp 的 Hashline**：模型用目标行内容哈希前缀标识位置（`@@{a3f2}`），只输出改动行，文件变了哈希对不上就拒绝（不打错地方）。基准数据：编辑成功率 6.7%→68.3%（10×），输出 Token 减 61%。

### 4. list_dir：进程内遍历，cjh 和 omp 同思路

**cjh 现状**（builtin.cj:182-209）：`Directory.walk` 进程内遍历，截断 50 项。和 omp 的进程内 find 同思路，无 fork 开销。

### 5. V2d 并发执行：工具级并发已实现，子 Agent 隔离未实现

**cjh 现状**：read-only 工具批次 `spawn` 并发 + `Future` 按原始顺序 `get()` 重排。这是**工具级并发**，和 omp 的「并行子 Agent + 文件系统快照隔离」不同层级。

**omp 的子 Agent**：平台原生文件系统快照（macOS APFS clone、Linux reflink/overlayfs、Windows projfs）隔离工作区，多个子 Agent 并行不冲突，每个返回 schema 校验的结构化对象。

## 三、效率差距优先级排序

| 优先级 | 差距 | 效率收益 | 实现难度 |
|--------|------|---------|---------|
| **P0** | write_file 全文覆盖 → Hashline 哈希锚点 | 编辑成功率 10×，Token 减 61% | 中（需哈希算法 + patch 应用） |
| **P1** | read_file 全文 dump → 结构化摘要 | Token 省一半 | 中（需 Tree-sitter 或符号提取） |
| **P2** | grep 单文件 → 目录树搜索 + gitignore | 搜索覆盖面 10× | 低（扩展 path 参数 + walk） |
| **P3** | 无 LSP → 14 操作 | IDE 级代码理解 | 高（需 LSP 客户端） |
| **P4** | 无子 Agent 隔离 → 文件系统快照 | 大任务并行 | 高（平台原生快照 API） |

## 四、结论

**cjh 的工具执行效率在搜索/遍历类工具上和 omp 同思路**（进程内、零 fork），但**编辑和读取两大核心工具效率差距明显**：

1. **write_file 全文覆盖是最大效率黑洞**——omp 的 Hashline 哈希锚点编辑成功率提升 10×、输出 Token 减 61%，这是数量级差距
2. **read_file 全文 dump 浪费上下文**——omp 的结构化摘要省一半 Token，立竿见影
3. **V2d 工具级并发已实现**，但 omp 的子 Agent + 文件系统快照隔离是更高层级并行，cjh 暂未实现

## 五、P0-P2 实现计划

### P0: Hashline 哈希锚点编辑
- 新增 `HashlineEdit` 工具（或改造 `write_file`）
- 模型输出格式：`@@{hash_prefix}` 标识目标行 + 改动内容
- 文件变了哈希对不上 → 拒绝（不打错地方）
- 哈希算法：行内容 SHA-256 前 4-6 hex 字符
- patch 应用：定位哈希行 → 替换/删除/插入
- 基准：编辑成功率应大幅提升（omp 实测 6.7%→68.3%）

### P1: read_file 结构化摘要
- 改造 `ReadTool`：默认返回结构化摘要（函数名/类名/重要注释）
- 添加 `offset`/`limit` 参数：按需展开具体行段
- 符号提取：仓颉无 Tree-sitter，可用 `list_symbols` 思路（正则匹配函数/类定义）
- Token 效率：大文件摘要 << 全文 dump

### P2: grep 目录树搜索 + gitignore
- 改造 `GrepTool`：`path` 参数支持目录（递归搜索）
- `.gitignore` 感知：跳过 `node_modules`/`target`/`.git` 等
- 上下文行：添加 `context` 参数（匹配行周围 N 行）
- 与 omp ripgrep 对齐：进程内、gitignore、目录树
