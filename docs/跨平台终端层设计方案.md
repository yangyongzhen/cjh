# 跨平台终端层设计方案（TUI 层 termios 抽象化）

> 状态：待评审（2026-08-30）· 是否实施由用户决定
> 目标读者：cjh 维护者
> 关联：`libs/cjterm/src/term.cj` · `cjpm.toml` · README「多后端编译」卖点

---

## 1. 背景：跨平台是仓颉的天然优势，但 TUI 层挡在了 Linux

仓颉语言多后端编译（cjnative / cjvm / 鸿蒙）本身就是跨平台卖点，README 已将其列为差异化优势。但当前 **TUI 层直接 FFI termios，仅 Linux/macOS（POSIX）可编译**，Windows 原生控制台无法运行——「多后端编译」的跨平台承诺在终端 UI 这里断链。

现状盘点（`libs/cjterm/src/term.cj`，873 行，纯 FFI 无第三方 .so）：

| 函数 | 用途 | 平台 | 归属 |
|---|---|---|---|
| `tcgetattr / tcsetattr` | 原始模式开关（清 ICANON/ECHO/ISIG…） | POSIX only | `Term.enableRaw/disableRaw` |
| `ioctl(TIOCGWINSZ)` | 终端尺寸查询 | POSIX only | `Term.size` |
| `select` | 输入轮询 / 超时等待 | POSIX only | `Term.hasInput/waitInput` |
| `read(fd=0)` | 按键字节读取 | POSIX only | `Term.readKey` |
| `open/dup2/dup/close` + `/dev/null` | stderr 屏蔽 | POSIX only | `Stderr.suppress/restore` |
| `getenv` | 环境变量（UTF-8 检测/兜底尺寸） | 通用 | `TermEnv` |
| ANSI 转义（print） | 备用屏/鼠标/差分渲染 | **可移植**（VT 模式） | `Term.enterAltScreen` 等 + 全部渲染层 |

关键洞察：**输出侧（ANSI/VT 转义 + 差分渲染）本就跨平台**——Windows 10 1809+ 控制台与 Windows Terminal 原生支持 VT 序列。真正的 Linux 依赖集中在**输入侧**（原始模式 + 按键读取 + 尺寸查询），全部可被 Win32 Console API 等价替代。

---

## 2. 设计目标

1. **抽象一层终端后端**，`Term` 对外 API 不变 → TUI 上层（screen/component/editor 等 3700+ 行）零改动
2. **Windows 原生支持**：VT 输出（复用现有渲染）+ Win32 Console API 输入，条件编译选择实现
3. **保持单二进制零依赖卖点**：Windows 下依赖 kernel32.dll 等**系统自带库**（等价于 Linux 依赖 libc），不引入第三方运行时
4. **不破坏现状**：Linux/macOS 走现有 termios 实现，行为不变（238 单测全绿为回归基线）

---

## 3. 抽象层设计：TerminalBackend

### 3.1 接口定义（新文件 `libs/cjterm/src/backend/backend.cj`）

与 `Term` 现有功能一一对应，仅剥离平台相关实现：

```cangjie
public interface TerminalBackend {
    // 原始模式：关闭行缓冲/回显/信号键，逐键读取
    func enableRaw(): Bool
    func disableRaw(): Unit
    // 输入探测
    func hasInput(): Bool                  // 非阻塞
    func waitInput(timeoutMs: Int64): Bool // 带超时
    // 按键读取（UTF-8 完整字符 + 转义序列 → KeyEvent）
    func readKey(): Option<KeyEvent>
    // 终端尺寸（行, 列）
    func size(): (Int64, Int64)
    // stderr 屏蔽（TUI 全屏防污染）
    func suppressStderr(): Bool
    func restoreStderr(): Unit
}
```

`Term` 类保留全部公共 API（`enableRaw/readKey/size/…`），内部委托给 `TerminalBackend` 实例。`KeyEvent` 结构（ch/方向键/功能键枚举）**平台无关**，由各后端把原始输入规范化为统一事件——Windows 输入事件（方向键/退格/Tab/功能键）映射到与 POSIX 转义序列解析**完全相同的 KeyEvent 语义**。

### 3.2 渲染层不动

`Ansi` 常量、差分渲染、screen/component 全部依赖 ANSI 转义序列（`ESC[` 控制码），Windows VT 模式逐字节兼容 → **零改动**。

## 4. 平台实现

### 4.1 POSIX backend（`term_posix.cj`）——现有代码原样迁移

`tcgetattr/ioctl/select/read/open/dup2` 全部保留，逻辑不变，从 `Term` 类搬进 `PosixTerminalBackend`。Linux 与 macOS 共用（macOS termios 兼容，仅 `TIOCGWINSZ` 等常量一致）。

### 4.2 Windows backend（`term_win.cj`）——VT 输出 + Win32 输入

**输出（渲染）**：`EnableVirtualTerminalProcessing` 开启控制台 VT 模式后，现有 ANSI 转义序列直接工作（Windows 10 1809+ / Windows Terminal / VS Code 终端）。fallback：旧 conhost 不支持 VT 时检测失败 → 明确报错提示升级或退 ASCII。

**输入（原始模式 + 按键）**：`SetConsoleMode` 清 `ENABLE_LINE_INPUT | ENABLE_ECHO_INPUT | ENABLE_PROCESSED_INPUT`（等价 POSIX raw 模式），`ReadConsoleInput` 读 `KEY_EVENT_RECORD` → 映射 KeyEvent：

| Win32 事件 | 映射 KeyEvent |
|---|---|
| 可打印字符（含 UTF-16 → UTF-8） | `ch = 码点` |
| `VK_LEFT/RIGHT/UP/DOWN` | 方向键（与 ESC[A/B/C/D 同义） |
| `VK_BACK` | 退格（ch=127，与 POSIX 对齐） |
| `VK_TAB` | Tab（ch=9） |
| `VK_RETURN` | 回车（ch=13） |
| `VK_DELETE/HOME/END/PRIOR/NEXT` | 功能键（与 ESC[3~/[H/[F/[5~/[6~ 同义） |
| `VK_ESCAPE` | ESC（ch=27），后随键按转义序列语义合并 |

**尺寸**：`GetConsoleScreenBufferInfo`（`CONSOLE_SCREEN_BUFFER_INFO.srWindow`）→ (rows, cols)。

**stderr 屏蔽**：无 `/dev/null` 概念 → `SetStdHandle(STD_ERROR_HANDLE, INVALID_HANDLE_VALUE)` 或重定向到 NUL 设备（`CreateFile("NUL")` + `SetStdHandle`）。语义等价，实现两行差异。

**UTF-8 检测**：`GetConsoleOutputCP() == 65001`（或 `GetACP`），替代 locale 字符串判断。

### 4.3 macOS backend

复用 POSIX backend（termios 兼容）。README 的跨平台矩阵：Linux ✓ / macOS ✓（POSIX 直通）/ Windows ✓（本方案）/ 鸿蒙（仓颉多后端，未来）。

## 5. 条件编译：`@When` + `--cfg` 注入平台标识

### 5.1 语法（仓颉内置注解）

```cangjie
// 仅当编译期 cfg os=windows 时编译此文件/声明
@When[os == "windows"]
public class WindowsTerminalBackend <: TerminalBackend { ... }

@When[os != "windows"]
public class PosixTerminalBackend <: TerminalBackend { ... }
```

编译期注入：`cjc --cfg "os=windows"`（cjpm 经 `compile-option` 透传）。

### 5.2 cjpm.toml 接线

```toml
# 根 cjpm.toml：按 target 传 cfg
[target.x86_64-pc-windows-msvc]
    compile-option = "--cfg os=windows"
    # 或 package-configuration = { os = "windows" }
[target.x86_64-unknown-linux-gnu]
    compile-option = "--cfg os=linux"
```

`Term` 的 backend 工厂：

```cangjie
public func createBackend(): TerminalBackend {
    @When[os == "windows"] { return WindowsTerminalBackend() }
    @When[os != "windows"] { return PosixTerminalBackend() }
}
```

条件编译发生在**编译期**：同一份源码，`cjc --cfg` 不同 → 编译出不同平台的二进制，无运行时平台探测开销（`Rune(27)` 级别的零成本）。

### 5.3 不采用运行时探测的原因

`#ifdef` 式运行时判断（如 `getenv("OS")` 或 `uname`）有两点劣势：① 两个后端的 FFI 符号会同时进入二进制，Windows 下链接 `tcgetattr` 直接失败；② 运行时分支违背「编译期能力优先」的项目设计原则（方案-v2 第 7 节）。仓颉 `@When` 从语言层面解决，与「语言特性即差异化」一致。

## 6. C 代码嵌入方式：`@C` 声明 vs 独立 .c 文件

Windows 控制台 API 在 `kernel32.dll`，两种接入方式：

### 6.1 方式 A（推荐）：`@C` foreign 声明 Win32 API —— 与现状同构

```cangjie
@C
foreign func GetStdHandle(nStdHandle: Int32): CPointer<Void>
@C
foreign func SetConsoleMode(h: CPointer<Void>, mode: UInt32): Bool
@C
foreign func GetConsoleMode(h: CPointer<Void>, mode: CPointer<UInt32>): Bool
@C
foreign func ReadConsoleInputW(h: CPointer<Void>, buf: CPointer<UInt8>, len: UInt32, read: CPointer<UInt32>): Bool
@C
foreign func GetConsoleScreenBufferInfo(h: CPointer<Void>, buf: CPointer<UInt8>): Bool
@C
foreign func WriteConsoleW(h: CPointer<Void>, s: CPointer<UInt16>, n: UInt32, written: CPointer<UInt32>, _: CPointer<Void>): Bool
```

与 term.cj 现有 termios FFI **完全同模式**（手工内存布局 + `@C` 声明），零 `.c` 文件、零编译链改动。`kernel32.dll` 是 Windows 系统自带（等价 Linux 的 libc），**单二进制零依赖卖点不变**。

优点：不引入 C 工具链依赖（Windows 交叉编译时不需要额外 cc）；缺点：`INPUT_RECORD`/`CONSOLE_SCREEN_BUFFER_INFO` 等结构体需手写内存布局（有 termios 60 字节布局经验，可复用方法论）。

### 6.2 方式 B（备选）：独立 `win_term.c` + 链接

`@C` 内嵌声明 + 一个 `win_term.c`（封装 raw 模式/读键/尺寸为 6 个纯 C 函数），cjc 链接 `-l` 或直接编入。结构体布局交给 C 编译器，仓颉侧只留 6 个函数签名。

缺点：Windows 交叉构建需 C 工具链（MSVC/mingw）；与「纯仓颉实现」宣传略有出入。**仅当方式 A 的 INPUT_RECORD 布局验证困难时启用。**

### 6.3 决策

**默认方式 A**：与现有 termios FFI 方法论一致、零新工具链依赖、保持"纯仓颉 + 系统库"叙事。若实施中发现 `INPUT_RECORD` 联合体（16 字节事件记录，含鼠标/窗口事件类型）布局在目标仓颉版本上解析不稳，降级方式 B。

## 7. 构建矩阵与验证

| 目标 | 后端 | 构建 | 验证 |
|---|---|---|---|
| Linux x86_64 | POSIX（现有） | cjnative ✓ 现有 CI | 238 单测 + PTY 集成（现有） |
| macOS | POSIX（直通） | cjnative | 手动冒烟（raw 模式/尺寸/中文输入） |
| Windows 10 1809+ | Win32 VT | cjnative + `--cfg os=windows` | Windows 终端/ConPTY 冒烟 + 单元测试（backend 可 mock） |
| WSL | POSIX（termios 可用） | 同 Linux | 无需特殊处理 |

**测试策略**：`TerminalBackend` 接口使测试可注入假后端（`FakeBackend` 返回预设按键序列），`Term`/TUI 层逻辑在无 TTY 环境可测——比现状（`Term` 直接 FFI，构造不碰 FFI 但按键逻辑难测）可测性提升。现有 238 单测为回归基线，P0 阶段必须保持全绿。

## 8. 实施计划（分阶段，每阶段可独立交付）

| 阶段 | 内容 | 交付 | 验收 |
|---|---|---|---|
| **P0 抽象重构** | 拆 `TerminalBackend` 接口 + `PosixTerminalBackend`（现有代码原样搬移），`Term` 改委托 | 行为零变化 | 238 单测全绿 + PTY 冒烟通过 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 旧 conhost（Win10 1809 前）无 VT 模式 | 渲染层失效 | `GetConsoleMode` + `SetConsoleMode(ENABLE_VIRTUAL_TERMINAL_PROCESSING)` 检测，失败则明确报错提示升级/用 Windows Terminal；不静默降级到无渲染 |
| `INPUT_RECORD` 联合体内存布局手写 | 按键读取错乱 | 方式 A 验证失败 → 降级方式 B（.c 文件）；P1 首日先做布局验证 spike |
| 仓颉 Windows 工具链成熟度（cjc 对 MSVC/mingw 目标支持、stdx 动态库） | 构建失败 | P0 阶段先做 `cjc --target x86_64-pc-windows-msvc` 最小验证（hello + FFI kernel32），确认链路再投入 |
| UTF-8 代码页（GBK 控制台） | 中文乱码 | `chcp 65001` 检测 `GetConsoleOutputCP()`，非 UTF-8 时 `isUtf8()` 返回 false 走 ASCII 降级（现有逻辑已支持） |
| `std.env.getWorkingDirectory` 等标准库平台差异 | 非 TUI 层问题 | 属另一议题，本方案聚焦 cjterm；README 跨平台声明以终端层为准 |
| 鼠标 SGR 1006 在 Windows VT 的兼容差异 | 滚轮/点选异常 | 鼠标为可选增强（`enableMouse`），Windows 下可先禁用或映射 Win32 鼠标记录 |

## 11. 结论

可行，且是「仓颉多后端编译」卖点的**必要补齐**——否则跨平台只是编译层面的话术，终端 UI 层仍锁死 Linux。方案要点：

1. **抽象一层 `TerminalBackend`**，`Term` 对外 API 不变，TUI 上层零改动
2. **Windows = VT 输出（复用现有渲染）+ Win32 输入（映射统一 KeyEvent）**，`@When` 条件编译选后端
3. **C 代码嵌入用 `@C` 声明 kernel32 API**（方式 A），与现有 termios FFI 同模式，零新工具链依赖，单二进制卖点不变
4. 三阶段实施（P0 抽象重构 → P1 Windows 后端 → P2 打磨），每阶段独立验收，238 单测为回归基线
